Master Data Reference

마스터데이터 레퍼런스

NPC 서버를 동작시키는 정적 데이터 전체 정의다. masterdata/가 단일 원천(SSOT)이며, LLM 프롬프트 프리픽스는 여기서 생성된다. 액션·플래그·아키타입을 코드에 하드코딩하지 않는다 — 둘이 어긋나면 검증 실패율이 즉시 치솟는다.

SSOT 플래그 43액션 37 아키타입 40버킷 2,880
로딩 규약기동 시 전량 로드 → 검증 → 불변. 검증 실패는 기동 실패다.
번호 규칙code·bit 번호를 재배치하지 않는다. 추가는 뒤에만.
생성물prompt/ 카탈로그와 npc_instances는 손으로 편집하지 않는다.
01

파일 목록과 규모

masterdata/
  world_flags.json        월드 상태 비트 플래그 정의 (64bit 중 42개 사용)
  actions.json            액션 카탈로그 (37)
  items.json              아이템·자원 (82) + 레시피
  zones.json              존 (12)
  pois.json               관심지점 (243)
  poi_distances.bin       POI 간 거리 행렬 (사전계산, Half 행렬)
  archetypes.json         NPC 아키타입 (40)
  context_buckets.json    시간대·지역상태·기후 정의 + 버킷 키 규칙
  interrupts.json         인터럽트 규칙 (14)
  fallback_plans.json     폴백 플랜 (수동 작성, 아키타입당 1개 = 40)
  npc_instances.json      NPC 인스턴스 (5,000, 생성 스크립트 산출물)
  prompt/
    system_rules.md       시스템 규칙 (프롬프트 프리픽스 1부)
    fewshot/*.json        few-shot 예시
로딩 규약

기동 시 전량 로드 → 스키마 검증 → 참조 무결성 검증 → 읽기 전용 인덱스로 컴파일 → 이후 불변. 검증 실패는 기동 실패다. 경고 후 진행을 허용하지 않는다.

번호를 재배치하지 않는다

code 번호와 bit 번호를 옮기면 프리베이크된 플랜 2,880개가 통째로 깨진다. 추가는 항상 뒤에만.

검증만 따로 돌릴 수 있다.

dotnet run --project src/Npc.Host -- validate --masterdata ./masterdata

world_flags.json — 월드 플래그 43비트

플랜의 전제조건·효과, 인지 스캔의 이탈 판정이 전부 이 64비트 위에서 돈다. 가장 먼저 확정해야 하는 파일이다. 43개를 정의하고 bit 22~23과 45~63은 예약한다.

이탈 판정 — 인지 스캔의 핵심 연산

비트 연산 세 번이다. NPC 5,000을 매 틱 훑어야 하므로 이보다 무거우면 안 된다.

static bool IsDeviated(WorldFlags cur, WorldFlags required,
                       WorldFlags requiredAny, WorldFlags forbidden)
    => (required & ~cur) != 0
    || (requiredAny != 0 && (requiredAny & cur) == 0)
    || (forbidden & cur) != 0;
03

actions.json — 액션 카탈로그 37개

LLM이 조합할 수 있는 유일한 원자 단위다. 이 파일이 곧 프롬프트 프리픽스의 본문이 된다. 상한은 40개이며, 추가하려면 하나를 빼거나 기존 액션의 파라미터로 흡수한다.

스키마

{
  "id": "MoveTo",                    // 플랜 DSL에서 이 문자열을 쓴다
  "code": 1,                         // 내부 ushort. 절대 재배치 금지
  "category": "movement",
  "desc": "지정한 POI로 이동한다",    // ← LLM 프롬프트에 그대로 실린다

  "params": {                        // JSON Schema 부분집합
    "poi":   { "type": "poi_ref", "required": true },
    "speed": { "type": "enum", "values": ["walk", "run"], "default": "walk" }
  },

  "requires":     [],                          // 전제 플래그 — 전부 성립 (AND)
  "requires_any": [],                          // 전제 플래그 — 하나 이상 (OR). 비면 검사 안 함
  "forbids":   ["IsSleeping", "IsExhausted"],  // 금지 플래그
  "grants":    [],                             // 성공 시 세팅되는 플래그
  "clears":    ["AtHome","AtWorkplace","AtMarket","AtTavern",
                "AtTemple","AtGate","AtField","InWilderness"],

  "duration": { "kind": "distance", "base_s": 0, "per_meter_s": 0.6 },
  "cost": 2,                                   // 계획 시 비용 힌트 (LLM에 노출)
  "default_timeout_s": 300,

  "emits": [                                   // 게임서버 명령 매핑
    { "command": "MoveTo", "priority": "Normal",
      "map": { "TargetPoi": "$poi", "Flags": "$speed" } }
  ],
  "completes_on": ["NpcArrived"],              // 이 이벤트 수신 시 스텝 완료
  "fails_on":     ["NpcActionFailed"]
}

emits[].map 값 문법

값뜻
"$param"플랜 스텝의 args에서 가져온다
"$home" "$workplace" "$self" "$zone"NPC 인스턴스에서 바인딩한다
"$first:Flag"해당 플래그를 세우는 인벤토리 아이템 중 첫 번째 (Eat·Drink)
그 외 문자열아이템 id 또는 열거값 리터럴
숫자정수 리터럴 (부호 있음)

emits[].priority는 역압 시 드롭 순서다. 생략하면 Normal이다.

// zones.json
{ "id": "town_center", "code": 1, "name_key": "zone.town_center",
  "adjacent": ["town_north","town_south","gate_east"],
  "default_region_state": "Peace",
  "default_climate": "Fair",
  "capacity": 1200 }

// pois.json
{ "id": "smithy_01", "code": 12, "zone": "town_center",
  "type": "workplace",        // home | workplace | market | tavern
                              // | temple | gate | field | wilderness
  "subtype": "smithy",
  "pos": { "x": 120.5, "y": 0.0, "z": -88.2 },
  "capacity": 3,
  "open_hours": { "from": "Morning", "to": "Evening" },
  "grants": ["AtWorkplace"],  // 이 POI에 있을 때 세팅되는 플래그
  "allowed_archetypes": ["blacksmith", "apprentice_smith"],
  "resources": []             // field 타입일 때 채집 가능 자원
}
allowed_archetypes는 출입 허가가 아니라 근무 허가다

일터·채집지·야외 작업지에서만 출입을 제한하고, 시장·선술집·신전·성문·주거는 공공장소라 누구나 드나든다. 농부가 시장에 못 가면 $market 바인딩이 실패한다.

poi_distances.bin은 Half 행렬이다. 이동 소요시간 계산과 검증기 3단(도달 가능성)에 쓰며, 빌드 스크립트가 pois.json에서 생성한다.

존의 default_region_state와 default_climate는 둘 다 초기 동기화 대상이다. 기후는 버킷 키의 한 축이라 하나만 보내면 그 존의 NPC가 다른 버킷의 플랜을 쓰게 된다.

context_buckets.json — 캐시 키 2,880

플랜 캐시의 키 공간을 정의한다. 수천 NPC가 같은 플랜을 공유하는 근거가 이 버킷이다.

{
  "dimensions": {
    "time_of_day": {
      "values": ["Dawn","Morning","Noon","Afternoon","Evening","Night"],
      "game_hours": { "Dawn":[5,7], "Morning":[7,11], "Noon":[11,14],
                      "Afternoon":[14,18], "Evening":[18,22], "Night":[22,5] },
      "world_flag": { "Dawn":"IsDawn", "Morning":"IsDay", "Noon":"IsDay",
                      "Afternoon":"IsDay", "Evening":"IsEvening", "Night":"IsNight" }
    },
    "region_state": { "values": ["Peace","Alert","War","Disaster"] },
    "climate":      { "values": ["Fair","Cold","Storm"] }
  },
  "key_format":  "{archetype}@{time_of_day}.{region_state}.{climate}",
  "key_example": "blacksmith@Evening.War.Cold",
  "total_keys":  2880       // 아키타입 수 × 6 × 4 × 3 — V6 이 계산해 대조한다 (코드는 안 읽는다)
}
// Npc.Core/Planning/BucketKey.cs
public readonly record struct BucketKey(ArchetypeId A, TimeOfDay T, RegionState R, Climate C)
{
    public const int PerArchetype = 6 * 4 * 3;                                     // 72
    public int ToIndex() => ((A.Value * 6 + (int)T) * 4 + (int)R) * 3 + (int)C;   // 아키타입 수와 무관
}

플랜 스토어는 Plan[total_keys] 고정 배열이면 충분하다. 조회는 인덱스 계산 한 번 — 해시맵도 필요 없다.

아키타입 수는 코드가 모른다

BucketKey.ArchetypeCount = 40 이라는 컴파일 상수였다(F-05 에서 제거). 지금은 archetypes.json 의 배열 길이가 정하고 MasterDataSet.Buckets(BucketSpace)가 ArchetypeCount·TotalKeys 로 들고 있다 — 플랜 스토어 배열 길이, 캐시 통계 배열, 히트맵 열 수가 전부 거기서 나온다. 배열은 기동 시 한 번 잡으므로 틱 루프의 조회 비용은 그대로다.

기존 첨자는 변하지 않는다. ToIndex() 식에 아키타입 수가 들어가지 않고 아키타입이 가장 바깥 차원이라, 뒤에 추가한 아키타입은 뒤에만 자리를 만든다. 프리베이크된 플랜이 첨자 때문에 어긋나지 않는 이유다. 다만 아키타입 카탈로그는 프롬프트 프리픽스에 실리므로 추가하면 프리픽스 해시가 바뀌고, 그때는 플랜 스토어가 전량 무효다.

total_keys 는 사람이 읽는 기록으로 남긴다. V6 이 실제 조합 수와 대조하지만 코드는 이 값을 읽지 않는다.

권장 상한 128, 하드 상한 4,096(npc_ref payload 12비트). 실질 제약은 둘 다 아니고 프리픽스 토큰 비용이다.

2,880을 다 채울 필요는 없다

실측에서 실제로 도달한 버킷은 264개(9.2%)였다. 나머지는 조합상 존재하지만 시나리오에서 안 나온다. 프리베이크 우선순위를 region_state 가중치(Peace 10 : Alert 3 : War 2 : Disaster 1)로 두는 이유다.

interrupts.json — 인터럽트 규칙 15개

LLM이 만들지 않는다. 인터럽트는 반응 속도가 생명이라 결정론 규칙으로만 정의한다. 공격·도주·긴급 대피처럼 재현성이 중요한 행동이 전부 이 경로에 있다.

{ "id": "flee_on_threat", "priority": 100,
  "when": { "any_flag": ["ThreatNearby","InCombat"],
            "archetype_trait": { "courage": "<40" } },
  "then": { "action": "Flee", "params": { "poi": "$nearest_safe" } },
  "replan": { "urgency": 100 } },

{ "id": "fight_on_threat", "priority": 100,
  "when": { "any_flag": ["ThreatNearby"],
            "archetype_trait": { "courage": ">=40" }, "combat_capable": true },
  "then": { "action": "Attack", "params": { "target": "$threat" } },
  "replan": { "urgency": 90 } },

{ "id": "attack_hostile_player", "priority": 100,
  "when": { "any_flag": ["HostilePlayerNearby"], "combat_capable": true },
  "then": { "action": "Attack", "params": { "target": "nearest:hostile_player" } },
  "replan": { "urgency": 95 } },

{ "id": "yield_to_player", "priority": 90,
  "when": { "event": "PlayerInteracted" },
  "then": { "action": "Wait", "params": { "duration_s": 30 } },
  "replan": { "urgency": 70 } },

{ "id": "eat_when_starving", "priority": 50,
  "when": { "all_flag": ["IsHungry","HasFood"] },
  "then": { "action": "Eat" },

nearest:hostile_player — 대상이 플랜에 없다 (B-06)

플레이어 id 는 회차마다 다르므로 플랜에 박을 수 없다. 이 npc_ref 는 발행 시점에 NpcStore.HostilePlayer 를 읽어 CombatAction.TargetPlayer 에 싣고 TargetNpc 는 0 으로 둔다 — 둘 다 채우면 게임서버가 어느 쪽을 공격할지 모른다.

인터럽트의 target 은 $threat · self · nearest:hostile_player 셋만 받는다. nearest:<archetype> 는 근접 판정을 게임서버에 넘기는 값이라 즉시 반응과 맞지 않는다 — 모르는 값은 기동 실패다.

then은 즉시 실행되고 replan.urgency는 재계획 큐에 점수로 들어간다. 즉 "먼저 도망치고, 새 계획은 나중에 받는다".

발동은 엣지 트리거다

when 조건은 대부분 플래그라 한 번 참이 되면 한동안 참으로 남는다. 이벤트마다 다시 발동시키면 강제 액션 → 완료 이벤트 → 다시 강제의 되먹임이 생겨 명령 수가 NPC당 수천 건으로 폭주한다. 그래서 매처는 NPC별로 마지막 발동 규칙을 기억하고, 같은 규칙이 이어서 걸리면 넘긴다. 조건이 한 번 풀렸다가 다시 참이 될 때 재무장한다.

cooldown_s 같은 필드를 두지 않는다 — 시간 기반 쿨다운은 Tick에 의존해 리플레이 재현을 어렵게 만든다. 엣지 트리거는 상태만 보므로 결정론이다.

fallback_plans.json · npc_instances.json

폴백 플랜 — 아키타입당 1개, 40개 전부 사람이 쓴다

LLM과 캐시가 전부 실패했을 때 쓰는 최후 보루다. LLM 전면 차단 시나리오가 통과하는 이유가 이것이다.

{ "id": "fb_blacksmith", "archetype": "blacksmith",
  "goal": "survive_and_work",
  "steps": [
    { "action": "MoveTo", "args": { "poi": "$workplace" }, "timeout_s": 300 },
    { "action": "Work",   "args": { "recipe": "$primary", "count": 1 }, "timeout_s": 900 },
    { "action": "MoveTo", "args": { "poi": "$home" }, "timeout_s": 300 },
    { "action": "Sleep",  "args": { "until_time": "Morning" } }
  ],
  "loop": true }

$workplace·$home·$primary는 NPC 인스턴스에서 바인딩되는 심볼이다. 폴백 플랜은 반드시 loop: true여서 무한히 지속 가능해야 한다.

모든 스텝에 timeout_s가 있다. 응답 이벤트가 안 오면 로컬에서 실패를 합성해 진행을 재개한다 — 이것이 명령 유실 방어책이다.

NPC 인스턴스 5,000 — 생성물이다

tools/gen_npcs.cs가 population_weight와 POI capacity를 보고 만든다. 수동 편집 대상이 아니다.

{ "seed": 20260725,                    // 결정론 재현용
  "npcs": [
    { "id": 1, "archetype": "blacksmith", "zone": "town_center",
      "home_poi": "house_042", "workplace_poi": "smithy_01",
      "spawn_pos": { "x": 120.5, "y": 0.0, "z": -90.0 },
      "trait_offsets": { "diligence": +5, "sociability": -10 },   // ±15 개체 편차
      "initial_inventory": [ ... ] }
  ] }
개체 편차는 플랜 선택에 영향을 주지 않는다

같은 버킷의 NPC는 같은 플랜을 쓴다. trait_offsets는 실행 시 소요시간·대기시간·경로 랜덤화에만 쓴다. "같은 플랜인데 다 다르게 보이는" 값싼 다양성의 원천이다.

고정 프리픽스는 기동 시 1회 조립하고 이후 불변프롬프트 캐시

system_rules.md 요지

You are a behavior planner for NPCs in a fantasy MMORPG village simulation.

Your ONLY job: given an NPC's archetype and current situation, output a JSON plan
that composes actions from the catalog below.

HARD RULES
1. Use ONLY action ids from the catalog. Never invent an action.
2. Maximum 10 steps. Prefer 5-8.
3. Every step's `requires` flags must be satisfiable by the preceding steps' `grants`,
   or already present in the given `flags` field.
4. Reference POIs only by the symbolic forms: $home, $workplace, $market, $tavern,
   $temple, $gate, $nearest_field, $nearest_safe, $nearest_shelter.
   Never invent a POI id.
5. Do not include dialogue text. Use Speak with a dialogue id only.
6. The plan must be loopable or must end in a rest/sleep state.
7. Output JSON only. No prose, no markdown fences.

#검증

편집 안전장치 F-04

src/Npc.MasterData/Authoring/. Studio·CLI·MCP 가 같은 라이브러리를 부른다.

클래스무엇
CodeAllocator파일별 다음 code/bit. 예약 구간(reserved_bits)을 먼저 채운다 — "최대 + 1" 로 두면 22~23 처럼 비워 둔 구간을 영영 못 쓴다. 재배치 API 는 없다
WeightRebalancer새 가중치를 어디서 뗄지 3안(최대 인구·같은 계열·균등) + 결과 인구표. 고르는 것은 사람이다. 반올림 잔차는 가장 많이 떼는 줄이 흡수해 V5 를 지킨다
JsonSurgeon서식 보존 JSON 편집. Utf8JsonReader 로 토큰 오프셋을 찾아 그 범위만 치환한다 — 무변경 편집은 바이트 동일
DerivedArtifacts위의 신선도 잠금
ImpactAnalyzer변경 집합 → 무효화 범위 · 프리픽스 변경 · 구조 해시 변경(게임서버 재배포) · 재생성 목록. PlanStoreValidator 와 같은 판정이어야 한다(테스트가 강제)

콘텐츠 해시와 플랜 스토어 무효화

MasterDataSet.ContentHash 가 바뀌면 → 프리베이크된 플랜 스토어 전량 무효
단, 변경된 파일이 pois.json 뿐이고 POI가 추가만 되었다면 → 부분 무효화 허용

마스터데이터를 조금 고칠 때마다 프리베이크를 통째로 다시 도는 것을 막아준다. 프롬프트 프리픽스를 건드리면 해시가 바뀌고 플랜 스토어가 전량 무효가 된다 — 의도한 것인지 반드시 확인한다.

12

작성 순서

마스터데이터는 의존 순서대로 만들어야 한다. 역순으로 만들면 계속 되돌아온다.

1. world_flags.json      ← 모든 것의 기반. 여기서 실수하면 전부 다시
2. items.json            ← grants 가 flags 를 참조
3. actions.json          ← requires/grants 가 flags 를, params 가 items 를 참조
4. zones.json → pois.json → poi_distances.bin
5. archetypes.json       ← allowed_actions 가 actions 를, poi_type 이 pois 를 참조
6. context_buckets.json  ← archetypes 수에 의존 (2,880 계산)
7. interrupts.json
8. fallback_plans.json   ← 사람이 40개 작성. 가장 오래 걸린다
9. prompt/               ← actions.json 에서 자동 생성
10. npc_instances.json   ← 스크립트 생성
8번이 사람 손이 가장 많이 가는 부분이다

폴백 플랜 40개 수작성은 동시에 오써링 자동화의 비교 기준선이 된다 — 사람이 40개 만드는 데 걸린 시간 대 LLM이 2,880개 만드는 데 걸린 시간이 이 프로젝트의 핵심 수치다. 실측치는 실측 데이터에 있다.
