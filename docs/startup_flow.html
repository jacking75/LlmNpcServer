기동부터 종료까지 — 코드가 실제로 하는 일

Npc.Host.exe 를 실행한 순간부터 마지막 DisposeAsync 까지, 어떤 코드가 어떤 순서로 돌고 · 그때 어떤 객체가 만들어지고 · 서버가 어떤 상태가 되고 · 무엇을 고를 수 있는지를 따라간다. 모든 코드 인용은 저장소의 실제 파일이고, 로그·수치는 이 문서를 쓰면서 실제로 돌린 결과다.

조립 루트 = Program.cs 한 파일 .NET 10 · C# 틱 10Hz · 예산 20ms 기동 22단계 실행 축 3개 (스레드) 문서 기준일 2026-07-27

한 문장 요약 — 기동은 전부 한 번에 만들어 두는 과정이고, 실행은 아무것도 새로 만들지 않는 과정이다. 틱 루프에서 new 가 나오면 그게 버그다.

처음이면 1 한눈에 → 4 조립 22단계(애니메이션) → 10 틱 한 번 순으로. 옵션만 알고 싶으면 3 무엇을 고를 수 있나 로 바로 가도 된다.

02P0 — 프로세스 진입

Program.cs 는 최상위 문(top-level statements)이다. 클래스도 Main 도 없이 파일 첫 줄부터 곧바로 실행된다. 처음 60줄이 하는 일은 네 가지뿐이다 — 서브커맨드 분기 · 인자 파싱 · 경로 해석 · Ctrl-C 훅.

왜 경로를 미리 푸나. dotnet run --project src/Npc.Host 는 작업 폴더를 프로젝트 폴더로 잡는다. README 대로 ./masterdata 라고 쳤을 때 죽지 않으려면 저장소 루트를 위로 찾아 올라가야 하는데, 그 규칙을 --masterdata 에만 적용하고 --scenario·--trace 에는 적용하지 않은 비대칭이 실제 버그였다.

04P1 — 조립 22단계

NpcHost.Create(options, Console.Out) 한 번에 서버 한 벌이 전부 만들어진다. DI 컨테이너를 쓰지 않는다 — 생성 순서 자체가 사양이기 때문이다. 아래에서 재생을 누르면 22단계를 순서대로 따라가며, 각 단계에서 실행되는 코드 · 그때 만들어지는 객체 · 그 직후 서버 상태를 보여준다.

06링크 선택 — 4갈래

IGameServerLink 는 게임서버로 향하는 NPC 서버의 아웃바운드 포트다. 이름의 "GameServer" 는 상대방을 가리킨다. 구현체 교체는 Program.cs 의 switch 한 곳에서만 일어나고, 그 아래 어느 코드도 구현체를 이름으로 알지 못한다.

src/Npc.Host/Program.cs · 307–332행
switch (options.Link)
{
    case LinkKind.Null:
        nullLink = new NullGameServerLink();
        link = nullLink;
        break;

    case LinkKind.Replay:
        link = ReplayGameServerLink.Load(options.TracePath!);
        break;

    case LinkKind.Record:
    {
        driver = SimDriver.Create(options, data, chosen);
        string path = options.TracePath ?? Path.Combine("artifacts", "link.jsonl");
        link = new RecordingGameServerLink(driver.Link, path);
        break;
    }

    case LinkKind.Loopback:
    default:
        driver = SimDriver.Create(options, data, chosen);
        link = driver.Link;
        break;
}
driver 가 null 인지가 실행 국면을 바꾼다. PumpAsync 는 드라이버가 있으면 _driver.Tick(now) 로 세계를 밀고, Null 이면 TickSync 만 흘리고, Replay 면 아무것도 하지 않는다 — 파일이 이미 이벤트를 다 갖고 있기 때문이다.

loopback 기본

SimDriver 한 벌이 통째로 만들어진다 — SimWorld · MovementSim · InteractionSim · FaultInjector · TransformEmitter · NeedsSim · PlayerBots · ScenarioRunner · CommandRing · LoopbackGameServerLink.

NPC 는 여기서 스폰된다 — 대역이 기동 시 NpcCommandKind.Spawn 을 직접 ApplyCommand 로 밀어 넣는다. 실제 게임서버라면 접속·로딩이 하는 일이다.

null 링크 없이 뜨는지 확인

명령을 아무 데도 보내지 않는다. 대역이 없으므로 킬스위치도 결선되지 않는다 — 끊을 시나리오 자체가 없다.

펌프는 _nullLink.PushTick(now) 만 한다. 시계는 진행하되 세계는 없다.

record loopback + 기록

RecordingGameServerLink 가 loopback 을 감싼다. 명령과 이벤트를 jsonl 로 흘려 --trace 경로에 쓴다 (기본 artifacts/link.jsonl).

기록 경로는 저장소 루트 기준으로 고정한다 — 작업 폴더 기준이면 같은 명령이 실행 방식에 따라 다른 곳에 쓴다.

replay 결정론 검증

기록된 jsonl 을 다시 먹인다. 게임서버도 대역도 없다. LLM 없이 같은 이벤트 열을 재생해 상태 해시가 일치하는지 본다 — W11 게이트가 이 경로다.

--trace 가 필수다. 없으면 TryParse 가 거절한다.

라우터의 선택 규칙

TieredPlanCompiler.SelectTier 는 딱 두 가지만 본다 — PlanQuality 와 T1 큐 깊이. 예산은 보지 않는다(강등은 Acquire 의 몫이고, 끊긴 티어는 Downgrade 가 한 칸 내린다).

src/Npc.Llm/TieredPlanCompiler.cs · 144–156행
private Tier Wanted(in PlanRequest request)
{
    // 아키타입 플랜은 수천 NPC 가 재사용한다 → 품질에 투자한다.
    if (request.Quality == PlanQuality.Archetype)
    {
        return Tier.T2;
    }

    // 개별 재계획은 1회용이라 LOD 와 무관하게 T1 이다.
    // 단, T1 이 밀려 있으면 T2 로 흘린다.
    return LocalQueueDepth is { } depth && depth() > SpilloverThreshold ? Tier.T2 : Tier.T1;
}
임계 64 의 근거. T1 지연이 실측 5.1s 이므로 큐에 64건이 밀려 있으면 마지막 건은 5분 뒤에 처리된다. 그 시점에는 스냅샷 낡음 판정이 거의 확실히 폐기한다 — 즉 임계를 넘긴 뒤의 T1 요청은 대부분 헛일이라 T2 로 흘린다. 이 스필오버가 T2 호출의 상당 부분이면 T1 워커가 모자란 것이다.

09P3 — 실행: 세 개의 축

host.RunAsync(ct) 안에서 세 종류의 실행 흐름이 동시에 돈다. 이 셋의 관계가 이 서버에서 가장 중요한 구조다 — 하나라도 경계를 넘으면 결정론이 깨지거나 틱 예산이 무너진다.

src/Npc.Host/Program.cs · 381–404행 — NpcHost.RunAsync
public async Task RunAsync(CancellationToken ct)
{
    using var workers = CancellationTokenSource.CreateLinkedTokenSource(ct);

    await _tiers.StartAsync(workers.Token);          // ③ 재계획 워커 풀 기동

    Task pump = Task.Run(() => PumpAsync(ct));         // ① 게임서버 대역 펌프
    Task loop = _loop.RunAsync(ct);                    // ② 틱 루프

    try
    {
        await Task.WhenAll(pump, loop);
    }
    catch (OperationCanceledException) { // Ctrl-C. 정상 종료다. }
    finally
    {
        // 틱 루프가 멈춘 뒤 워커를 세운다 — 순서가 반대면 마지막 스왑이 유실된다.
        await workers.CancelAsync();
        await _tiers.StopAsync();
    }
}

① 펌프 — 세계를 한 틱씩 민다

펌프는 틱 루프보다 앞서 나가면 안 된다. 앞서면 명령이 나오기도 전에 세계가 다음 틱으로 넘어가 응답 이벤트가 하나도 돌아오지 않는다 — 전부 타임아웃 합성이 된다.

src/Npc.Host/Program.cs · 610–655행 — PumpAsync
while (!ct.IsCancellationRequested && (_totalTicks == 0 || tick < _totalTicks))
{
    tick++;
    var now = new Tick(tick);

    // 기다리는 것을 "세계를 밀기 전"으로 옮겼다. 밀고 나서 기다리면 tick N+1 의
    // 이벤트가 이미 채널에 들어간 뒤라, 틱 루프가 N 을 돌리는 동안 N+1 이 섞여 들어온다.
    var spin = new SpinWait();

    while (tick - _loop.TicksCommitted > MaxLeadTicks && !ct.IsCancellationRequested)
    {
        // sleep1Threshold: -1 — Thread.Sleep(1) 로 넘어가지 않게 한다.
        // 여기서 1ms 를 자면 1,440틱짜리 하루가 1분 39초 → 9분 8초가 된다.
        spin.SpinOnce(sleep1Threshold: -1);
    }

    if (_driver is not null) { _driver.Tick(now); }
    else                     { _nullLink!.PushTick(now); }

    if (_options.MaxSpeed) { continue; }   // 측정용 — 페이싱 없이

    long due  = tick * 1_000 / NpcServerLoop.TickHz;
    long wait = due - stopwatch.ElapsedMilliseconds;

    if (wait > 0) { await Task.Delay((int)wait, ct); }
}
기준이 TicksProcessed 가 아니라 TicksCommitted 인 이유. RunTick 이 끝나면 TicksProcessed 는 오르지만 그 시점에 이번 틱의 명령은 아직 링크 큐 안에 있다. 그 숫자만 보고 세계를 밀면 어떤 명령이 반영되는지가 스레드 스케줄에 달린다 — 같은 시나리오를 두 번 돌려도 이벤트 수가 달라진다 (실측 30,416 vs 30,649). TicksCommitted 는 FlushAsync 뒤에 오르므로 그 창이 닫힌다.
벽시계는 호스트 쪽에만 있다. Stopwatch 가 여기 있어도 되는 이유는 게임 로직이 여전히 Tick 만 보기 때문이다.

② 틱 루프 — 이 서버의 심장

③ 재계획 워커 — 루프 밖, 다른 스레드

ReplanWorker 는 BackgroundService 다. LLM 호출은 전부 여기서만 일어나고, 결과는 Volatile.Write 로만 건넨다. 워커가 런타임 상태를 직접 고치면 데이터 레이스와 비결정성이 생긴다.

이 클래스가 Npc.Planning 이 아니라 Npc.Host 에 있는 이유. 워커는 IPlanCompiler(Npc.Llm)와 NpcStore(Npc.Runtime)를 둘 다 필요로 한다. Npc.Planning 에 두면 Npc.Runtime → Npc.Planning → Npc.Llm 경로가 생겨 "틱 루프에 LLM 이 들어올 길" 이 열린다. 조립 루트가 유일하게 전부를 아는 곳이다.

src/Npc.Runtime/PlanExecutor.cs · 348–370행 — SynthesizeTimeout
private bool SynthesizeTimeout(int npc, Tick tick)
{
    CompiledPlan plan = PlanOf(npc);
    if (plan.Steps.IsEmpty) { return false; }

    int index = Math.Min(_store.StepIndex[npc], plan.Steps.Length - 1);
    long budget = TimeoutTicks(plan.Steps[index].TimeoutSeconds);

    if (tick.Value - _store.StepIssuedTick[npc] < budget) { return false; }

    _correlations.Invalidate(npc);                    // 늦게 온 응답은 무시된다
    _store.StepStatus[npc]    = (byte)StepStatus.Failed;
    _store.LastFailReason[npc] = (byte)ActionFailReason.Timeout;
    TimeoutsSynthesized++;
    return true;
}
실측 스모크에서 1,440틱 동안 타임아웃 합성 16,538건이 났다. --drop-rate 0 인데도 나는 이유는 timeout_s 가 게임 초라 --time-scale 600 에서는 매우 짧은 틱 수로 환산되기 때문이다 (ticks = timeout_s × 10 ÷ TimeScale, 최소 1). 배속이 곧 타임아웃 압력이다.

틱 루프는 큐에 넣기만 한다. 꺼내서 LLM 을 부르고 결과를 되돌려 놓는 것은 전부 워커 스레드의 일이다. 둘 사이의 접점은 딱 두 곳 — ReplanQueue 와 NpcStore.PendingPlanId.

13P4 — 종료와 정리

종료는 역순이다. 그리고 순서가 틀리면 조용히 데이터를 잃는다.

  1. 정지 신호 — Ctrl-C 가 lifetime.Cancel() 을 부르거나, --days 만큼 돌아 StopAtTick 에 닿으면 틱 루프가 return 한다. 펌프도 같은 조건에서 루프를 빠져나온다.
  2. 채널 닫기 — 펌프가 _driver.CompleteAsync()(또는 _nullLink.DisposeAsync()) 로 이벤트 스트림을 닫는다. 이걸 해야 틱 루프의 WaitToReadAsync 가 풀린다.
  3. 워커 정지 — finally 에서 workers.CancelAsync() → _tiers.StopAsync(). 틱 루프가 멈춘 뒤에 세운다 — 순서가 반대면 마지막 스왑이 유실된다.
  4. 종료 리포트 — host.Report(Console.Out) 가 두 줄을 찍는다. 게이트 러너가 이 숫자를 본다.
  5. 웹 호스트 정지 — await app.StopAsync(CancellationToken.None).
  6. 자원 해제 — await using 이 NpcHost.DisposeAsync() 를 부른다: meter.Dispose → tiers.DisposeAsync → link.DisposeAsync → driver.DisposeAsync.
  7. return 0
