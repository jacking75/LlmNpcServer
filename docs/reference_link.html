게임서버 연동 계약

NPC 서버가 게임서버와 주고받는 경계의 전체 정의다. 패킷 구조, 여덟 개의 절대 규칙, 소켓 위의 표현, 그리고 게임서버 쪽이 지켜야 할 발행 규약을 담는다. 게임서버 팀에 그대로 건넬 수 있는 문서로 쓴다.

연동 레퍼런스 N1~N8MemoryPack TCPfire-and-forget
방향명령은 NPC 서버가 낸다. 게임서버는 사실만 통보한다.
결합패킷에 문자열·시각·참조가 없다. 전부 강타입 ID와 Tick이다.
고정WireCommand 56B · WireEvent 64B (v1) · V2 72B/80B. 크기를 테스트가 못 박는다.
01

관점 — 누가 무엇을 만드는가

이 프로젝트가 만드는 것은 NPC 서버다. 게임서버는 만들지 않는다. 다만 NPC 서버를 혼자 돌려볼 수 없으므로 게임서버 역할을 하는 대역(Npc.Sim, Npc.TestGameServer)을 함께 둔다.

이름에 속지 않는다

IGameServerLink는 "게임서버의 인터페이스"가 아니라 "게임서버로 향하는 NPC 서버의 링크"다. 이름의 "GameServer"는 상대방을 가리킨다. 헥사고날 아키텍처의 아웃바운드 포트에 해당한다.

용어뜻방향
NpcCommandNPC 서버가 발행하는 명령. "이 NPC를 저기로 보내라"NPC 서버 → 게임서버
GameEventNPC 서버가 수신하는 통보. "그 NPC가 도착했다"게임서버 → NPC 서버
IGameServerLink위 둘이 오가는 NPC 서버 쪽 포트—

판단은 NPC 서버가 한다. GameEventKind 17개가 전부 과거형 사실이고 명령형이 하나도 없는 것은 우연이 아니다. 게임서버는 "적대 플레이어가 12m 앞에 있다"를 올려보내고, 공격할지 도망칠지 무시할지는 NPC 서버가 아키타입 특성과 인터럽트 규칙으로 정한다.

02

N1~N8 — 여덟 개의 절대 규칙

인터페이스만 만들고 나중에 네트워크를 붙이는 계획의 실패 원인은 거의 항상 같다. 인프로세스라서 공짜였던 가정이 네트워크에서 깨진다. 아래 여덟은 그 가정을 미리 제거한다. 전부 컴파일 타임 또는 테스트로 강제되며, 어기면 빌드가 아니라 테스트가 깨진다.

#규칙이유강제 방법
N1명령은 fire-and-forget. 결과는 반드시 이벤트로 돌아온다. RPC 왕복(await SendAndWait)을 만들지 않는다네트워크 RTT가 틱 루프를 블록하면 그 순간 끝이다IGameServerLink에 반환값 있는 메서드를 두지 않는다
N2모든 패킷은 순수 값 타입. 참조 공유·가변 컬렉션·object 금지참조를 공유하면 네트워크 전환 시 전부 재작성readonly record struct. Contracts_AllValueTypes
N3문자열 금지. 전부 ID.직렬화 비용 + 프롬프트 인젝션 방어Contracts_NoStringFields
N4시간은 Tick(long)만. DateTime·TimeSpan·Stopwatch 금지서버 간 시계는 다르다. 결정론 리플레이도 깨진다Contracts_NoDateTimeFields
N5모든 명령에 CorrelationId. 이벤트는 이걸로 명령과 매칭된다네트워크는 재정렬·지연된다. 순서 가정 금지NpcCommand 헤더에 필수
N6이벤트에 Sequence. 수신 측이 유실·중복을 검출한다유실을 조용히 넘기면 NPC가 영원히 멈춘다갭 검출 시 EventGapsDetected 증가 + 경보
N7이벤트 처리는 멱등. 같은 이벤트를 두 번 받아도 상태가 같아야 한다재전송은 반드시 생긴다Link_Idempotent — 2회 주입 후 상태 해시 동일
N8배치가 기본. 단건 전송은 배치 크기 1의 특수 케이스5,000 NPC × 초당 명령을 단건으로 보내면 죽는다API에 Enqueue + FlushAsync만 노출

덧붙는 두 가지

  • 명령 유실 허용 설계 — 명령이 유실돼도 NPC가 영구히 멈추면 안 된다. 모든 플랜 스텝에 timeout_s가 있고, 타임아웃 시 ActionFailed(Timeout)을 로컬에서 합성해 진행을 재개한다. 이 경로는 --drop-rate로 상시 테스트한다.
  • 역압 명시 — 명령 링이 차면 자기보다 낮은 우선순위(Cosmetic → Normal)부터 밀어낸다. Critical은 무손실이다. 드롭은 예외를 던지지 않고 LinkStats.CommandsDropped에만 나타난다.

인터페이스와 구현체

// Npc.Contracts/IGameServerLink.cs
public interface IGameServerLink : IAsyncDisposable
{

    ChannelReader<GameEvent> Events { get; }

스레드 모델 — 틱 루프는 소켓을 만지지 않는다

 [틱 루프]                          [센더 태스크]              [리시버 태스크]
  Enqueue ──► PriorityCommandRing        │                          │
  Flush   ──► BatchQueue 게시 ──────────►│ → WireCommand[]          │
              (할당 0)                   │ → MemoryPack → 소켓       │
                                                                    │ PipeReader → 프레임
  link.Events.TryRead ◄─────────────────────────────────────────────┘ → GameEvent → 채널

커널 송신 버퍼가 차기를 틱 루프에서 기다리면 그 순간 틱이 밀린다. FlushAsync가 하는 일은 링을 배치 슬롯으로 옮기고 꼬리를 올리는 것뿐이고, 그 경로에 할당이 없다 — TcpLink_FlushDoesNotAllocate가 워밍업 후 10,000회 할당 델타 0을 단언한다.

링을 스레드 너머로 넘기지 않는다

PriorityCommandRing은 삽입과 꺼냄이 같은 카운터를 만져 SPSC로 안전하지 않다. 스레드 경계는 생산자/소비자 첨자가 갈린 BatchQueue다.

런타임 배선 — 틱 루프 안의 유일한 await

while (await _link.Events.WaitToReadAsync(ct))
{
    // 1) 수신 이벤트 전부 배수 → 월드 뷰 갱신 (멱등, N7)
    while (_link.Events.TryRead(out var ev))
        _applier.Apply(in ev);          // WorldFlags·위치·LOD 등급 갱신
                                        // 인터럽트 이벤트는 여기서 즉시 큐 삽입
    // 2) 틱 진행 (TickSync 수신 시에만)
    if (_applier.TickAdvanced(out Tick tick))
    {
        _cognition.Scan(tick);          // 인지 LOD 슬라이스 스캔 → 재계획 큐
        _executor.Step(tick, _link);    // 플랜 스텝 실행 → _link.Enqueue()
        await _link.FlushAsync(ct);     // 배치 송출 (N8)
    }
}

이 루프 안에 await 대상이 FlushAsync 하나뿐이다. LLM 호출은 이 루프에 존재하지 않는다 — 별도 BackgroundService가 재계획 큐를 소비하고 완성된 플랜을 원자적으로 스왑한다.

ID 번호는 마스터데이터가 소유한다

PoiId·ItemId·ArchetypeId의 실제 번호는 masterdata/가 단일 원천이다. 양쪽 프로세스가 같은 마스터데이터를 보고 있는지는 핸드셰이크에서 해시로 검증한다 (§09).

NpcId 는 전역 인스턴스 id 다 A-08

npc_instances.json 의 id(1..N)이고, 런타임 슬롯 첨자가 아니다. 슬롯은 NPC 서버 안쪽 사정이라 게임서버가 알 이유가 없다 — 존을 나눠 두 NPC 서버를 띄우면 양쪽의 슬롯 7번은 서로 다른 NPC 이고, 그 상태로 명령이 오가면 대장장이에게 밭을 갈라고 명령하게 된다. 변환은 양쪽 경계에서 배열 첨자 한 번이라 할당 0 이다(Npc.Core/GlobalIdMap.cs). 게임서버는 Features 의 GlobalIds 비트로 이것을 확인한다.

08

와이어 프로토콜

Npc.Wire가 링크의 전송 표현이다. Npc.Contracts에 NuGet 의존을 만들지 않으려고 와이어 DTO를 따로 두고 1:1 매핑한다 — [MemoryPackable]을 NpcCommand에 붙이는 순간 계약 프로젝트가 직렬화기 버전에 묶인다.

프레임 — 헤더 8바이트 고정

 0      1      2      3      4      5      6      7      8 ...
+------+------+------+------+------+------+------+------+---------------+
|      PayloadLength (u32)   | Kind | Ver  |   Reserved  |    Payload    |
+------+------+------+------+------+------+------+------+---------------+
        little-endian          u8     u8      u16 = 0     MemoryPack
  • PayloadLength는 헤더를 뺀 바이트 수다.
  • Ver ∈ [1, 2] (B-01). 범위 밖이면 즉시 Bye(ProtocolViolation) 후 끊는다. 핸드셰이크 전에는 1로 쓰고, 협상이 끝나면 그 결과가 이후 모든 프레임의 Ver다. 예전에는 단일 값 비교라 v2 프레임을 아예 읽을 수 없었고, 그래서 "버전이 다르다"를 협상으로 풀 방법이 없었다.
  • PayloadLength > 1,048,576(1MiB)이면 연결을 끊는다. 길이 접두 프로토콜에서 이 검사를 빼면 잘못된 4바이트 하나로 프로세스가 죽는다.
  • 헤더는 손으로 쓴다. MemoryPack 안에 길이를 또 넣지 않는다 — 진실의 출처를 둘로 만들지 않는다.

배치 페이로드는 unmanaged 배열이다. MemoryPack은 unmanaged 원소 배열을 원시 메모리로 복사하므로 원소마다 태그가 붙지 않는다 — 크기도 작고 할당도 없다.

크기를 테스트로 못 박는다

Wire_LayoutIsFrozen이 sizeof(WireCommand) == 56, sizeof(WireEvent) == 64를 단언한다. 누가 필드를 끼워 넣으면 이 테스트가 먼저 깨진다. Wire_MirrorsContractMembers는 리플렉션으로 계약 타입과 DTO의 멤버 집합이 1:1인지 본다 — 계약에 필드를 추가하고 와이어를 잊으면 여기서 걸린다.

v2 DTO — 확장 슬롯 (B-02)

v1 DTO 두 개는 동결이다. 확장은 새 타입으로만 한다 — v1 게임서버가 그 배치를 그대로 읽고 있기 때문이다. WireCommandV2·WireEventV2는 Npc.Wire.V2에 있고, 게임서버가 LinkFeatures.ExtSlots를 켜고 프로토콜 2로 협상했을 때만 쓰인다. 켜지 않으면 v1으로 나가고 확장 필드는 조용히 버려진다 — 이해하지 못하는 값을 실어 보내는 것보다 버리는 편이 정직하다.

InstanceInstanceId(ushort)채널·인스턴스 던전·레이어. 0 = 기본 월드. 게임서버가 NpcSpawned로 알려주고 NPC 서버는 그 NPC로 나가는 모든 명령에 그대로 찍는다 — 값을 해석하지 않는다

왜 Reserved를 필드로 두는가

MemoryPack은 unmanaged struct를 원시 복사한다. 암묵 패딩이 남아 있으면 초기화되지 않은 바이트가 그대로 소켓에 나가고, 회차마다 값이 달라져 골든 바이트 벡터(B-03)가 성립하지 않는다. 다른 언어 구현이 그 바이트를 해석하려 들 수도 있다. Wire_HasNoImplicitPadding_V2가 필드 크기 합 == sizeof를 단언한다.

72바이트다 — 로드맵 초안의 64가 아니다

v1 명령이 56B(패딩 0)이고 Instance(2)+Faction(2)+ExtA(4)+ExtB(4) = 68B, 정렬 8이라 72B다. 64에 넣으려면 예약 슬롯 하나를 버려야 하고, 그러면 "예약 슬롯 2개"라는 설계 자체가 없어진다. 이벤트는 초안대로 80B다.

프레임 버전으로 배치를 고른다. 수신 측은 협상 결과가 아니라 프레임 헤더의 Ver를 보고 v1/v2 배치를 고른다. 협상 직후의 경계에서 두 버전이 섞여 도착할 수 있고, 그때 협상값으로 읽으면 배치가 어긋나 스트림 전체가 쓰레기가 된다.

v2 배치는 명시 직렬화다

Npc.Wire/V2/WireWriter.cs 가 필드마다 BinaryPrimitives 로 리틀엔디언을 쓴다. 바이트는 원시 복사와 같지만(테스트가 못 박는다) 명세가 배치가 아니라 오프셋 표가 된다. 배치 페이로드는 int32 접두 + 고정 크기 원소이고, 접두가 음수면 null 배열이라 빈 배치(0)와 다르다.

해시 분할 (B-04)

마스터데이터가 한 글자만 달라도 링크가 안 붙던 것을 고쳤다. 상용에서는 게임서버·NPC 서버·클라이언트가 다른 파이프라인으로 배포되고 핫픽스로 한쪽만 갱신되는 일이 잦은데, 그때마다 NPC 전체가 멈추는 것(성능 저하가 아니라 링크 거절)은 과잉이다.

해시재료불일치 시
구조 StructuralHash액션·아이템·아키타입·존·POI 의 id ↔ code · 월드 플래그의 id ↔ bit · POI 의 소속 존과 좌표 · 버킷 공간의 차원거절. 두 프로세스가 같은 번호로 다른 것을 가리키는 상태다
내용 ContentHash파일 전체 (구조 포함). 실질적으로 desc·traits·allowed_actions·인터럽트·폴백·레시피·open_hours·정원이 여기서만 움직인다경고 후 수락. 양쪽 해시를 HelloAck·로그·/status 에 남긴다
code·bit 재배치 금지는 그대로다

번호를 바꾸면 구조 해시가 바뀌고 링크가 거절된다. 그것이 이 분할이 지키는 것이다 — 느슨해진 것은 "설명을 고쳤다" 뿐이고, 위험한 변경은 여전히 연결 시점에 죽는다.

구조 해시는 파일 바이트가 아니라 로드된 표에서 계산한다

같은 파일 안에서 구조와 내용을 가르는 방법은 그것뿐이다. 덕분에 들여쓰기·키 순서를 바꿔도 구조 해시는 그대로다.

샤드 정의는 deploy/shards.json 이다. 마스터데이터가 아니다 — 배포 토폴로지이지 콘텐츠가 아니라 content_hash 에 들어가지 않는다. 대신 ZoneMask 가 핸드셰이크에 실려 어긋나면 그 자리에서 거절된다. 겹침·모르는 존·code 63 초과·샤드 번호 중복은 로드 실패다 (V15).

1단계에서 NPC 는 자기 샤드의 존 안에서만 산다. $nearest_market 같은 심볼 바인딩이 샤드 밖 POI 를 고르지 않도록 후보를 마스크로 거른다 — 안 거르면 그 NPC 는 우리가 이벤트를 받지 못하는 곳으로 걸어가 timeout_s 가 만료될 때까지 멈춘다.

2단계(존 간 핸드오프)는 미구현이다

NPC 가 샤드 경계를 넘어 이동하려면 소유권 이관(NpcHandoff)과 상태 직렬화가 필요하다. 지금은 존 그래프가 샤드 안에서 연결돼 있다고 가정한다.

상호 인증 (A-06)

예전 핸드셰이크가 검증하는 것은 "같은 데이터를 보고 있는가"였지 "네가 누구인가"가 아니었다. 링크 포트에 붙기만 하면 누구나 NPC 명령 스트림을 관측하고 이벤트를 위조할 수 있었다.

단계누가무엇
1게임서버Nonce(16B, OS 난수) 생성 → Hello.Auth = HMAC-SHA256(secret, 협상 필드 ‖ 해시 3종 ‖ Nonce)
2NPC 서버같은 비밀로 검산. nonce 재사용도 거절(세션당 256개 기억) — 태그는 "그때 이 비밀을 아는 누군가가 만들었다"만 증명하지 "지금 만들었다"를 증명하지 않는다
3NPC 서버HelloAck.Auth = HMAC(secret, ack 필드 ‖ 같은 Nonce)
4게임서버검산. 한쪽만 검증하면 "우리에게 붙는 가짜 게임서버"는 막아도 "가짜 NPC 서버가 게임서버에 붙는 것"은 못 막는다
비밀은 환경변수로만 온다

NPC_LINK_SECRET(hex 64자 = 32바이트). 인자에도 파일에도 두지 않는다 — 인자는 ps에 보이고 파일은 이미지에 굽힌다. 태그 비교는 고정 시간이다(FixedTimeEquals): 앞에서부터 비교하면 타이밍으로 한 바이트씩 알아낼 수 있다.

거절에는 태그를 싣지 않는다

상대의 신원을 모르는데 우리 비밀로 서명하면 그것이 곧 오라클이 된다.

암호화 (A-06)

--link-tls off|tls|mtls. SslStream은 TcpGameServerLink 본문을 건드리지 않고 연결 생성기 이음매에 끼운다 — 재접속 백오프·핸드셰이크·프레임 코덱은 스트림이 무엇인지 모른 채 그대로 돈다. TLS 1.2/1.3만 켠다.

동적 로스터 — 런타임 스폰·디스폰 (B-05)

로스터 해시가 완전 일치라 이벤트성 NPC·인스턴스 던전 NPC 를 런타임에 넣고 뺄 수 없었다. LinkFeatures.DynamicRoster 를 양쪽이 같이 켜면 그것이 열린다.

항목규약
로스터 해시"초기 활성 집합" 이 아니라 "누가 존재할 수 있는가" — npc_instances.json 전체의 해시다. 활성 집합은 핸드셰이크 뒤 NpcSpawned 재발행으로 동기화된다
켜는 방법NPC 서버 --dynamic-roster · 게임서버도 같은 스위치. 한쪽만 켜면 해시가 어긋나 RosterMismatch 로 거절된다 — 기능 협상은 핸드셰이크 중에 끝나므로 해시를 협상 결과로 고를 수 없다. 어긋난 채 붙는 것보다 거절이 싸다
슬롯 배정 A-08 에서 뒤집혔다NPC 서버가 한다. NpcSpawned.Npc 는 전역 인스턴스 id 이고, 그것을 어느 배열 칸에 앉힐지는 NPC 서버 사정이다. B-05 는 Npc 가 슬롯 번호였기 때문에 ExtA 로 인스턴스 id 를 따로 실었는데, A-08 이후로는 같은 값을 두 번 싣는 것이 되어 그 등록을 지웠다. 게임서버가 NPC 서버의 첨자를 고르면 샤드마다 다른 첨자 공간을 게임서버가 관리해야 한다
용량NPC 서버가 --npc-capacity(기본 로스터 × 1.2)만큼 기동 시 슬롯을 잡는다. 틱 루프에서 배열을 늘릴 수 없다. 넘는 스폰은 무시하고 센다
디스폰슬롯을 비운다 — 인벤토리·플래그·플랜까지. 비우지 않으면 다음 거주자가 이전 거주자의 물건을 들고 시작한다
멱등 (N7)같은 스폰을 두 번 받으면 두 번째는 아무 일도 하지 않는다. 디스폰도 같다
모르는 NpcId스폰이면 빈 슬롯을 잡아 앉히고, 스폰이 아니면 버리고 센다(/status 의 unknownNpcEvents). 이동·완료 이벤트가 자리를 만들면 게임서버의 라우팅 실수가 조용히 정상으로 보인다
인스턴스 테이블에 없는 id 는 1단계에서 지원하지 않는다

게임서버가 즉석에서 만든 NPC 는 아키타입을 알 방법이 없어 시드할 수 없다 — 거절하고 센다. 2단계(템플릿 스폰)는 ExtB 에 아키타입 code 를 실어 허용하는 것이고, 그때 이 표에 줄이 하나 늘어난다.

미판정은 통과가 아니다

플레이어가 없었으면 근접을, 전투가 없었으면 전투를 볼 수 없다. 보고서는 그것을 미판정으로 적고 사유를 남긴다 — 합격 수에 넣지 않는다. 판정하려면 관찰을 늘리거나 시나리오를 주입한다.

실제 연동 시 남는 것

TCP 링크 구현은 NPC 서버 코드를 한 줄도 바꾸지 않고 끝났다 — 이것이 이 인터페이스 설계의 검증 기준이었다. 실제 게임서버에 붙일 때 추가로 필요한 것은 아래 셋뿐이며, 전부 Npc.Wire와 그 바깥에서 해결된다.

항목상태내용
이기종 엔디언·패딩구현됨 (v2)v2 배치는 필드별 리틀엔디언 쓰기다 (Npc.Wire/V2/WireWriter.cs, B-03) — 원시 복사를 전제하지 않는다. 오프셋 표는 docs/wire/layout_v2.md(생성물), 골든 바이트는 docs/wire/vectors_v2/, 참조 코덱은 docs/wire/reference/npc_wire.h(C++17)·npc_wire.py 다. v1 배치는 여전히 원시 복사이고 그것이 v1 의 의미다 — 다른 런타임과 붙을 때는 v2 로 협상한다

소켓 경로에서는 결정론이 성립하지 않는다

리플레이 100% 일치는 루프백 경로의 성질이다. 소켓에서는 명령이 몇 틱 늦게 도착할 수 있고 그것이 스텝 경계를 바꾼다. 결함이 아니라 사실이다 — 실제 게임서버에 붙으면 원래 그렇다. 재현이 필요하면 기록 링크로 이벤트 열을 남겨 재생 링크로 되민다. 그 경로는 결정론이다.
