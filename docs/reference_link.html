게임서버 연동 계약

NPC 서버가 게임서버와 주고받는 경계의 전체 정의다. 패킷 구조, 여덟 개의 절대 규칙, 소켓 위의 표현, 그리고 게임서버 쪽이 지켜야 할 발행 규약을 담는다. 게임서버 팀에 그대로 건넬 수 있는 문서로 쓴다.

연동 레퍼런스 N1~N8MemoryPack TCPfire-and-forget
방향명령은 NPC 서버가 낸다. 게임서버는 사실만 통보한다.
결합패킷에 문자열·시각·참조가 없다. 전부 강타입 ID와 Tick이다.
고정WireCommand 56B · WireEvent 64B. 크기를 테스트가 못 박는다.
01

관점 — 누가 무엇을 만드는가

이 프로젝트가 만드는 것은 NPC 서버다. 게임서버는 만들지 않는다. 다만 NPC 서버를 혼자 돌려볼 수 없으므로 게임서버 역할을 하는 대역(Npc.Sim, Npc.TestGameServer)을 함께 둔다.

        │   NPC 서버   ★ 이 저장소       │

        │  Npc.Llm     · Npc.Core       │
        └───────────┬───────────────────┘

        │   IGameServerLink   ★ 이 문서  │   ← NPC 서버의 아웃바운드 포트
        │   NpcCommand ▲ / GameEvent ▼   │      "게임서버로 나가는 문"

이름에 속지 않는다

IGameServerLink는 "게임서버의 인터페이스"가 아니라 "게임서버로 향하는 NPC 서버의 링크"다. 이름의 "GameServer"는 상대방을 가리킨다. 헥사고날 아키텍처의 아웃바운드 포트에 해당한다.

용어뜻방향
NpcCommandNPC 서버가 발행하는 명령. "이 NPC를 저기로 보내라"NPC 서버 → 게임서버
GameEventNPC 서버가 수신하는 통보. "그 NPC가 도착했다"게임서버 → NPC 서버
IGameServerLink위 둘이 오가는 NPC 서버 쪽 포트—

판단은 NPC 서버가 한다. GameEventKind 17개가 전부 과거형 사실이고 명령형이 하나도 없는 것은 우연이 아니다. 게임서버는 "적대 플레이어가 12m 앞에 있다"를 올려보내고, 공격할지 도망칠지 무시할지는 NPC 서버가 아키타입 특성과 인터럽트 규칙으로 정한다.

02

N1~N8 — 여덟 개의 절대 규칙

인터페이스만 만들고 나중에 네트워크를 붙이는 계획의 실패 원인은 거의 항상 같다. 인프로세스라서 공짜였던 가정이 네트워크에서 깨진다. 아래 여덟은 그 가정을 미리 제거한다. 전부 컴파일 타임 또는 테스트로 강제되며, 어기면 빌드가 아니라 테스트가 깨진다.

#규칙이유강제 방법
N1명령은 fire-and-forget. 결과는 반드시 이벤트로 돌아온다. RPC 왕복(await SendAndWait)을 만들지 않는다네트워크 RTT가 틱 루프를 블록하면 그 순간 끝이다IGameServerLink에 반환값 있는 메서드를 두지 않는다
N2모든 패킷은 순수 값 타입. 참조 공유·가변 컬렉션·object 금지참조를 공유하면 네트워크 전환 시 전부 재작성readonly record struct. Contracts_AllValueTypes
N3문자열 금지. 전부 ID.직렬화 비용 + 프롬프트 인젝션 방어Contracts_NoStringFields
N4시간은 Tick(long)만. DateTime·TimeSpan·Stopwatch 금지서버 간 시계는 다르다. 결정론 리플레이도 깨진다Contracts_NoDateTimeFields
N5모든 명령에 CorrelationId. 이벤트는 이걸로 명령과 매칭된다네트워크는 재정렬·지연된다. 순서 가정 금지NpcCommand 헤더에 필수
N6이벤트에 Sequence. 수신 측이 유실·중복을 검출한다유실을 조용히 넘기면 NPC가 영원히 멈춘다갭 검출 시 EventGapsDetected 증가 + 경보
N7이벤트 처리는 멱등. 같은 이벤트를 두 번 받아도 상태가 같아야 한다재전송은 반드시 생긴다Link_Idempotent — 2회 주입 후 상태 해시 동일
N8배치가 기본. 단건 전송은 배치 크기 1의 특수 케이스5,000 NPC × 초당 명령을 단건으로 보내면 죽는다API에 Enqueue + FlushAsync만 노출

덧붙는 두 가지

  • 명령 유실 허용 설계 — 명령이 유실돼도 NPC가 영구히 멈추면 안 된다. 모든 플랜 스텝에 timeout_s가 있고, 타임아웃 시 ActionFailed(Timeout)을 로컬에서 합성해 진행을 재개한다. 이 경로는 --drop-rate로 상시 테스트한다.
  • 역압 명시 — 명령 링이 차면 자기보다 낮은 우선순위(Cosmetic → Normal)부터 밀어낸다. Critical은 무손실이다. 드롭은 예외를 던지지 않고 LinkStats.CommandsDropped에만 나타난다.
03

인터페이스와 구현체

// Npc.Contracts/IGameServerLink.cs
public interface IGameServerLink : IAsyncDisposable
{
    // NPC 서버 → 게임서버. 배치 전송만 허용한다 (N8).
    // 반환값 없음 — 결과는 Events로만 돌아온다 (N1).
    void      Enqueue(in NpcCommand command);
    ValueTask FlushAsync(CancellationToken ct);

    // 게임서버 → NPC 서버.
    ChannelReader<GameEvent> Events { get; }

    LinkState State { get; }
    LinkStats Stats { get; }
    event Action<LinkState>? StateChanged;
}

public enum LinkState { Disconnected, Connecting, Connected, Degraded, Faulted }

public readonly record struct LinkStats(
    long CommandsEnqueued,
    long CommandsFlushed,
    long CommandsDropped,      // 역압 드롭 + 재접속 시 폐기
    long EventsReceived,
    long EventGapsDetected,    // N6 시퀀스 갭
    int  PendingCommands);
구현체용도
LoopbackGameServerLinkNpc.Sim 헤드리스 월드에 직결. 부하 측정과 결정론 리플레이의 주력
NullGameServerLink명령 폐기, 이벤트 없음. 단위 테스트·성능 기준선
RecordingGameServerLink데코레이터. 명령·이벤트를 jsonl로 기록
ReplayGameServerLink기록된 jsonl을 이벤트 소스로 재생
TcpGameServerLink실제 네트워크. 연결·핸드셰이크·송수신·재접속

스레드 모델 — 틱 루프는 소켓을 만지지 않는다

 [틱 루프]                          [센더 태스크]              [리시버 태스크]
  Enqueue ──► PriorityCommandRing        │                          │
  Flush   ──► BatchQueue 게시 ──────────►│ → WireCommand[]          │
              (할당 0)                   │ → MemoryPack → 소켓       │
                                                                    │ PipeReader → 프레임
  link.Events.TryRead ◄─────────────────────────────────────────────┘ → GameEvent → 채널

커널 송신 버퍼가 차기를 틱 루프에서 기다리면 그 순간 틱이 밀린다. FlushAsync가 하는 일은 링을 배치 슬롯으로 옮기고 꼬리를 올리는 것뿐이고, 그 경로에 할당이 없다 — TcpLink_FlushDoesNotAllocate가 워밍업 후 10,000회 할당 델타 0을 단언한다.

링을 스레드 너머로 넘기지 않는다

PriorityCommandRing은 삽입과 꺼냄이 같은 카운터를 만져 SPSC로 안전하지 않다. 스레드 경계는 생산자/소비자 첨자가 갈린 BatchQueue다.

런타임 배선 — 틱 루프 안의 유일한 await

while (await _link.Events.WaitToReadAsync(ct))
{
    // 1) 수신 이벤트 전부 배수 → 월드 뷰 갱신 (멱등, N7)
    while (_link.Events.TryRead(out var ev))
        _applier.Apply(in ev);          // WorldFlags·위치·LOD 등급 갱신
                                        // 인터럽트 이벤트는 여기서 즉시 큐 삽입
    // 2) 틱 진행 (TickSync 수신 시에만)
    if (_applier.TickAdvanced(out Tick tick))
    {
        _cognition.Scan(tick);          // 인지 LOD 슬라이스 스캔 → 재계획 큐
        _executor.Step(tick, _link);    // 플랜 스텝 실행 → _link.Enqueue()
        await _link.FlushAsync(ct);     // 배치 송출 (N8)
    }
}

이 루프 안에 await 대상이 FlushAsync 하나뿐이다. LLM 호출은 이 루프에 존재하지 않는다 — 별도 BackgroundService가 재계획 큐를 소비하고 완성된 플랜을 원자적으로 스왑한다.

NpcCommand — 나가는 명령

public enum NpcCommandKind : byte
{
    Spawn = 1, Despawn, MoveTo, Stop, FaceTo,
    PlayAnimation, SetVisualState, Interact, Speak,
    InventoryChange, CombatAction, SetAggro,
}

public readonly record struct NpcCommand
{
    // --- 헤더 (모든 명령 공통) ---
    public required NpcCommandKind  Kind        { get; init; }
    public required NpcId           Npc         { get; init; }
    public required Tick            IssuedAt    { get; init; }   // N4
    public required CorrelationId   Correlation { get; init; }   // N5
    public required CommandPriority Priority    { get; init; }   // 역압 시 드롭 순서

    // --- 페이로드 (Kind에 따라 사용 필드가 달라진다) ---
    public PoiId       TargetPoi    { get; init; }
    public WorldPos    TargetPos    { get; init; }
    public NpcId       TargetNpc    { get; init; }
    public PlayerId    TargetPlayer { get; init; }
    public ItemId      Item         { get; init; }
    public int         Amount       { get; init; }
    public AnimationId Animation    { get; init; }
    public DialogueId  Dialogue     { get; init; }
    public VisualState Visual       { get; init; }
    public ArchetypeId Archetype    { get; init; }
    public ZoneId      Zone         { get; init; }
    public byte        Flags        { get; init; }   // 이동속도 등급, Aggro on/off 등
}

public enum CommandPriority : byte { Critical = 0, Normal = 1, Cosmetic = 2 }
public enum VisualState : byte
{ Idle, Walking, Running, Working, Fighting, Sleeping, Sitting, Dead }

판별 공용체를 struct로 표현한다. 필드 유니온 대신 명시 필드를 쓴다 — 직렬화기가 단순해지고 디버깅이 쉽다.

NPC 서버는 플레이어 좌표를 저장하지 않는다. nearest:<archetype> 같은 참조도 대상을 여기서 고르지 않고 아키타입만 실어 보낸다 — 근접 판정은 게임서버 소관이다. 5,000 NPC × 플레이어 20이면 틱당 10만 회 거리 계산이고, 그것만으로 20ms 틱 예산이 날아간다.

GameEvent — 들어오는 통보

public enum GameEventKind : byte
{
    TickSync = 1, GameTimeChanged,
    NpcSpawned, NpcDespawned, NpcTransform,
    NpcArrived, NpcActionCompleted, NpcActionFailed,
    NpcVitalsChanged, NpcInventoryChanged,
    PlayerProximity, PlayerInteracted,
    CombatStarted, CombatEnded, DamageTaken,
    ZoneStateChanged, WeatherChanged,
}

public readonly record struct GameEvent
{
    public required GameEventKind Kind       { get; init; }
    public required long          Sequence   { get; init; }   // N6
    public required Tick          OccurredAt { get; init; }   // N4
    public NpcId         Npc         { get; init; }
    public CorrelationId Correlation { get; init; }           // N5 — 명령 응답일 때
    public WorldPos      Pos         { get; init; }
    public float         Heading     { get; init; }
    public PoiId         Poi         { get; init; }
    public ZoneId        Zone        { get; init; }
    public PlayerId      Player      { get; init; }
    public NpcId         OtherNpc    { get; init; }
    public ItemId        Item        { get; init; }
    public int           Amount      { get; init; }
    public short         Hp          { get; init; }
    public short         Stamina     { get; init; }
    public byte          Code        { get; init; }   // FailReason / RegionState
}                                                     // / Climate / TimeOfDay / Enter·Leave

public enum ActionFailReason : byte
{
    None = 0, Unreachable, Timeout, Interrupted, PreconditionFailed,
    TargetGone, InventoryFull, InsufficientResource, Dead, Rejected,
}

public enum ProximityChange : byte { Enter = 0, Leave = 1 }
번호를 재배치하지 않는다

GameEventKind와 ActionFailReason의 번호를 옮기면 기록된 리플레이 로그가 통째로 깨진다. 추가는 항상 뒤에만 한다.

인지 LOD — 거리가 등급이 되는 지점

PlayerProximity의 거리는 세 구간으로 압축되어 NpcStore.Lod[]에만 남는다. 이 등급이 매 틱 인지 스캔 슬라이스의 크기를 정한다.

08

와이어 프로토콜

Npc.Wire가 링크의 전송 표현이다. Npc.Contracts에 NuGet 의존을 만들지 않으려고 와이어 DTO를 따로 두고 1:1 매핑한다 — [MemoryPackable]을 NpcCommand에 붙이는 순간 계약 프로젝트가 직렬화기 버전에 묶인다.

프레임 — 헤더 8바이트 고정

 0      1      2      3      4      5      6      7      8 ...
+------+------+------+------+------+------+------+------+---------------+
|      PayloadLength (u32)   | Kind | Ver  |   Reserved  |    Payload    |
+------+------+------+------+------+------+------+------+---------------+
        little-endian          u8     u8      u16 = 0     MemoryPack
  • PayloadLength는 헤더를 뺀 바이트 수다.
  • Ver ∈ [1, 2] (B-01). 범위 밖이면 즉시 Bye(ProtocolViolation) 후 끊는다. 핸드셰이크 전에는 1로 쓰고, 협상이 끝나면 그 결과가 이후 모든 프레임의 Ver다. 예전에는 단일 값 비교라 v2 프레임을 아예 읽을 수 없었고, 그래서 "버전이 다르다"를 협상으로 풀 방법이 없었다.
  • PayloadLength > 1,048,576(1MiB)이면 연결을 끊는다. 길이 접두 프로토콜에서 이 검사를 빼면 잘못된 4바이트 하나로 프로세스가 죽는다.
  • 헤더는 손으로 쓴다. MemoryPack 안에 길이를 또 넣지 않는다 — 진실의 출처를 둘로 만들지 않는다.

메시지 6종

Kind이름방향페이로드
1HelloGS → NPCv1 WireHello · v2 WireHelloV2
2HelloAckNPC → GSv1 WireHelloAck · v2 WireHelloAckV2

배치 페이로드는 unmanaged 배열이다. MemoryPack은 unmanaged 원소 배열을 원시 메모리로 복사하므로 원소마다 태그가 붙지 않는다 — 크기도 작고 할당도 없다.

DTO — 크기가 고정이다

필드 순서는 큰 타입부터다. 패딩을 없애 크기를 고정한다.

[MemoryPackable] public partial struct WireCommand   // 56 bytes, unmanaged
{
    public long   IssuedAt;                // Tick
    public int    Npc, TargetNpc, TargetPlayer, Amount;
    public uint   Correlation;
    public float  PosX, PosY, PosZ;        // WorldPos
    public ushort TargetPoi, Item, Animation, Dialogue, Archetype, Zone;
    public byte   Kind, Priority, Visual, Flags;
}

[MemoryPackable] public partial struct WireEvent     // 64 bytes, unmanaged
{
    public long   Sequence, OccurredAt;
    public int    Npc, OtherNpc, Player, Amount;
    public uint   Correlation;
    public float  PosX, PosY, PosZ, Heading;
    public ushort Poi, Zone, Item;
    public short  Hp, Stamina;
    public byte   Kind, Code;
}
크기를 테스트로 못 박는다

Wire_LayoutIsFrozen이 sizeof(WireCommand) == 56, sizeof(WireEvent) == 64를 단언한다. 누가 필드를 끼워 넣으면 이 테스트가 먼저 깨진다. Wire_MirrorsContractMembers는 리플렉션으로 계약 타입과 DTO의 멤버 집합이 1:1인지 본다 — 계약에 필드를 추가하고 와이어를 잊으면 여기서 걸린다.

대역폭 어림. NPC 500, 관측 대상 256 상한 기준 이벤트는 최악 256 × 64B × 10Hz ≈ 164KB/s. 명령은 NPC당 스텝 경계에서만 나가므로 훨씬 적다.

마스터데이터가 다른 두 프로세스를 붙이면 POI 코드가 어긋나 NPC가 엉뚱한 곳으로 간다. 원인을 찾는 데 하루가 든다. 연결 시점에 죽이는 편이 싸다. --force 같은 우회 옵션을 만들지 않는다.

버전 협상 (B-01)

v1 은 ProtocolVersion이 다르면 협상 없이 절단이었다. 계약(의미)에는 버전 자체가 없어서, NpcCommandKind에 항목 하나를 뒤에 추가해도 알릴 방법이 없었고 알리려면 양쪽을 동시에 내려야 했다 — 라이브 서비스의 롤링 배포와 정면으로 충돌한다.

v2 는 범위를 보내고 NPC 서버가 고른다. 게임서버가 [MinProtocolVersion, ProtocolVersion]과 ContractMajor/Minor·Features를 보내면, NPC 서버가 자기 범위 [1, 2]와의 교집합에서 최댓값을 골라 HelloAck.ProtocolVersion으로 돌려준다. 최솟값을 고르면 양쪽이 새 버전을 지원해도 영원히 옛 버전으로 돌아 새 버전을 올릴 이유가 사라진다.

해시 분할 (B-04)

마스터데이터가 한 글자만 달라도 링크가 안 붙던 것을 고쳤다. 상용에서는 게임서버·NPC 서버·클라이언트가 다른 파이프라인으로 배포되고 핫픽스로 한쪽만 갱신되는 일이 잦은데, 그때마다 NPC 전체가 멈추는 것(성능 저하가 아니라 링크 거절)은 과잉이다.

해시재료불일치 시
구조 StructuralHash액션·아이템·아키타입·존·POI 의 id ↔ code · 월드 플래그의 id ↔ bit · POI 의 소속 존과 좌표 · 버킷 공간의 차원거절. 두 프로세스가 같은 번호로 다른 것을 가리키는 상태다

code·bit 재배치 금지는 그대로다

번호를 바꾸면 구조 해시가 바뀌고 링크가 거절된다. 그것이 이 분할이 지키는 것이다 — 느슨해진 것은 "설명을 고쳤다" 뿐이고, 위험한 변경은 여전히 연결 시점에 죽는다.

구조 해시는 파일 바이트가 아니라 로드된 표에서 계산한다

같은 파일 안에서 구조와 내용을 가르는 방법은 그것뿐이다. 덕분에 들여쓰기·키 순서를 바꿔도 구조 해시는 그대로다.

게임서버 발행 규약

패킷 정의만으로는 부족하다. 언제 무엇을 얼마나 자주 보내는가가 NPC 서버의 동작을 좌우한다. 아래는 레퍼런스 게임서버(Npc.TestGameServer)가 실제로 지키는 규약이며, 실제 게임서버를 붙일 때도 같은 것을 기대한다.

틱 순서

벽시계 기준 100ms 주기. 게임서버는 NPC 서버를 기다리지 않는다 — 락스텝이 없는 것이 이 설계의 전제다.

1. CommandInbox 배수 → 월드에 적용
2. 시나리오 주입 (jsonl)
3. PlayerRegistry — 입력 적용 → 이동 → 근접 변화
4. 이동 시뮬
5. 상호작용 시뮬
6. TransformEmitter
7. 니즈 시뮬
8. 월드 틱 (TickSync 발행)
9. 이벤트 채널 → EventBatch 프레임 1개로 Flush

플레이어 근접 — 가장 중요한 규약

항목규약왜
판정 주기5틱(0.5초)마다. 매 틱이 아니다매 틱 재면 NPC 수 × 플레이어 수를 10Hz로 돈다
후보 축소플레이어가 있는 존 + 인접 존의 NPC만 검사먼 존은 볼 이유가 없다
발행 단위NPC당 최대 1건. 그 NPC에게 가장 가까운 플레이어 하나만 싣는다쌍 단위로 보내면 O(NPC×플레이어)가 된다. NPC 서버가 필요한 것은 "누군가 있다"이지 "몇 명"이 아니다
히스테리시스거리 ≤ 200m면 Enter, ≥ 220m면 Leave경계에 선 NPC가 판정마다 Enter/Leave를 번갈아 내면 재계획 큐가 폭주한다
에지 트리거상태가 바뀐 NPC만 이벤트를 낸다플레이어가 마을에 서 있으면 이벤트 0건이 정상이다

실제 연동 시 남는 것

TCP 링크 구현은 NPC 서버 코드를 한 줄도 바꾸지 않고 끝났다 — 이것이 이 인터페이스 설계의 검증 기준이었다. 실제 게임서버에 붙일 때 추가로 필요한 것은 아래 셋뿐이며, 전부 Npc.Wire와 그 바깥에서 해결된다.

항목상태내용
이기종 엔디언·패딩구현 필요unmanaged 배열을 원시 메모리로 복사하므로 양쪽이 같은 x64 .NET 런타임임을 전제한다. 다른 런타임의 게임서버에 붙일 때는 필드별 쓰기를 하는 커스텀 포매터로 바꾼다 — 바꿀 자리가 Npc.Wire 한 곳뿐인 것이 이 설계의 요점이다
인증·암호화구현 필요핸드셰이크가 검증하는 것은 "같은 데이터를 보고 있는가"지 "네가 누구인가"가 아니다. 신뢰 경계 밖에 놓으려면 TLS와 토큰이 필요하다
샤딩구현 필요링크 하나가 게임서버 하나에 붙는다. 월드를 여러 프로세스로 쪼개면 존별 라우팅이 필요하다
소켓 경로에서는 결정론이 성립하지 않는다

리플레이 100% 일치는 루프백 경로의 성질이다. 소켓에서는 명령이 몇 틱 늦게 도착할 수 있고 그것이 스텝 경계를 바꾼다. 결함이 아니라 사실이다 — 실제 게임서버에 붙으면 원래 그렇다. 재현이 필요하면 기록 링크로 이벤트 열을 남겨 재생 링크로 되민다. 그 경로는 결정론이다.
