5장 — 틱 루프와 SoA 저장소

여기가 심장부다. 10Hz로 돌고, 한 틱에 5,000마리를 전부 훑고, 예산은 20 ms이며, 힙 할당이 0바이트다. 이 장은 그 루프의 여섯 단계를 하나씩 열어 보고, class Npc를 5,000개 만들지 않는 이유를 메모리 그림으로 확인한다.

예산을 100 ms 전부로 잡지 않는 이유 같은 프로세스에서 다른 것들도 돈다 — 대시보드 HTTP, 소켓 리시버, 직렬화, GC. 틱 루프가 100 ms를 다 쓰면 그 순간 다음 틱이 밀리고, 밀린 틱은 영원히 따라잡지 못한다 (게임서버가 계속 TickSync를 보내기 때문이다). 20 %로 잡으면 나머지 80 ms가 완충이 된다 — 실측에서 틱 사이 여유는 98.3 ms였다.

2. 틱 루프 여섯 단계

src/Npc.Runtime/NpcServerLoop.cs
public async Task RunAsync(CancellationToken ct)
{
    while (await _link.Events.WaitToReadAsync(ct))       // ① await — 이벤트 대기
    {
        int drained = DrainEvents();                      // 이벤트 배수 (멱등, N7)

        while (_clock.TryAdvance(out Tick tick))            // TickSync 를 받은 만큼만 진행
        {
            RunTick(tick, drained);
            drained = 0;

            await _link.FlushAsync(ct);                    // ② await — 유일하게 허용된 것
            TicksCommitted = tick.Value;
        }

        await _link.FlushAsync(ct);   // 인터럽트가 틱 밖에서 낸 명령도 내보낸다
    }
}

public void RunTick(Tick tick, int drained = 0)
{
    Observer?.OnTickBegin(tick);

    _bands.Rebalance();                       // ③ LOD 밴드 이동 — 틱당 최대 64건
    Handoff?.DrainReturns(_replanQueue);      // ④ 워커가 되돌린 요청을 힙에 복귀
    _cognition.Scan(tick, _replanQueue);      // ⑤ 인지 스캔 — 틱당 최대 150건
    Handoff?.Pump(_replanQueue, PumpPerTick); //    힙 → 워커 통로
    _executor.Step(tick, _link);              // ⑥ 플랜 실행 + 명령 발행
    Transition?.Tick(_clock, _swapper);       // ⑦ 버킷 전환 예약 처리
    _swapper.ApplyPendingSwaps(_executor);    // ⑧ 스텝 경계 플랜 스왑

    TicksProcessed++;
    Observer?.OnTickEnd(tick, _cognition.LastScanned, drained);
}

2.1 각 단계에 상한이 있다

단계상한넘치면왜 이 값
이벤트 배수MaxEventsPerTick = 4,096다음 틱으로 넘긴다 (EventBacklogs++)이벤트 폭주가 틱을 삼키지 못하게
LOD 밴드 이동MaxBandMigrationsPerTick = 64커서를 들고 다음 틱에 이어서존 전체 승격이 한 틱에 배열을 다시 짜면 그게 스파이크다
인지 스캔MaxScansPerTick = 150밴드별 커서로 다음 틱에 이어서상한이 없으면 실측 637건까지 오른다
워커 통로 펌프PumpPerTick (기본값 존재)다음 틱에힙을 만지는 것은 틱 루프뿐이어야 한다
플랜 실행상한 없음 — 전원 순회—SoA 배열 순회 한 번이라 5,000이어도 싸다
버킷 전환지터로 분산 (±300 또는 ±14틱)—5,000마리가 한 틱에 갈아타면 스파이크
"굶는 NPC 는 없다" 상한에 걸려 잘린 몫은 버려지지 않는다. 밴드별 커서가 잘린 뒤쪽을 기억했다가 다음 틱에 이어 본다. 군중이 생기면 판정 주기가 늘어날 뿐이고, 어떤 NPC도 영원히 스캔되지 않는 상태에 빠지지 않는다.

3. SoA — class Npc를 5,000개 만들지 않는다

매 틱 전원을 훑는다. 그러면 캐시 지역성이 곧 성능이다. 객체 배열(AoS)과 배열의 구조체(SoA)의 차이가 여기서 결정적이다.

3.2 인벤토리가 int[][]가 아닌 이유

// 평탄한 1차원 배열 + 스트라이드
public int[] Inventory = [];
public int InventoryStride { get; }   // = 최대 item code + 1 = 83

public Span<int> InventoryOf(int npc) =>
    Inventory.AsSpan(npc * InventoryStride, InventoryStride);   // 할당 0

5,000개의 작은 배열은 참조 추적이 늘고 캐시 라인이 흩어진다. 평탄 배열이면 한 NPC의 인벤토리가 연속 메모리에 있고, Span으로 잘라 쓰므로 할당도 없다.

3.3 RingBuffer8 — 구조화 기억

public readonly record struct RecentEvent(
    GameEventKind Kind, Tick At, int Subject, byte Salience);

자연어 요약이 아닌 이유

이 값이 프롬프트 서픽스 300토큰 예산 안에 들어가야 한다. "어제 대장장이와 다퉜다" 같은 문장을 저장하면 요약 호출이 필요하고, 그 순간 드리프트와 비용이 동시에 생긴다. 값 타입 8칸이면 둘 다 없다.

왜 하필 8칸인가

서픽스에 실리는 것은 salience 상위 3개뿐이다. 8칸이면 최근 사건 중 중요한 것이 밀려나기 전에 뽑힐 만큼은 된다. 더 늘리면 콜드 메모리만 커진다. NpcTransform은 중요도 0이라 아예 안 들어간다 — 최다 이벤트라 넣으면 8칸이 그것만으로 찬다.

4. 할당 0을 지키는 방법

"할당하지 말자"는 구호로는 지켜지지 않는다. 아래는 이 저장소가 실제로 쓰는 구체적인 장치들이다.

흔한 코드여기서 쓰는 것왜
foreach (var npc in list.Where(...)) for (int i = 0; i < _store.Count; i++) LINQ는 이터레이터 객체를 할당한다
logger.LogDebug($"npc {id} failed") [LoggerMessage] 소스 생성 로거 문자열 보간은 박싱 + 할당이다
IEnumerable<NpcCommand> Emit(...) int Emit(..., Span<NpcCommand> destination) 호출자가 준 버퍼에 쓴다. 사전 할당 _batch[4]
new ConcurrentQueue<T>() 사전 할당 링 버퍼 (CommandRing) 큐 노드가 할당이다
Dictionary 순회 정렬된 배열 + 첨자 할당 + 순서 비결정성 둘 다 문제
lock (_gate) { ... } Volatile.Read/Write + 원자 참조 교체 락 경합 자체가 틱을 밀어낸다
클로저를 캡처하는 람다 정적 메서드 · 값 타입 컨텍스트 (EmitContext) 캡처는 디스플레이 클래스 할당이다

4.1 계측 — gen0Collections로 재지 않는다

틱 루프를 재는 계기는 bytesPerTick 하나다 GC.CollectionCount(0)은 프로세스 전역 카운터다. 같은 프로세스에서 대시보드 HTTP·소켓 리시버·직렬화·Sim이 전부 할당하므로, Gen0가 0이 아니라고 해서 틱 루프가 할당한 것이 아니다. bytesPerTick은 틱 창 안의 스레드 할당 델타라 그 혼입이 없다.

P4 게이트에서 이 판정 기준이 한 번 개정됐다

718버킷 스토어로 돌렸더니 틱 창 할당 누계가 264 B가 나와 실패했다. 추적해 보니 틱당 누수가 아니라 콜드 스타트였다 — 회차를 3배(1,440틱 → 4,320틱)로 늘려도 할당이 정확히 같은 세 틱(1 · 148 · 396)에서만 나고 누계도 264 B 그대로였다. 그 코드 경로가 틱 창 안에서 처음 실행될 때의 JIT·정적 초기화 비용이었다. 

// 전:  AllocatedInTicks == 0                  → JIT 런타임에서 달성 불가능
// 후:  LastAllocatingTick * 2 < TicksProcessed  → "회차 후반부에 할당이 없다"
//      BytesPerTick == 0                       (그대로)

임의의 워밍업 상수를 두지 않았다. 실측(396틱)에 맞춰 상수를 정하면 게이트를 실측에 맞추는 것이다. "후반부"는 회차 길이에 따라 자동으로 정해지고, 진짜 누수는 계속 나므로 반드시 후반부에도 걸린다.

// NPC 별 결정론 지터. [-span, +span]. Random 을 쓰지 않는다.
public static int Jitter(NpcId npc, int salt, int span)
{
    int period = (span * 2) + 1;
    return (int)(Mix(npc.Value, salt) % (uint)period) - span;
}

5.1 페이싱과 결정론 — TicksCommitted가 따로 있는 이유

이 부분은 실제로 버그를 잡고 나서 생긴 코드다. 결정론 리플레이가 처음에 안 맞았고, 원인이 여기 있었다.

SpinOnce(sleep1Threshold: -1) 락스텝이라 매 틱 한 번은 기다리게 되는데, 여기서 Thread.Sleep(1)로 넘어가면 1,440틱짜리 게임 하루가 그것만으로 20초를 더 쓴다 — 실측 1분 39초 → 9분 8초였다. 그래서 스핀만 하고 절대 재우지 않는다.

6. 조립 — 무엇이 무엇을 아는가

NpcHost.Create가 유일하게 전부를 아는 곳이다. 순서에 이유가 있다.

src/Npc.Host/Program.cs — NpcHost.Create

MasterDataSet data = MasterDataLoader.Load(masterDataDir);

// ★ 로스터를 할당보다 먼저 뽑는다 — --zone 이 걸리면 실제 마릿수가 --npcs 보다 작다

순서 이유어기면
로스터가 할당보다 먼저 --zone이 걸리면 뒤쪽이 영원히 빈 배열이 되고, 로스터 해시가 게임서버와 어긋나 연결이 거절된다
폴백을 버킷보다 먼저 등록 버킷이 하나도 없을 때 Resolve가 유효한 플랜을 못 준다 (시나리오 C가 깨진다)

7.1 --max-speed는 처리량 측정이지 지연 측정이 아니다

게이트 회차는 대부분 --max-speed로 돈다 — 10Hz 페이싱을 끄고 최대 속도로 민다. 게임 로직은 여전히 Tick만 보므로 결과는 페이싱 유무와 무관하지만, 거기서 나온 "초당 명령 수"는 벽시계 기준 처리량이다. 실서비스 10Hz 회차의 p99는 1.674 ms이고, 틱 사이 여유는 100 − 1.7 = 98.3 ms다.

5장 요약
  • 틱 루프의 await은 두 개뿐이다 — 이벤트 대기와 FlushAsync.
  • 각 단계에 상한이 있고, 잘린 몫은 커서로 다음 틱에 이어 본다. 굶는 NPC는 없다.
  • 핫 배열 23 B × 5,000 = 115 KB가 L2에 들어가는 것이 20 ms 예산의 근거다.
  • 할당 0은 구호가 아니라 LINQ 금지 · Span 반환 · 소스 생성 로거 · 사전 할당 링의 결과다.
  • 계측은 bytesPerTick으로 한다. gen0Collections는 프로세스 전역이라 못 쓴다.
  • TicksCommitted 기준 페이싱이 리플레이 100 % 일치의 조건이다.
