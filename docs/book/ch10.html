10장 — 전송과 테스트 베드

3장에서 정한 계약이 실제 소켓 위에서 성립하는지를 확인하는 층이다. P6는 게임서버 대역과 WinForms 클라이언트와 와이어 프로토콜을 통째로 새로 만들었는데, Npc.Runtime·Npc.Planning·Npc.Core·Npc.Contracts의 diff가 0줄이다. 그것이 이 Phase가 잰 것이다.

1. 왜 Npc.Wire를 따로 두는가

계약 타입에 [MemoryPackable]을 붙이면 Npc.Contracts가 직렬화기 버전에 묶인다. 이 프로젝트는 "외부 NuGet 의존 0"이 규칙이고, 그 규칙이 있는 이유는 계약이 특정 라이브러리의 수명에 종속되면 안 되기 때문이다.

2. 프레임 — 손으로 쓴 8바이트 헤더

src/Npc.Wire/FrameCodec.cs
// 버전을 길이보다 먼저 본다 — 버전이 다르면 길이 해석 자체를 믿을 수 없다.
if (version != Version)
    throw new InvalidDataException($"와이어 버전이 다르다: 받은 {version}, 기대 {Version}.");

if (length > MaxPayloadLength)
    throw new InvalidDataException(
        $"페이로드가 상한을 넘는다: {length}B > {MaxPayloadLength}B. 프레임 경계가 밀렸을 가능성이 높다.");

if (buffer.Length < total) return false;   // 아직 다 안 왔다. 버퍼를 건드리지 않는다
길이 상한 검사를 빼지 않는다 길이 접두 프로토콜에서 그 검사가 없으면 잘못된 4바이트 하나로 프로세스가 죽는다. 상대가 악의적이지 않아도 프레임 경계가 한 번 밀리면 바로 그 상황이 된다. 예외를 던지되 연결만 끊고 프로세스는 산다 — 호출부가 잡아서 Bye(ProtocolViolation)를 보내고 소켓을 닫는다.

3. 핸드셰이크 — 네 값이 전부 맞아야 붙는다

검증 값어긋나면 생기는 일거절 코드
프로토콜 버전프레임 해석 자체가 안 된다ProtocolVersion
마스터데이터 콘텐츠 해시POI code 1이 서로 다른 장소를 가리킨다MasterDataMismatch
NPC 로스터 해시대장장이에게 밭을 갈라고 명령하게 된다 — 첨자가 어긋난다RosterMismatch
타임스케일게임 초 → 틱 환산이 달라 타임아웃이 전부 어긋난다TimeScaleMismatch
로스터 해시가 필요한 이유 NPC 선택 규칙(NpcRoster.Select)이 한 곳에만 있고 게임서버도 같은 함수를 부른다. 그래도 --zone 필터가 양쪽에서 다르면 집합이 갈리는데, 그 사고는 조용히 일어난다 — 양쪽 다 정상적으로 돌면서 서로 다른 NPC를 가리킬 뿐이다. 해시를 핸드셰이크에 실어 연결 시점에 터뜨린다.

3.1 해시를 hex 문자열로 싣지 않는다

// SHA-256 32바이트를 ulong 4개로. N3(패킷에 string 금지)이 와이어에서도 그대로다.
[MemoryPackable]
public readonly partial record struct WireHash(ulong A, ulong B, ulong C, ulong D);

ulong 4개면 정확히 32바이트라 손실도 없다. hex로 실으면 64바이트에 파싱까지 붙는다. 사람이 읽어야 할 때만 ToHex()로 되돌린다 — 로그·비교 출력용이고 와이어에는 안 나간다.

5.1 판정 명령이 틀려 있던 것을 고친 이야기

G6-1의 원래 판정 명령 git diff main -- src/Npc.Runtime ... 이었는데, main 위에서 자기 자신과 비교하니 언제나 비어 있었다. 즉 항상 통과하는 게이트였다. 커밋 범위를 명시하는 형태로 고쳤고, 고친 뒤에도 실제로 0줄이었다.

5.2 G6-5의 판정 계기를 바꾼 이유

원래 기준은 "Gen0 증가 0"이었는데, 그 계기는 GC.CollectionCount(0)이라 프로세스 전역이다. 대시보드 HTTP·소켓 리시버·직렬화가 전부 든다 — 틱 루프를 재지 못한다. 그래서 bytesPerTick == 0으로 바꿨다(결정 1-A). 5장 §4.1과 같은 이야기다.

5.3 G6-9에서 관측된 것 — 사람이 볼 것 하나가 안 보였다

시간대가 바뀌어도 버킷 플랜을 안 갈아탄다 데모 3종이 전부 끝까지 돌았고 지표도 전부 정상이었는데, 인스펙터의 planBucket이 게임 시각을 따라가지 않았다. 이대로면 G6-10에서 사람이 볼 것이 안 보인다.

이 문제는 P6 밖이다 — 루프백 회차에서도 그대로 재현된다. 즉 테스트 베드의 결함이 아니라 본체 쪽 문제이고, 그래서 P6 게이트로 덮지 않고 따로 남겼다.

6. TCP 링크 — 호스트에서 어떻게 배선되나

src/Npc.Host/Program.cs
case LinkKind.Tcp:
    // 대역을 만들지 않는다 — Replay 와 같은 경로다.
    // 세계를 미는 것은 게임서버이고, 우리는 이벤트를 받아 명령을 낼 뿐이다.
    link = tcp = TcpLink(options, data, roster);
    break;
TCP 링크만 구체 타입으로 따로 들고 있는 이유 접속·재접속 루프는 IGameServerLink에 없는 동작이다 — 계약이 Enqueue·FlushAsync·Events뿐이기 때문이다. 누군가는 구체 타입으로 RunAsync를 돌려야 하고, --link record는 데코레이터라 감싼 참조로는 안쪽 소켓에 닿을 수 없다.

그리고 이 소켓 루프는 WhenAll에 넣지 않는다 — 취소될 때까지 끝나지 않으므로 --days N처럼 틱 루프가 먼저 끝나는 회차에서 종료를 막는다.

6.1 --link record가 무엇을 감쌀지 정하는 법

// --gs-host / --gs-port 를 명시했는가 로 가른다.
// 기본값과 명시값을 구별하지 못하면 "포트가 7010 이니까 TCP 겠지" 라는 추측이 된다.
public bool UsesGameServer { get; init; }
명령기록되는 것
--link recordSim 대역과의 왕복 — 재현 가능한 자료
--link record --gs-port 7010소켓 너머 게임서버와의 왕복 — 실전 트래픽
둘 다 → --link replay --trace <path>같은 이벤트 열을 다시 먹여 결정론 검증

10장 요약
  • Npc.Wire를 따로 둔 것은 계약이 직렬화기 버전에 묶이지 않게 하기 위해서다. 드리프트는 Wire 카테고리가 잡는다.
  • 프레임 헤더는 손으로 쓴 8바이트다. 길이의 진실을 두 곳에 두지 않는다.
  • 핸드셰이크는 네 값을 검증하고 우회 옵션이 없다. 로스터 해시가 없으면 첨자 어긋남이 조용히 진행된다.
  • 클라이언트는 게임서버가 아니라 NPC 서버를 직접 폴링한다 — 링크에 없는 정보를 중계하면 가짜 결합이 생긴다.
  • P6가 잰 것은 "본체 diff 0줄"이고, 그 판정 명령이 틀려 있던 것도 찾아 고쳤다.
  • 남은 게이트는 사람이 화면 앞에 앉는 일 하나다.
