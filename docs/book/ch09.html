1. 티어 라우팅 — 무엇이 어디로 가나

1.1 선택 규칙 — 품질이 아니라 재사용 횟수

src/Npc.Llm/TieredPlanCompiler.cs
private Tier Wanted(in PlanRequest request)
{
    // 아키타입 플랜은 수천 NPC 가 재사용한다 → 품질에 투자한다.
    if (request.Quality == PlanQuality.Archetype) return Tier.T2;

    // 개별 재계획은 1회용이라 LOD 와 무관하게 T1. 단, T1 이 밀려 있으면 T2 로 흘린다.
    return LocalQueueDepth is { } depth && depth() > SpilloverThreshold
        ? Tier.T2 : Tier.T1;
}
스필오버 임계가 64인 근거 T1 지연이 실측 5.1초이므로 큐에 64건이 밀려 있으면 마지막 건은 5분 뒤에 처리된다. 그 시점에는 스냅샷 낡음 판정(6장 §5.1)이 거의 확실히 폐기한다 — 즉 임계를 넘긴 뒤의 T1 요청은 대부분 헛일이다. 그래서 T2로 흘린다.

이건 "늦게 오는 것보다 비싸게 오는 게 낫다"는 임시 조치다. Spillovers가 T2 호출의 상당 부분이면 T1 워커가 모자란 것이고, 워커 수나 예산을 다시 잡아야 한다.

1.2 강등은 내려가기만 한다

private Tier Downgrade(Tier wanted)
{
    if (wanted == Tier.T2 && Available(Tier.T2)) return Tier.T2;
    return Available(Tier.T1) ? Tier.T1 : Tier.None;
}
올리지 않는 이유 T1 차단은 "재계획 전면 중단, 캐시 플랜만 남는다"는 뜻이다. 개별 재계획을 T2로 올려 보내면 시나리오 C 2단계가 측정하려던 것이 사라진다. 킬스위치는 "무엇이 끊겼을 때 무엇이 남는가"를 재는 장치이지, 우회로가 아니다.

3. 플랜 스토어 — 락 없는 조회

3.1 개별 플랜 풀 — 512칸이 의미하는 것

PlanId 값가리키는 것
> 0레지스트리 id. 버킷 인덱스가 아니다
== 0최후 플랜 (IdlePlanId)
< 0개별 풀 슬롯. ~value가 슬롯 번호
~slot이고 -slot이 아닌 이유 NpcStore.PendingPlanId도 0 = 없음이므로 개별 슬롯은 반드시 음수여야 한다. -slot이면 슬롯 0이 0과 겹친다. ~slot이면 슬롯 0이 −1이 된다.

512는 "동시에 특별 대우를 받는 NPC 수"의 상한이고, 이것이 곧 재계획 예산과 맞물린다. TurnoverRate(Evicted / 512)가 크면 개별 재계획이 과다한 것이다.

회수된 슬롯을 예전 주인이 읽으면 TryGet이 false를 돌려주고, 호출부는 버킷 플랜으로 되돌아가야 한다. 실행기의 PlanOf가 그 일을 한다(7장 §2.3).

계측 경로는 TryPeek을 쓴다 — TryGet을 쓰면 /metrics를 폴링하는 것만으로 LRU 순서가 바뀌어 어느 NPC가 슬롯을 잃는지가 대시보드 열람 여부에 달리게 된다. 리플레이가 깨지는 길이다.

5.1 AIMD — 429를 맞으며 올리지 않는다

// 성공 16연속 → +1 (additive increase)
// throttle(429) → /2 (multiplicative decrease)
public const int DefaultStart = 8;
public const int DefaultSuccessStreak = 16;
초기값 8의 근거를 정직하게 적는 방식 규칙은 "실측한 429 최초 발생 동시성의 절반, 그 실행 전이면 8"이다. 그런데 OpenRouter 동시 18까지, Poe 동시 32까지 429가 한 번도 나지 않았다 — 절반 규칙이 발동할 값이 없어 8을 유지한다. 이 값과 근거는 회차마다 manifest.json의 generated_by.concurrency· first_rate_limit_concurrency에 남는다.

기준을 맞추려고 동시성을 올려 429를 맞지 않는다는 것이 docs/13 §7의 규칙이다.

5.2 워밍업 — 사양이 틀렸다는 것을 실측이 보여준 사례

사양(docs/13 §4)의 전제실측
동시 N개가 전부 cache miss로 시작한다아니다. 파동 안에서 먼저 도착한 요청이 캐시를 만들고 나머지가 물려받는다 — 동시 32에서 워밍업 없이 68.6 % 적중
cache write에 할증(1.25~2배)이 붙는다없다. Gemini 암시적 캐싱은 write 할증이 없고 적중분이 오히려 0.25배로 싸다
그래서 워밍업 1회가 N번의 할증을 막는다막을 것이 없다. 요청 1개가 늘어나는 만큼 순손실이다

그런데도 워밍업을 기본으로 켜 둔다 — 이유 셋, 전부 비용 논거가 아니다

  1. Anthropic 계열에서는 전제가 성립한다. 명시적 캐싱(cache_control)은 write 할증이 실제로 있다. 다만 그 실측은 이 저장소의 어느 엔드포인트로도 못 한다 — OpenAI 호환 경유로는 cache_control을 실어 보낼 수 없다.
  2. 회차 전체의 예비 점검이다. 2,880건을 던지기 전에 키·엔드포인트·프리픽스·스키마가 실제로 통하는지 요청 하나로 확인한다.
  3. 비용이 무시할 수준이다. 2,880건 회차에서 요청 1개는 0.03 %다.

docs/13 §4·§8의 "비용 3배" 표현은 이 실측으로 고쳤다. 사양이 틀렸으면 사양을 고친다 — 코드를 사양에 맞추지도, 사양을 못 본 척하지도 않는다.
