6부 · 돌려보고 고치기

11장 — 설정을 바꾸면 무엇이 달라지나

이 장은 레퍼런스이자 실습서다. 실행 옵션 26개, appsettings.Llm.json, 코드 안의 튜닝 상수 20여 개를 "바꾸면 무엇이 어떻게 달라지는가" 기준으로 정리했다. 아래 시뮬레이터로 조합을 골라 보면 그 회차에 무슨 일이 벌어지는지 미리 볼 수 있다.

가장 자주 볼 장 옵션 26개 튜닝 상수 20+

1. 먼저 — 다섯 줄로 돌려보기

# 0) 확인
dotnet --version                          # 10.x

# 1) 빌드 + 테스트 (LLM 안 부른다)
dotnet build -c Release
dotnet test "--filter Category!=Golden&Category!=Gate&Category!=Load"

# 2) 마스터데이터만 검증 (V1~V11)
dotnet run --project src/Npc.Host -- validate --masterdata ./masterdata

# 3) LLM 없이 스모크 — 500마리 · 게임 7일 · 600배속
dotnet run -c Release --project src/Npc.Host -- `
    --loopback --npcs 500 --time-scale 600 --days 7 --no-llm

# 4) 대시보드 보면서 5,000마리
dotnet run -c Release --project src/Npc.Host -- `
    --loopback --npcs 5000 --time-scale 60 --days 7 --scenario ./scenarios/siege.jsonl
# → http://localhost:5080/dashboard
LLM 없이도 전부 돈다 기본이 --tier none이라 LLM을 한 번도 부르지 않는다. API 키도 GPU도 없이 NPC 5,000마리가 게임 7일을 완주한다 — 폴백 40개 + 프리베이크 플랜으로. P1 게이트가 잰 것이 정확히 이것이다.

2. 조합 시뮬레이터

3. 실행 옵션 전체

3.1 규모와 시간

옵션기본바꾸면 무엇이 달라지나
--npcs N500 SoA 배열 크기 · 인지 스캔 대상 · 명령 수. 상한은 npc_instances.json의 5,000 — 넘겨도 Math.Min으로 잘린다
--time-scale N60 게임 초 ↔ 틱 환산. timeout_s가 전부 이 값으로 나뉜다 — 600배속이면 게임 300초 타임아웃이 5틱이다
--days N1 돌릴 게임 일수. 0이면 무제한. 총 틱 = 86,400 × 10 ÷ TimeScale × days
--player-bots N20 0이면 모든 NPC가 LOD 3(비활성)에 머문다 — 인지 스캔이 0이 되고 재계획이 사실상 멈춘다
--seed N20260725 Sim의 시드. 게임 로직의 지터는 이 값과 무관하다 — 그건 Hash(npcId)다
--zone id[,id]전체 로스터 필터. 게임서버와 같아야 한다 — 다르면 로스터 해시가 어긋나 핸드셰이크에서 거절된다

3.2 링크

옵션기본바꾸면 무엇이 달라지나
--loopback기본Npc.Sim 인프로세스 월드에 직결
--link null—TickSync만 흐른다. 링크 없이 기동되는지 확인용. 명령은 전부 버려진다
--link record—안쪽 링크를 감싸 jsonl로 기록. 안쪽이 무엇인지는 --gs-* 명시 여부로 갈린다
--link replay—기록을 재생. Sim을 만들지 않는다. --trace가 필수
--link tcp—실제 소켓. Sim을 만들지 않는다 — 세계를 미는 것은 게임서버다
--trace <path>—record의 출력 · replay의 입력
--gs-host / --gs-port127.0.0.1 / 7010게임서버 주소. 명시하면 --link record가 TCP를 감싼다

3.3 티어와 재계획

옵션기본바꾸면 무엇이 달라지나
--tier none｜t1｜t2｜allnone 워커를 띄울지 정한다. none이면 ReplanWorker가 아예 없어서 큐가 채워지기만 하고 비지 않는다 — 그 성질을 보는 것이 P4 게이트 항목 10이다
--no-llm—--tier none의 별칭
--t1-workers N2 T1 예산 상한이 0.195 × N req/s로 곱해진다. W1 실측에서 8B는 동시 8에서 0.36 req/s로 붕괴한다 — 무작정 올리면 오히려 준다
--t2-workers N8외부 동시 요청 수. 파일럿에서 동시 24까지 429가 0회였다
--t1-engine / --t2-engine설정 파일appsettings.Llm.json의 엔진 id. 키가 없으면 그 티어가 꺼지고 경고만 남는다
--weights A｜B｜C｜DB 재계획 점수 가중치 세트. 오타는 기동 실패다 — 조용히 기본값으로 떨어지면 A/B 결과가 거짓이 된다
--scan-cap N150 0이면 상한 해제. 측정 전용이다 — 운영에서 풀면 그것이 틱 예산을 지키는 장치를 없애는 것이다

3.4 장애 주입과 측정

옵션기본바꾸면 무엇이 달라지나
--fail-rate 0~10Sim이 액션을 실패시키는 확률 → on_step_fail 정책이 돈다
--drop-rate 0~10 명령 유실 확률 → 타임아웃 합성 경로가 돈다. G6-7이 0.3에서 "멈춘 NPC 0"을 확인한다
--max-speed— 10Hz 페이싱을 끈다. 처리량 측정이지 지연 측정이 아니다. 게임 로직은 여전히 Tick만 보므로 결과는 같다
--scenario <jsonl>—존 상태·기후·킬스위치 주입
--port N5080대시보드·메트릭 포트
--no-dashboard—웹 호스트를 안 띄운다. 헤드리스 스모크·CI용
--dev-control꺼짐 POST /control/killswitch를 연다. 조건부 401이 아니라 조건부 라우트 등록이라 없으면 404다
--masterdata / --planstore./masterdata / ./planstore없으면 저장소 루트를 위로 찾아 올라간다

5. appsettings.Llm.json

필드바꾸면
preferred (배열)앞에서부터 키가 채워져 있는 첫 엔진을 쓴다. 사람이 매번 --model을 바꾸면 회차마다 엔진이 달라져 실측을 나란히 못 놓는다
default--t2-engine을 안 줬을 때의 엔진
kindDotLlm / LlamaCpp / External. 비용 계산과 캐시 판정 방식이 갈린다
api_key_env환경변수 이름만 적는다. 키 자체를 파일에 쓰지 않는다
*_usd_per_m_tok비용 집계와 예산 캡 판정에 그대로 쓰인다. 모델을 바꾸면 이 값도 바꾼다
suffix_tag엔진 전용 꼬리표(Qwen3의 /no_think). 서픽스 끝에만 붙는다 — 프리픽스는 안 건드린다
temperature시도 1의 값. 재시도는 +0.2다
max_output_tokens플랜 하나는 300~700 토큰. 추론형 모델은 이 상한을 추론 토큰으로 먼저 소진한다
force_json_schema기본 false. 켜면 유효 JSON은 오르지만 어휘 검증이 무너진다(W1 실측 통과 0/100)
timeout_seconds로컬 CPU 추론은 분 단위가 나온다. 로컬 엔진은 900을 쓴다
엔진을 바꿨을 때 같이 확인할 것
  1. 단가를 갱신했나 — 안 하면 예산 캡이 실사용과 어긋난다
  2. 이 엔진이 cached_tokens를 보고하는가 — dotLLM은 항상 0을 보고한다. 대시보드가 "미보고"로 그려야 한다
  3. 추론형인가 — 그렇다면 추론 예산을 따로 눌러야 JSON이 나온다

6. 코드 안의 튜닝 상수

아래 값들은 CLI로 못 바꾼다. 바꾸려면 코드를 고쳐야 하고, 대부분은 바꾸면 안 되는 이유가 주석에 적혀 있다.

상수값파일올리면 / 내리면
TickBudgetMs20NpcServerLoop 오버런 판정 기준. 올리면 문제가 안 보이게 될 뿐이다
MaxEventsPerTick4,096NpcServerLoop 올리면 이벤트 폭주가 틱을 삼킨다 / 내리면 EventBacklogs가 는다
MaxScansPerTick150CognitionScheduler 이것이 O(1)을 만든다. 올리면 틱 시간이 선형으로 늘고, 내리면 판정 주기가 늘어난다
MaxBandMigrationsPerTick64LodBandSet 내리면 PendingMigrations가 상시로 커진다 / 올리면 공성 때 스파이크
ReplanQueue 용량4,096ReplanQueue 올리면 이미 상황이 바뀐 NPC가 쌓인다. 낡음 판정이 그만큼 더 폐기한다
MaxUrgentSlots용량의 50 %ReplanQueue 올리면 공성 때 일반 재계획이 영원히 안 된다
UrgentBase1,000ReplanQueue 일반 점수 상한(9.5)과 겹치지 않게 잡은 값
ReplanOnFailScore50PlanExecutor 이탈(≤9.5)보다 크고 인터럽트(1000+)보다 작다
DefaultPumpPerTick64ReplanHandoff 틱 예산 방어. 포화 시 한 틱에 전부 옮기면 그 틱만 O(4096 log n)
DefaultMaxDrift4ReplanSnapshots 내리면 폐기가 늘어 예산이 헛돈다 / 올리면 낡은 플랜이 반영된다
DefaultStaleTicks36,000Weights 노후 항이 1.0이 되는 틱. 배속 60에서 게임 6시간
DeviationScale8ReplanScorer 42로 나누면 실제 이탈이 0.05 밑으로 깔려 항이 죽는다
IndividualPlanPool.Capacity512IndividualPlanPool "동시에 특별 대우받는 NPC 수". 올리면 TurnoverRate가 준다
SpilloverThreshold64TieredPlanCompiler T1 지연 5.1 s × 64 = 5분. 그 이후 요청은 대부분 낡아서 폐기된다
DefaultEstimatedTokens23,109TieredPlanCompiler 예산 선차감량. 실측(6,655,438 / 288)이다. 프리픽스를 바꾸면 같이 바꾼다
MaxAttempts2LlmPlanCompiler 올리면 성공률은 거의 안 오르고 지연이 선형으로 는다
TokenBudget (서픽스)300PlanRequestSuffix 올리면 매 요청의 prefill이 그만큼 는다. 캐시가 안 걸리는 부분이다
TokenFloor (프리픽스)4,096PromptPrefix 미달하면 프롬프트 캐시가 아예 안 걸린다 (제공사 최소 임계)
JitterSpread / ZoneJitterSpread300 / 14BucketTransition 존 쪽을 올리면 공성 3초 요구를 못 지킨다
PoiBinder.CandidateCount4PoiBinder 1이면 수백 마리가 같은 POI로 몰린다 / 크게 하면 먼 곳까지 간다
MaxCommandsPerStep4CommandEmitter 액션 하나가 낼 수 있는 명령 수. 링크 큐 사이징의 곱수이기도 하다
PriorityCommandRing.DefaultCapacity4,096PriorityCommandRing 호스트가 npcs × 4로 다시 잡는다. 그대로 두면 첫 틱에 904건이 버려진다

7. 마스터데이터로 바꾸는 것들

바꾸고 싶은 것어디를주의
NPC가 어떤 행동을 할 수 있나archetypes.json의 allowed_actions 프리픽스가 바뀐다 → 플랜 전량 무효
NPC 성격 (겁 많음 · 부지런함)archetypes.json의 traits 인터럽트 규칙이 이 값을 본다. 프리픽스에도 실린다
인구 구성population_weight → gen_npcs 재실행 합이 1.0이어야 한다 (V5). 프롬프트 SHA는 안 바뀐다
어느 존이 위험한가zones.json의 default_region_state 도달 버킷 집합이 바뀐다 — 새 조합을 프리베이크해야 한다
즉시 반응 규칙interrupts.json 재기동만 하면 즉시 반영. 프리베이크 불필요
액션의 타임아웃actions.json의 default_timeout_s 스텝이 timeout_s를 명시하면 그쪽이 이긴다
액션이 어떤 명령을 내나actions.json의 emits 런타임 코드를 안 고쳐도 된다
최후의 보루 행동fallback_plans.json V7·V8이 기동 시 검사한다. loop: true·skip 유지
LLM에게 주는 지시prompt/system_rules.md 한 글자만 바꿔도 프리픽스 SHA가 바뀐다 → 전량 무효

무효화 범위 전체 표는 2장 §9에 있다.

9. 자주 막히는 곳

증상원인해결
마스터데이터 폴더를 찾지 못했다 dotnet run --project는 작업 폴더를 프로젝트 폴더로 잡는다 보통은 알아서 위로 찾아 올라간다. 안 되면 --masterdata에 절대경로
--zone을 줬더니 NPC가 없다 존 id 오타. 조용히 무시하지 않는다 에러 메시지가 있는 존 목록을 찍어 준다
인지 스캔이 0이다 --player-bots 0 — 전원이 LOD 3 봇을 20 이상으로
재계획 큐가 항상 가득 --tier none이라 비우는 워커가 없다 정상이다. 그 상태에서도 NPC는 기존 플랜으로 돈다
합성 타임아웃이 17 %나 된다 Sim이 Craft·Trade 일부를 일부러 흘린다 결함이 아니라 유실 대응 경로가 상시로 돈다는 증거다
첫 틱에 명령이 수백 건 드롭 링크 큐 크기가 npcs × 4보다 작다 호스트가 자동으로 잡는다. 커스텀 배선이면 직접 계산
--link replay가 안 뜬다 --trace 없이 실행 파싱 단계에서 막는다 — 필수 인자다
TCP 연결이 RosterMismatch로 거절 양쪽 --npcs·--zone이 다르다 같은 값을 준다. 우회 옵션은 없다
--tier t2인데 LLM을 안 부른다 API 키 환경변수가 없다 → 티어가 꺼지고 경고만 기동 로그의 warn: T2 엔진 '…' 의 키(…)가 없다를 본다

11장 요약
  • LLM 없이 전부 돈다. 기본이 --tier none이고 그것이 P1 게이트의 조건이었다.
  • --player-bots 0은 인지 LOD를 통째로 죽인다. 실수하기 쉬운 옵션 1위다.
  • --scan-cap 0과 --max-speed는 측정 전용이다. 운영에서 쓰지 않는다.
  • 시나리오 파일의 틱 좌표는 특정 배속 기준이다. 배속을 바꾸면 타임라인이 어긋난다.
  • 코드 상수는 대부분 바꾸면 안 되는 이유가 주석에 있다. 바꾸기 전에 읽는다.
