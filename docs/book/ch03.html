3장 — 게임서버 링크 계약

NPC 서버가 바깥과 닿는 유일한 자리다. 여기서 정한 여덟 개 규칙(N1~N8)이 "어떻게 붙일까"가 아니라 "어떻게 붙여도 깨지지 않는가"를 정한다. 실제로 P6에서 TCP 소켓 링크를 붙일 때 이 파일을 한 줄도 바꾸지 않았다 — 그것이 이 계약이 잰 것이다.

원문 · docs/02_GameServer_Link.md 패킷 29종 (명령 12 · 이벤트 17) 규칙 N1~N8

1. 관점 — 이름에 속지 않는다

이 장에서 가장 많이 하는 오해 IGameServerLink는 "게임서버의 인터페이스"가 아니다. 게임서버로 향하는 NPC 서버의 아웃바운드 포트이고, 이름의 "GameServer"는 상대방을 가리킨다. 우리가 만드는 것은 NPC 서버 하나뿐이다.

NPC 서버 (Npc.Host)만든다본체
경계 정의 (IGameServerLink + 패킷)만든다이 장의 내용
게임서버 대역 (Npc.Sim)만든다혼자 돌려보기 위한 가짜
실제 MMORPG 게임서버안 만든다"붙일 때 이렇게 붙는다"만 정의

2. 인터페이스 — 메서드가 다섯 개뿐인 이유

src/Npc.Contracts/IGameServerLink.cs
public interface IGameServerLink : IAsyncDisposable
{
    // NPC 서버 → 게임서버. 배치 큐에 쌓기만 한다. 반환값 없음 (N1).
    void Enqueue(in NpcCommand command);

    // 쌓인 배치를 내보낸다. 틱 루프 안에서 유일하게 허용되는 await 대상이다.
    ValueTask FlushAsync(CancellationToken ct);

    // 게임서버 → NPC 서버.
    ChannelReader<GameEvent> Events { get; }

    LinkState State { get; }
    LinkStats Stats { get; }
    event Action<LinkState>? StateChanged;
}
여기에 Task<bool> SendAsync() 를 추가하고 싶어질 때 그 순간 네트워크 RTT가 틱 루프를 블록한다. 5,000마리가 한 틱에 명령을 내는데 하나라도 응답을 기다리면 10Hz가 성립하지 않는다. 그래서 N1은 "명령은 fire-and-forget"이 아니라 "반환값 있는 전송 메서드를 이 인터페이스에 추가하지 않는다"로 적혀 있고, ContractRuleTests가 리플렉션으로 그것을 검사한다.

3. N1~N8 — 여덟 개 규칙

#규칙어기면강제
N1명령은 fire-and-forget. 반환값 있는 메서드를 추가하지 않는다 RTT가 틱을 블록한다리플렉션 검사
N2모든 패킷은 readonly record struct. 참조 필드·가변 컬렉션·object 금지 발행 경로에 힙 할당이 생긴다리플렉션 검사
N3패킷에 string 필드 금지. 전부 강타입 ID 직렬화 비용 + 프롬프트 인젝션 경로리플렉션 검사
N4DateTime/TimeSpan 금지. 시간은 Tick(long)만 리플레이가 깨진다리플렉션 검사
N5모든 명령에 CorrelationId 낡은 응답을 새 스텝 완료로 오인한다필드 존재 검사
N6모든 이벤트에 Sequence. 갭 검출 → 경보 유실을 조용히 넘겨 NPC가 영원히 멈춘다NpcServerLoop.EventGaps
N7이벤트 처리는 멱등. 2회 주입 → 상태 해시 동일 재전송이 인벤토리를 두 번 더한다NpcStore.StateHash() 비교
N8배치가 기본. Enqueue + FlushAsync만 노출 패킷당 syscall — 5,000 NPC에서 죽는다인터페이스 형태

3.1 N3이 보안 규칙이기도 한 이유

패킷에 string이 없다는 것은 성능 이야기로 들리지만, 실은 프롬프트 인젝션 방어선이다.

5. 명령은 유실된다 — 이 전제가 만든 것들

네트워크 링크에서 명령이 사라지는 것은 예외가 아니라 정상이다. 이 저장소는 그것을 가정하고, 유실돼도 NPC가 멈추지 않는 경로를 상시로 돌린다.

5.1 타임아웃 합성 — 모든 스텝에 timeout_s가 있는 이유

src/Npc.Runtime/PlanExecutor.cs
private bool SynthesizeTimeout(int npc, Tick tick)
{
    CompiledPlan plan = PlanOf(npc);
    int index = Math.Min(_store.StepIndex[npc], plan.Steps.Length - 1);
    long budget = TimeoutTicks(plan.Steps[index].TimeoutSeconds);

    if (tick.Value - _store.StepIssuedTick[npc] < budget) return false;

    _correlations.Invalidate(npc);                             // 늦게 온 응답을 무시한다
    _store.StepStatus[npc] = (byte)StepStatus.Failed;
    _store.LastFailReason[npc] = (byte)ActionFailReason.Timeout;
    TimeoutsSynthesized++;
    return true;
}
설계 결정이유
timeout_s가 0이면 안 된다. 컴파일러가 최소 5초로 올린다0이면 완료 이벤트를 못 받았을 때 NPC가 영구 정지한다
합성한 실패도 ActionFailReason.Timeout이라는 정상 실패 코드다on_step_fail 정책이 그대로 적용된다 — 특수 경로가 없다
합성 시 상관 ID를 무효화한다뒤늦게 도착한 응답이 새 스텝의 완료로 오인되면 안 된다
게임 초 → 틱 환산에 TimeScale이 들어간다60배속이면 게임 300초는 실시간 5초 = 50틱이다

6. N6·N7 — 시퀀스 갭과 멱등

모든 이벤트가 지나는 곳은 NpcServerLoop.DrainEvents 한 곳뿐이라, 갭 검출도 거기서 한다.

while (drained < MaxEventsPerTick && _link.Events.TryRead(out GameEvent ev))
{
    if (ev.Sequence > _lastSequence)
    {
        if (_lastSequence != 0 && ev.Sequence != _lastSequence + 1) EventGaps++;   // N6
        _lastSequence = ev.Sequence;
    }

    _applier.Apply(in ev);            // N7 — 같은 시퀀스면 내부에서 무시한다
    Transition?.Observe(in ev, _clock);
    // … 인터럽트 판정 …

        if (ev.Kind == GameEventKind.TickSync) break;   // ★ 여기서 끊는 것이 결정론의 조건이다
}
TickSync에서 배수를 끊는 이유 게임서버 대역은 틱마다 TickSync를 마지막에 낸다. 그래서 이 경계가 곧 틱 경계다. 끊지 않으면 생산자가 앞서 나간 만큼 다음 틱의 이벤트까지 한 배수에 들어오고, 아직 돌리지 않은 틱의 결과가 이번 틱의 판단에 반영된다. 얼마나 들어오는지는 스레드 스케줄이 정하므로 같은 시나리오가 실행마다 갈라진다 (실측: 이벤트 수 30,416 vs 30,649).

6.1 멱등성은 어떻게 확인하나

// 같은 이벤트 열을 두 번 주입하고 상태 해시를 비교한다.
ulong first  = store.StateHash();
Inject(events); Inject(events);      // 두 번
ulong second = store.StateHash();
Assert.Equal(first, second);          // N7

StateHash는 FNV-1a 64이고 부동소수 좌표를 비트 패턴 그대로 섞는다 — 반올림 차이를 놓치지 않기 위해서다.

7. 역압 — 무엇을 먼저 버리는가

src/Npc.Gateway/PriorityCommandRing.cs

큐가 차면 자기보다 낮은 우선순위부터 밀어낸다. Critical은 무손실이다. 드롭은 예외를 던지지 않고 Stats.CommandsDropped에만 나타난다.

드롭이 0이 아니면 사이징 실수일 수 있다 링크 큐는 한 틱치 명령을 담아야 한다. 소비자(FlushAsync)가 매 틱 전량을 비우므로, 여기서 넘치는 것은 역압이 아니라 크기 계산 실수다 — 실제로 기본값 4,096을 그대로 두면 NPC 5,000의 첫 틱에 904건이 버려지고 그 NPC들은 timeout_s가 만료될 때까지 첫 걸음을 못 뗀다. 그래서 호스트가 npcs × MaxCommandsPerStep으로 다시 잡는다.

P6가 실제로 증명한 것 TCP 링크를 붙이면서 IGameServerLink.cs를 한 줄도 바꾸지 않았고, Npc.Runtime의 세 프로젝트는 Npc.Gateway를 참조조차 하지 않는다. 링크 교체 시 런타임 diff = 0이 P5 게이트 항목 4였고, 그것이 통과했다.

8.1 데코레이터가 자연스럽게 되는 이유

// src/Npc.Host/Program.cs — --link record 는 안쪽이 무엇이든 감싼다
IGameServerLink inner = options.UsesGameServer
    ? TcpLink(options, data, roster)       // 소켓을 감싸면 실전 트래픽을 기록한다
    : SimDriver.Create(...).Link;          // 대역을 감싸면 재현 가능한 자료가 나온다

link = new RecordingGameServerLink(inner, path);

인터페이스에 메서드가 다섯 개뿐이고 반환값 있는 전송이 없기 때문에(N1) 데코레이터가 상태를 들고 있을 필요가 없다. N1이 성능 규칙일 뿐 아니라 구조 규칙이기도 한 지점이다.

9. Npc.Sim — 게임서버 대역

실제 게임서버 없이 NPC 서버를 돌리려면 상대방이 필요하다. Npc.Sim이 그 역할이다. 이것도 우리가 만든다 — 다만 "게임서버를 만든다"는 뜻은 아니다. 검증용 가짜다.

하위 시뮬하는 일
MovementSimMoveTo를 받아 거리·속도로 이동시키고 도착하면 NpcArrived
InteractionSimInteract·InventoryChange 처리
TransformEmitter이동 중인 NPC의 NpcTransform 발행
NeedsSim배고픔·갈증·스태미나 감소 → NpcVitalsChanged
PlayerBots가상 플레이어가 POI를 돌며 PlayerProximity 발행
ScenarioRunnerjsonl 시나리오를 재생 — 존 상태 전환·킬스위치
FaultInjector--fail-rate·--drop-rate 주입
DryRunValidator검증기 4단. 축소 세계에서 플랜을 1~2 사이클 돌린다
Sim은 일부러 불완전하다 Craft·Trade 같은 액션 중 일부를 처리하지 않고 흘린다(SimWorld.Unhandled). 그래서 P1 실측에서 합성 타임아웃이 명령의 17.3 %였다. 이것은 결함이 아니라 타임아웃 합성 경로가 상시로 돌고 있다는 증거다. 실제 게임서버가 붙으면 이 비율은 드롭률만큼으로 떨어진다.
3장 요약
  • IGameServerLink는 NPC 서버의 아웃바운드 포트다. 이름의 GameServer는 상대방이다.
  • N1~N8은 취향이 아니라 테스트로 강제되는 계약이다. 특히 N3은 프롬프트 인젝션을 타입 단계에서 막는다.
  • 명령은 유실된다고 가정한다. 모든 스텝에 timeout_s가 있고 응답이 없으면 로컬에서 실패를 합성한다.
  • 낡은 응답은 상관 ID 무효화로 걸러진다. 이게 없으면 플랜 스왑이 상태를 망친다.
  • TickSync에서 이벤트 배수를 끊는 것이 리플레이 100 % 일치의 조건이다.
  • 링크 구현체 5종이 코드 변경 0으로 교체된다 — P5 게이트 항목 4.
