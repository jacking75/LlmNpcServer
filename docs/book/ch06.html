6장 — 인지 LOD와 재계획 큐

5,000마리를 매 틱 전부 판정할 수는 없고, 재계획 예산은 그보다 훨씬 적다. 그래서 두 개의 깔때기가 있다 — 누구를 볼 것인가(인지 LOD)와 본 것 중 누구를 먼저 고칠 것인가(재계획 큐). 이 장은 그 두 깔때기의 상한과, 상한이 실제로 무엇을 자르는지를 본다.

2. 인지 LOD — 등급은 이벤트로만 바뀐다

스캔 안에서 거리를 계산하지 않는다 NPC 5,000 × 플레이어 20이면 틱당 10만 회 거리 계산이다. 그것만으로 20 ms 예산이 날아간다. 대신 게임서버가 이미 계산해서 보내주는 PlayerProximity 이벤트를 쓴다. 인지 LOD 설계 전체가 이 이벤트 하나에 얹혀 있다.
src/Npc.Runtime/LodUpdater.cs
public static byte GradeOf(int distance) => distance switch
{
    < 50  => 0,   // LodZeroDistance — 시야 내
    < 200 => 1,   // LodOneDistance  — 같은 존
    _        => 2,   // 원거리
};
등급이름주기언제 이 등급이 되나재계획 근접 항
0시야 내1틱플레이어 50 m 이내1.0
1동일 존10틱플레이어 200 m 이내 · 존이 War/Disaster0.5
2원거리100틱플레이어가 떠났는데 존이 활성일 때0.1
3비활성이벤트 시만플레이어가 떠나고 존도 평시. 초기값0.0
초기 등급이 0이 아니라 3인 이유 기동 직후 전원을 LOD 0으로 두면 5,000마리가 전부 매 틱 판정 대상이 되어 틱 예산이 통째로 날아간다. 플레이어가 다가와야 승격된다. 같은 이유로 플레이어가 떠나면 반드시 내려야 한다 — 안 내리면 한 번이라도 플레이어를 만난 NPC가 영원히 스캔 대상으로 남고, NPC를 늘릴수록 틱당 스캔이 선형으로 자라 O(1) 설계가 깨진다.

2.1 밴드와 슬라이스

src/Npc.Runtime/LodBand.cs — LodBandSet.SliceOf
public (int Start, int End) SliceOf(int lod, long tick)
{
    int period = Bands[band].Period, count = _counts[band];

    if (period <= 0 || count == 0) return (0, 0);   // 비활성 밴드
    if (period == 1) return (0, count);                // LOD 0 — 전원

    long slice = ((tick % period) + period) % period;
    return ((int)(count * slice / period), (int)(count * (slice + 1) / period));
}

밴드 멤버를 Period개의 슬라이스로 나누고 그중 하나만 본다. 그래서 그 밴드의 NPC 한 마리는 Period틱마다 정확히 한 번 판정된다.

문서의 근거가 틀렸던 이야기 docs/14 §6의 기대표는 인지 스캔을 O(1)로 적고 근거를 "슬라이스가 고정 비율이므로"라고 썼다. 그 논거는 성립하지 않는다 — 슬라이스는 밴드 인원을 Period로 나눈 것이고, 밴드 인원이 NPC 수와 함께 자란다. 월드(존·POI)가 고정이라 NPC를 늘리면 밀도가 올라가고, 한 플레이어 반경 안의 NPC가 그만큼 는다.

실제로 O(1)을 만드는 것은 MaxScansPerTick(150) 하나다. 설계는 맞았고 문서의 근거가 틀렸다 — docs/14 §6을 정정했다.
추정과 실측이 맞은 곳 docs/11 §4는 "상한이 없으면 612까지 간다"고 추정했고, 실측은 637이었다 — 4.1 % 차이.

2.3 밴드 이동 — 틱당 64건, swap-remove

private void Move(int npc, int from, int to)
{
    // swap-remove. 마지막 원소를 빈 자리로 당긴다 — O(1) 이고 순서가 결정론적이다.
    int slot = _slotOf[npc];
    int last = --_counts[from];
    int moved = _members[from][last];

    _members[from][slot] = moved;
    _slotOf[moved] = slot;

    _slotOf[npc] = _counts[to];
    _members[to][_counts[to]++] = npc;
    _bandOf[npc] = to;
}

PendingMigrations가 상시로 크면 등급이 바뀌는 속도가 옮기는 속도(틱당 64)를 넘는 것이다. 공성처럼 존 전체가 한꺼번에 승격되면 잠시 커지고, 그게 정상이다.

3. 재계획 점수 — 네 항의 가중합

src/Npc.Planning/ReplanScorer.cs
score = W1 × Proximity(lod)                    // 1.0 / 0.5 / 0.1 / 0.0
      + W2 × Staleness(assignedTick, now)      // StaleTicks(36,000) 에서 1.0 포화
      + W3 × Deviation(required, forbidden, cur) // PopCount(어긋난 비트) / 8
      + W4 × Urgency(pendingUrgency)           // interrupts.json 의 0~100 을 정규화
항정규화이 항이 잡는 것
근접 W1LOD 0/1/2/3 → 1.0 / 0.5 / 0.1 / 0.0 관측되지 않는 연산 문제의 해결책이 이 한 계수다. LOD 3은 0이라 인터럽트가 없는 한 사실상 재계획되지 않는다
노후 W2age / StaleTicks, 상한 1.0 같은 플랜을 너무 오래 들고 있는 NPC. 기본 36,000틱 = 배속 60에서 게임 6시간
이탈 W3PopCount(missing｜violated) / 8 플랜 전제가 얼마나 깨졌나. 8비트로 나누는 이유 — 42비트 전부로 나누면 실제 이탈(1~3비트)이 0.05 밑으로 깔려 항이 죽는다
긴급 W4urgency / 100 인터럽트가 NpcStore.PendingUrgency에 남긴 값. 새 플랜이 배정되면 0으로 소진된다

각 항이 [0, 1]이라 점수 상한은 W1+W2+W3+W4(기본 9.5)다. 인터럽트가 넣는 UrgentBase(1000)와 겹치지 않는 것이 설계다.

3.1 이탈 판정 자체는 비트 연산 두 번이다

// CompiledPlan — 틱당 최대 150회 도는 핫패스
public bool NeedsReplan(WorldFlags current) =>
    (RequiredFlags & ~current) != 0 || (ForbiddenFlags & current) != 0;

// ReplanScorer — 점수는 PopCount 한 번을 더한다
return MathF.Min(1f, BitOperations.PopCount(missing | violated) / 8f);
스텝을 순회하지 않는다 플랜 전체의 RequiredFlags·ForbiddenFlags는 컴파일 시점에 한 번 계산된다(4장 §4.1). 런타임에는 그 두 마스크만 본다. 스텝 10개를 순회하면 이 핫패스가 10배가 된다.

A/B가 세트를 가르지 못했다 — 그래서 기본값을 안 바꿨다 네 세트의 LLM 요청 수가 전부 1,686건으로 같다. T1 예산 상한(실측 0.195 req/s × 워커 2)이 정확히 묶은 값이고, 가중치는 거기에 관여하지 않는다. 남는 차이는 "그 1,686건을 누구에게 쓰는가"뿐인데, 같은 세트의 회차 간 변동(±2.6 %)이 세트 간 차이(0.9 %p)보다 크다.

이번 회차 1위는 D-uniform이었지만 1위를 기본값으로 올리면 잡음을 기본값으로 승격하는 것이라, Weights.Default는 사양의 기본값 B-baseline을 유지한다. WeightAbHarness.Choose는 1위가 2위를 회차 폭보다 크게 이겼을 때만 갈아탄다.

⚠ docs/14 §2의 설계 논거("W1을 크게 잡는 것이 핵심")는 반증되지 않았다. 지금 예산에서는 확인도 반증도 못 한다는 것이 이 회차의 결론이다. T1 처리량이 올라 큐가 포화를 벗어나면 다시 잰다 — 그때는 가중치가 "누구를 먼저"가 아니라 "몇 명을"까지 정하게 된다.

4. 재계획 큐 — 라운드로빈이 아니라 점수순

4.1 네 가지 방어

장치값없으면
중복 방지 — _heapPos[npc]-1 = 큐에 없음 같은 NPC가 수십 번 들어가 큐가 즉시 포화한다
용량 상한min(NPC 수, 4,096) 큐가 무한히 자라 이미 상황이 바뀐 NPC를 재계획하게 된다
최하위 축출포화 시 잎 노드 중 최솟값과 비교 새 요청이 무조건 거절되거나, 아무거나 버려 우선순위가 무의미해진다
인터럽트 슬롯 상한용량의 50 % (2,048칸) 공성 한 번에 큐 4,096칸이 통째로 인터럽트로 차고, 그때부터 이탈 판정과 스텝 실패는 처리되지 않는다
동점을 npc 첨자 오름차순으로 가르는 이유 힙 구조에 순서를 맡기면 같은 점수의 처리 순서가 삽입 이력에 따라 달라진다. 리플레이 100 % 일치가 W11 게이트인데, 그것부터 깨진다. 
private bool Precedes(int npc, float score, int other) =>
    score != _score[other] ? score > _score[other] : npc < other;

최하위를 찾을 때 잎만 훑는다

최대 힙에서 최솟값은 반드시 잎이다. 잎은 절반이라 용량 4,096이면 비교 2,048회다. 비싸 보이지만 포화 상태에서만 돈다 — 포화는 이미 예산이 모자란 퇴화 구간이고, 그때 "아무 잎이나" 버리면 사양의 최하위 축출이 성립하지 않아 급한 요청이 낮은 점수에 밀린다.

5. 틱 루프와 워커 사이 — 힙을 공유하지 않는다

실제로 났던 사고 ReplanQueue는 고정 크기 힙이고 동기화가 없다. 워커가 그 힙을 직접 꺼내 쓰면 틱 루프의 TryEnqueue와 경합한다 — 용량 검사와 삽입 사이 창에서 _count가 용량을 넘어 _heap[_count]가 범위를 벗어난다. 2026-07-28 실측: 8회 중 2회 IndexOutOfRangeException.

고치는 방법은 힙에 락을 거는 것이 아니다. 틱 루프의 lock은 금지돼 있고, 워커 8개가 다투는 락을 틱 루프가 같이 잡으면 그 순간 p99가 무너진다.

5.1 낡음 판정 — 왕복만 하고 진전이 없는 것을 막는다

문제

T1 지연이 실측 3.7~5.1초이고 10Hz 틱이니 한 요청이 대기+생성 사이에 37~51틱을 보낸다. 그 사이 밤이 되고 전투가 끝나고 존이 War로 바뀌면, 돌아온 플랜은 이미 존재하지 않는 상황의 것이다. 그것을 그대로 스왑하면 다음 인지 스캔이 즉시 이탈로 판정해 또 재계획을 요청한다 — LLM 예산이 왕복만 하고 아무 진전이 없다.

해법

큐에 넣을 때 플래그를 찍어 두고(ReplanSnapshots.Capture), 워커가 꺼낼 때 지금 플래그와 비교한다. 어긋난 비트가 MaxDrift(기본 4)를 넘으면 폐기하고 지금 상태로 재삽입한다.

폐기는 손실이 아니다 — 아직 LLM을 부르지 않았으므로 버리는 것은 낡은 컨텍스트뿐이다.

임계 4가 나온 근거 "평범한 진행"과 "상황 전환"을 가르는 선이다. NPC가 걸어서 POI를 옮기면 장소 플래그가 2비트(이전 해제 + 새로 설정), 시간대가 바뀌면 또 2비트. 그 둘이 겹친 정도까지는 같은 상황으로 본다. 5비트 이상은 전투·존 상태·인벤토리 중 무언가가 더 바뀐 것이다.

6장 요약
  • LOD 등급은 이벤트로만 바뀐다. 스캔 안에서 거리를 계산하면 그것만으로 예산이 날아간다.
  • 슬라이스만으로는 상한이 안 지켜진다. O(1)을 만드는 것은 MaxScansPerTick 하나다 — 문서의 원래 근거는 틀렸었다.
  • 점수는 근접 · 노후 · 이탈 · 긴급 네 항이고, LOD 3의 근접 항이 0이라 아무도 안 보는 NPC는 사실상 재계획되지 않는다.
  • 큐는 중복 방지 · 용량 상한 · 최하위 축출 · 인터럽트 50 % 상한 네 겹으로 방어한다.
  • 힙은 틱 루프만 만진다. 워커와는 ReplanHandoff 링 두 개로만 주고받는다.
  • 가중치 A/B는 세트를 가르지 못했다 — 지금은 예산이 병목이고, 그것을 정직하게 적어 두었다.
