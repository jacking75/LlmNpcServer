이 프로젝트에서 액션·플래그·아키타입을 코드에 하드코딩하지 않는다는 규칙은 취향이 아니다. LLM 프롬프트의 본문이 이 JSON에서 생성되고, 검증기의 판정 기준도 여기서 나오며, 런타임의 비트 연산도 여기서 정한 비트 번호 위에서 돈다. 코드와 데이터가 갈라지면 세 곳이 한꺼번에 어긋난다.

2.1 작업 순서 — 역순이면 계속 되돌아온다

3. 월드 플래그 — 64비트 위의 세계관

NPC의 상태는 ulong 한 개다. 플랜의 전제조건, 액션의 효과, 인지 스캔의 이탈 판정, 검증기 3단의 GOAP 시뮬 — 전부 이 64비트 위에서 돈다. class NpcState가 아니라 비트인 이유는 판정이 비트 연산 한 번으로 끝나야 하기 때문이다.

masterdata/world_flags.json → src/Npc.Core/WorldFlags.g.cs (소스 생성기)
// 이 파일에서 enum 이 생성된다. 손으로 쓴 enum 을 두지 않는다.
{ "bit": 0,  "id": "AtHome",         "group": "location"  }
{ "bit": 11, "id": "HasRawMaterial", "group": "inventory" }
{ "bit": 31, "id": "OnDuty",         "group": "social"    }
{ "bit": 40, "id": "ThreatNearby",   "group": "threat"    }

"reserved_bits": [22, 23, 44…63]   // 추가는 여기에만
"exclusive_groups": [{ "id": "time", "flags": ["IsDawn","IsDay","IsEvening","IsNight"] }]

3.1 직접 만져보기 — 플래그가 액션 가능 여부를 어떻게 정하나

src/Npc.Core/Plan/CompiledPlan.cs
public bool IsSatisfiedBy(WorldFlags state) =>
    (Requires & ~state) == 0                                        // 전부 서 있나 (AND)
    && (RequiresAny == WorldFlags.None || (RequiresAny & state) != 0) // 하나라도 (OR)
    && (Forbids & state) == 0;                                     // 금지가 서 있나
이 세 줄이 왜 중요한가 인지 스캔은 틱당 최대 150회 돌고, 여기에 스텝 순회가 들어가면 그것만으로 예산이 날아간다. 그래서 CompiledPlan은 플랜 전체의 RequiredFlags·ForbiddenFlags를 컴파일 시점에 한 번 OR 해두고, 런타임에는 NeedsReplan(current) 비교 두 번으로 끝낸다. 자세한 것은 6장.

4. 액션 카탈로그 — LLM이 조합할 수 있는 유일한 원자

액션은 37개이고 상한은 40이다. 새 액션을 추가하려면 하나를 빼거나 기존 액션의 파라미터로 흡수해야 한다. 이유는 프롬프트 프리픽스에 이 카탈로그가 통째로 실리기 때문이다 — 액션 하나가 대략 150~200 토큰이다.

masterdata/actions.json — MoveTo 전문
{
  "id": "MoveTo",
  "code": 1,                          // ActionCatalog 배열 첨자. 재배치 금지
  "category": "movement",
  "desc": "지정한 POI 로 이동한다. 경로 계산과 충돌 처리는 게임서버가 …",   // 프롬프트에 그대로 실린다
  "params": {
    "poi":   { "type": "poi_ref", "required": true },
    "speed": { "type": "enum", "values": ["walk","run"], "default": "walk" }
  },
  "requires": [],                                       // AND — 전부 성립해야
  "requires_any": [],                                   // OR — 하나 이상
  "forbids": ["IsSleeping", "IsExhausted"],           // 하나라도 서면 불가
  "grants": [],                                         // 완료 후 세우는 플래그
  "clears": ["AtHome","AtWorkplace","AtMarket",…],       // 완료 후 내리는 플래그
  "duration": { "kind": "distance", "per_meter_s": 0.6 },
  "cost": 2,
  "default_timeout_s": 300,                            // 스텝이 timeout_s 를 생략하면 이 값
    "emits": [{ "command": "MoveTo", "priority": "Normal",
              "map": { "TargetPoi": "$poi", "Flags": "$speed" } }],
  "completes_on": ["NpcArrived"],                       // 이 이벤트가 오면 스텝 완료
  "fails_on": ["NpcActionFailed"]
}

4.1 emits — 액션이 명령으로 번역되는 자리

CommandEmitter에는 액션 이름이 하나도 없다. 위 emits를 읽어서 필드를 채울 뿐이다. 덕분에 새 액션을 추가할 때 런타임 코드를 고칠 필요가 없다.

map 값 문법어디서 오나예
"$param"플랜 스텝의 args"$poi" → 스텝이 지정한 POI 심볼
"$home" "$workplace" "$self" "$zone"NPC 인스턴스npc_instances.json의 그 NPC 행
"$first:Flag"그 플래그를 세우는 첫 인벤토리 아이템Eat → $first:HasFood = 빵
그 외 문자열아이템 id / 열거값 리터럴"Walking" → VisualState.Walking
숫자정수 리터럴 (부호 있음)-1 → Amount
$first:HasFood 가 있는 이유 "빵을 먹으면 배가 부르다"를 코드가 알면 안 된다. 코드가 아는 것은 "HasFood를 세우는 아이템 중 인벤토리에 있는 첫 번째"라는 규칙뿐이고, 어떤 아이템이 그 플래그를 세우는지는 items.json의 grants가 정한다. 치즈를 추가하고 grants: ["HasFood"]만 적으면 Eat이 그대로 치즈를 먹는다.

5. 아키타입 40종 — 버킷 키의 최상위 자리

masterdata/archetypes.json — blacksmith
{
  "id": "blacksmith", "code": 0,          // 0..39 — 버킷 인덱스가 0..2879 전단사이려면 0부터여야 한다
  "desc": "마을의 대장장이. 광석을 제련해 …",  // 프롬프트에 그대로 실린다
  "allowed_actions": ["Craft","Drink","Eat", … "Work"],   // 22개. V2.ACTION_NOT_ALLOWED 의 기준
  "home_poi_type": "home",
  "workplace_poi_type": "smithy",             // $workplace 가 바인딩될 POI 종류. null 이면 일터 없음
  "primary_recipes": ["iron_sword","iron_tool","horseshoe"],
  "traits": { "diligence": 80, "sociability": 40, "courage": 55, "greed": 50 },
  "default_goals": ["restock_ore","fulfill_orders","maintain_shop"],
  "initial_inventory": [{"item":"smith_hammer","count":1}, …],
  "fallback_plan": "fb_blacksmith",               // V7 — 없으면 기동 실패
  "combat_capable": true,                        // 인터럽트 규칙이 본다
  "population_weight": 0.012                     // 40종 합 = 1.0 (V5)
}

traits는 장식이 아니다

인터럽트 규칙이 courage < 40 같은 비교로 이 값을 본다. 겁 많은 아키타입은 위협에 Flee, 용감하면 Attack, 둘 다 아니면 Retreat로 갈린다. 같은 이벤트에 아키타입마다 다르게 반응하는 것이 시나리오 B 게이트 항목 하나다.

allowed_actions는 두 곳에 실린다

프리픽스의 ARCHETYPES 표에 한 번, 서픽스에도 한 번 더 싣는다. 프리픽스 표만으로는 모델이 자기 행을 안정적으로 못 찾아 V2.ACTION_NOT_ALLOWED가 최다 실패 원인이었기 때문이다(T2-21 실측). 서픽스가 약 80토큰 늘지만 300 예산 안이다.

6. 버킷 — 상황을 2,880칸으로 이산화한다

플랜 캐시의 키다. BucketKey는 전단사 정수 인덱스를 갖기 때문에 플랜 스토어가 해시맵이 아니라 2,880칸 고정 배열일 수 있다.

6.1 2,880칸 중 실제로 쓰이는 것은 264칸이다

bucket_usage.md가 마스터데이터에서 도달 가능 집합을 전수 계산한 결과다. 표본이 아니다.

축전체시나리오 A 도달왜
아키타입40405,000마리가 40종을 다 채운다
시간대66하루를 살면 다 거친다
지역상태42어느 존의 기본값에도 War·Disaster 가 없다
기후32기본값에 Storm 이 없다
곱하면 960일 것 같지만 실제는264아키타입과 존이 묶여 있다 — 광부는 광산에만 산다
이 발견이 만든 것 전량 2,880을 만들면 $5.12 · 19분이다. 도달 집합 264만 만들면 $0.37 · 97초인데 시나리오 A 캐시 히트율이 76.08 % → 98.67 %로 오히려 올랐다. 개수가 아니라 어느 버킷이냐가 히트율을 정한다. 자세한 것은 9장.

7. 나머지 파일들 — 짧게

7.1 items.json — grants가 전부다

{ "id": "iron_ore", "code": 1, "category": "raw",
  "grants": ["HasRawMaterial"], "stack": 50 }

인벤토리 변경 이벤트가 오면 EventApplier.RecomputeItemFlags가 인벤토리 전체를 훑어 grants를 OR 한다. code 구간은 의미가 있다 — 1~19 원자재 / 20~39·81~82 완제품 / 40~59 식음료 / 60~78·80 도구·무기 / 79 화폐.

7.2 pois.json · zones.json — 세계의 지형

필드쓰는 곳
grants도착하면 서는 장소 플래그. EventApplier.MoveTo가 장소 플래그를 통째로 지우고 이 값으로 바꾼다
capacity정원. gen_npcs가 이 값을 넘지 않게 배치한다 (V10)
allowed_archetypes비어 있으면 제한 없음. V3.UNREACHABLE_POI의 기준
adjacent (zones)대칭이어야 하고 그래프가 연결돼야 한다 (V11)
default_region_state · default_climate도달 버킷 264를 결정하는 값. 여기 War 를 넣으면 도달 집합이 확 는다

POI 좌표는 존 중심 기준 황금각 나선 위의 결정론적 배치다 — 난수를 쓰지 않았다. 같은 이유로 poi_distances.bin도 생성물이며 tools/gen_poi_distances.cs가 만든다.

7.3 interrupts.json — LLM이 만들지 않는 유일한 행동 규칙

{
  "id": "flee_on_threat", "priority": 100,
  "when": { "any_flag": ["ThreatNearby","InCombat"],
             "archetype_trait": { "courage": "<40" } },
  "then": { "action": "Flee", "params": { "poi": "$nearest_safe" } },
  "replan": { "urgency": 100 }
}
순서가 정해져 있다 먼저 도망치고, 새 계획은 나중에 받는다. then은 그 틱에 즉시 명령으로 나가고, replan.urgency는 재계획 큐에 1000 + urgency 점수로 들어간다. LLM은 이 경로에 끼어들지 않는다 — 반응 속도가 필요한 판단은 항상 규칙이다(CLAUDE.md §8).

7.4 fallback_plans.json — 마지막 보루 40개

규칙이유
전부 loop: true폴백은 무한히 지속 가능해야 한다
on_step_fail: skip폴백에서 또 폴백으로 가면 갈 곳이 없다
Guard·Patrol을 쓰지 않는다둘 다 OnDuty를 요구하는데 폴백은 근무 배정 없이도 돌아야 한다
V7 — 기동 시 40개 전부가 검증기 4단을 통과해야 한다이게 보장되지 않으면 시나리오 C가 성립하지 않는다

7.5 prompt/ — 손으로 편집하지 않는 부분

system_rules.md와 fewshot/*.json은 사람이 쓴다. 하지만 액션 카탈로그 절은 actions.json에서 생성된다(CatalogRenderer). few-shot 파일은 파일명 정렬 순서로 실린다 — 디렉터리 순회 순서에 의존하면 기계마다 프리픽스 SHA가 갈린다.

7.6 npc_instances.json — 5,000줄의 인구

tools/gen_npcs.cs(파일 기반 .NET 앱)가 population_weight와 POI 정원을 보고 배치한다. 이 파일이 월드 인구를 5,000으로 못 박는다 — P4 게이트에서 10,000 부하를 호스트로 재지 못한 이유가 이것이고 (NpcHost.Create가 Math.Min으로 자른다), pois.json 총 정원 자체가 9,238이라 늘리려면 마스터데이터를 먼저 바꿔야 한다.

#검사이걸 어기면
V1파일 내 code 유일성배열 첨자가 겹쳐 엉뚱한 액션이 실행된다
V2flag id 참조가 world_flags.json에 존재오타 하나가 "전제조건 없음"으로 조용히 읽힌다
V3poi/item/zone/action 참조가 실재런타임에서 0번 POI(=없음)로 바인딩된다
V4allowed_actions가 전부 카탈로그에 있음프롬프트에 없는 액션 이름이 실린다
V5population_weight 합 = 1.0 (±0.001)인구 배치가 5,000에 못 미치거나 넘친다
V6total_keys == 실제 조합 수 (아키타입 수 × 72)선언과 실제가 어긋난 채로 남는다. 코드는 이 값을 읽지 않는다 — 배열 길이는 아키타입 수가 정한다
V7모든 아키타입에 폴백이 있고 4단을 통과시나리오 C에서 NPC가 멈춘다
V8폴백이 그 아키타입의 allowed_actions만으로 구성됨폴백 자체가 V2를 어긴다
V9프롬프트 프리픽스 ≥ 4,096 토큰프롬프트 캐시가 아예 안 걸린다 (제공사 최소 임계)
V10POI 정원 총합 ≥ 그 아키타입 인구gen_npcs가 배치 도중 멈춘다
V11모든 POI가 존 그래프에서 도달 가능고립 POI로 이동 명령이 나가고 영원히 타임아웃
V12duty_hours 없이 OnDuty 요구 액션(Guard·Patrol)을 허용하지 않음그 액션의 전제조건이 영원히 충족되지 않아 인지 스캔이 매 틱 이탈로 읽고 재계획 큐가 포화된다
V13npc_instances.json 의 참조 · id 중복 · 개체 단위 정원없는 POI 를 가리키는 NPC 가 그 NPC 가 움직일 때 터진다 — 5,000마리 중 하나면 며칠 뒤에야 발견된다
경고 후 진행을 허용하지 않는다 V1~V13 실패는 기동 실패다. "경고만 하고 뜨게 하자"는 유혹이 반드시 오는데, 이 검사들이 잡는 것은 전부 증상이 한참 뒤에, 엉뚱한 곳에서 나타나는 종류다 — V2 오타는 "왜 이 NPC만 이상하게 움직이지"로, V11 고립 POI는 "왜 타임아웃이 많지"로 나타난다.

V13 은 파일이 없으면 건너뛴다. 마스터데이터 검증은 validate 만 돌려도 성립해야 하고, 인스턴스 생성은 그다음 단계다 — 없는 것을 실패로 세면 순서를 강요하게 된다.
코드만 내지 않는다

검증이 실패하면 V5 같은 코드가 나온다. 그 코드를 받은 LLM 은 무엇을 고쳐야 하는지 모른다 — 사람은 소스를 열어 보지만 LLM 은 그럴 수 없고, 그러면 온보딩 자동화가 거기서 멈춘다.

그래서 검증 코드 41건 전부에 "무엇을 하면 되는가" 를 붙였다 (Validation/FixHints.cs). 텍스트 출력은 힌트를 한 줄 덧붙이고, --json 은 위반마다 file·path·fix_hint· related 를 싣는다. 사전 문서(docs/llm/VALIDATION.md)는 생성물이다 — 두 벌 관리하면 반드시 어긋나고, 어긋난 문서는 없는 것보다 나쁘다.

8.1 생성물은 낡는다 — derived.lock.json

poi_distances.bin 과 npc_instances.json 은 생성물이다. 입력이 바뀌었는데 다시 만들지 않으면 서버는 낡은 거리표로 조용히 돈다 — 검증도 통과하고 기동도 되지만 NPC 가 존재하지 않는 POI 로 걸어간다. 그 오류는 재현하기도 어렵다.

masterdata/derived.lock.json
{
  "artifacts": {
    "npc_instances.json": {
      "generator": "tools/gen_npcs.cs",
      "inputs": { "archetypes.json": "<sha256>", "pois.json": "…", "zones.json": "…" }
    },
    "poi_distances.bin": { "generator": "tools/gen_poi_distances.cs", "inputs": { … } }
  }
}

생성기가 쓰고 로더가 읽는다. 기록이 없으면 낡은 것으로 본다 — 무엇으로 만들었는지 모르는 파일을 최신이라 부를 근거가 없다. 판정은 MasterDataSet.StaleArtifacts 에 실려 호스트 기동 로그와 validate 출력에 WARN 으로 나온다.

왜 기동 실패가 아닌가 낡은 거리표로도 개발 중에는 돌려 봐야 한다. 검증 규칙 위반과 달리 이것은 "틀렸다" 가 아니라 "다시 만들어야 한다" 는 사실이고, 지금 만들지 말지는 사람이 정한다. 대신 조용히 넘기지 않는다 — npc regen --check 는 낡았으면 비0 으로 끝나므로 파이프라인에 걸 수 있다.

9. 무엇을 고치면 무엇이 무효화되나

이 표가 이 장에서 실무적으로 가장 자주 볼 부분이다. 무효화 범위 판정은 PlanStoreValidator.Compare가 하고, 호스트가 기동할 때 경고로 알려준다.

고친 것무효화 범위해야 하는 일프롬프트 SHA
world_flags.json 비트 추가 (예약 구간) Partial 영향받는 액션의 버킷만 재생성 바뀐다 → 전량 무효
world_flags.json 비트 재배치 Full 플랜 2,880개 전량 재생성. 하지 말 것 바뀐다
actions.json 액션 추가 / desc 수정 Full 프리픽스가 바뀌므로 전량 바뀐다
actions.json emits·default_timeout_s만 수정 None 재생성 불필요. 런타임 동작만 바뀐다 바뀐다(카탈로그에 실림) — 확인 필요
archetypes.json allowed_actions 수정 Full 그 아키타입 72버킷 + 프리픽스 전량 바뀐다
archetypes.json population_weight만 None gen_npcs 재실행 → npc_instances.json. 재배분 3안은 npc scaffold 가 낸다 안 바뀐다
pois.json POI 1개 추가 Partial 거리 행렬 재생성 + 그 존 관련 버킷. npc regen --check 가 낡음을 잡는다 안 바뀐다
zones.json default_region_state 변경 Partial 도달 버킷 집합이 바뀐다 — 새 조합을 프리베이크 안 바뀐다
interrupts.json 규칙 추가 None 재기동만. 즉시 반영 안 바뀐다
prompt/system_rules.md 한 글자 Full 프롬프트 캐시가 전면 미적중이 된다 바뀐다
fallback_plans.json 수정 None V7·V8 재검증만. 즉시 반영 안 바뀐다

이 표를 손으로 보지 않아도 된다

같은 판정을 ImpactAnalyzer 가 한다 (Npc.MasterData/Authoring/). 바뀐 파일 목록을 주면 무효화 범위 · 프리픽스 변경 여부 · 구조 해시 변경(게임서버 재배포) · 재생성해야 할 파생물을 한 번에 낸다. PlanStoreValidator 와 같은 답이어야 하고 테스트가 그것을 강제한다 — 두 곳이 다른 답을 내면 어느 쪽을 믿고 프리베이크를 돌릴지 알 수 없다. 

> npc diff
masterdata 변경 (base: HEAD)

  archetypes.json

구조 해시  변경 → 게임서버 재배포 필요 (핸드셰이크 거절)
프리픽스   변경 → 플랜 스토어 전량 무효 → 프리베이크 필요
플랜       전량 무효 → 전량 재생성
파생물     npc_instances.json 낡음 → `npc regen`

무효화됐는지 어떻게 아나

호스트가 기동할 때 manifest.json과 지금 마스터데이터를 비교해 알려준다.

// src/Npc.Host/Program.cs — WarnIfStale
warn: 플랜 스토어가 낡았다 — 무효화 Full (바뀐 것: prompt_sha, actions)
      tools/Npc.Prebake 로 재생성한다.

기동을 막지는 않는다. 낡은 플랜이라도 폴백보다는 나은 경우가 있고, 재생성 판단은 사람이 할 일이기 때문이다.

2장 요약
  • 액션·플래그·아키타입은 코드가 아니라 masterdata/가 정한다. 같은 사실이 프롬프트·검증기·런타임 세 곳에서 쓰이기 때문이다.
  • 상태는 64비트 플래그 하나다. 그래서 이탈 판정이 비트 연산 한 번이다.
  • code·bit 재배치는 프리베이크된 플랜 2,880개를 조용히 깬다. 추가는 뒤에만.
  • 버킷 2,880 중 실제로 조회되는 것은 264다 — 존 배치가 아키타입을 묶기 때문이다.
  • V1~V13 실패는 기동 실패다. 무효화 범위 표(§9)를 보고 재생성 여부를 정한다.
