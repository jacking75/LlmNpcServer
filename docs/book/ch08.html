8장 — 프롬프트와 LLM 컴파일러

이 층의 설계는 한 가지 사실 위에 서 있다 — 프리픽스는 캐시되고 서픽스는 매번 prefill 된다. 그래서 프리픽스는 13,488토큰이어도 되고, 서픽스는 300토큰을 넘으면 안 된다. 이 장은 그 비대칭이 만든 모든 결정을 따라간다.

2.1 결정론 — SHA가 흔들리면 캐시가 전면 미적중이다

흔들릴 수 있는 곳어떻게 막았나
파일이 CRLF로 체크아웃된 기계 Normalize()가 절마다 CR을 걷어낸다. ReadText만으로는 부족했다 — RenderDsl의 raw string literal이 .cs 소스의 줄 끝을 그대로 들고 나온다
few-shot 파일 순서 파일명 Ordinal 정렬. 디렉터리 순회 순서에 의존하면 기계마다 SHA가 갈린다
아키타입 액션 순서 archetypes.json 등장 순서 그대로. 정렬하면 파일과 어긋난다
플래그·액션·레시피 열거 전부 code 순서 또는 이름 순서로만 돈다 (CatalogRenderer)
엔진별 꼬리표 (Qwen3의 /no_think) 서픽스 끝에만 붙인다 (SuffixTag). 프리픽스는 절대 건드리지 않는다
유니크 프리픽스 SHA가 2개 이상 = 즉시 경보 /metrics의 uniquePrefixHashes가 1이 아니면 프롬프트 캐시가 깨진 것이다. 실제로 288버킷 파일럿 회차에서 이 값은 1종이었다 — 캐시가 깨지지 않았다는 뜻이다.

3.1 예산은 테스트가 아니라 조립기가 지킨다

중요한 구분 Suffix_NeverExceeds300Tokens 테스트만 있으면, 실제로 넘치는 입력이 들어왔을 때 그대로 나간다. 그래서 Build()가 예산을 넘기면 우선순위대로 덜어낸다. 테스트는 그 조립기가 실제로 동작하는지를 볼 뿐이다.
단계빼는 것왜 이 순서
0전부 싣는다—
1recent재시도 블록이 더 구체적이다
2last_plan_outcome결과보다 지금 상태가 중요하다
3인벤토리 8종 → 4종code 오름차순이라 원자재가 먼저 남는다
4인벤토리 제거 + 실패 설명 절반인벤토리는 플래그로도 어느 정도 드러난다
5성향 · 목표최후다 — 이 단계에서는 "무엇이 유효한가"가 "어떤 성격인가"를 이긴다

3.2 재시도 피드백은 서픽스에만 붙는다

# PREVIOUS ATTEMPT REJECTED

{"previous_attempt_failed":{"stage":"Coherence","code":"V3.PRECONDITION_UNMET",
  "step":3,"detail":"Craft requires HasRawMaterial but no preceding step grants it. …"}}

Fix exactly that and output the corrected plan. JSON only.
블록을 새로 만들지 않는다 검증기가 만든 문자열을 그대로 붙인다(CoherenceValidator.Explain). 다만 detail 길이만 180자로 자른다 — 안 자르면 재시도 서픽스가 예산의 두 배를 넘긴다(T2-07 실측 665토큰). 자를 수 있는 이유는 핵심(액션 이름·모자란 플래그·스텝 번호)이 문장 앞쪽에 있어서다.

5.1 강제 디코딩을 기본으로 켜지 않는 이유

W1(T0-09) 실측 response_format=json_schema는 유효 JSON 99/100을 내면서 어휘 검증 통과 0/100이었다. 실패 코드는 전부 V2.UNKNOWN_ARG — 문법을 지키면서 인자를 지어낸다.

그래서 스키마는 프롬프트에 실리는 문서가 주 용도이고, response_format으로 강제할지는 엔진별 설정으로 뺐다.
스키마에서 뺀 것W1 실패 건수대신 잡는 곳
minItems/maxItems7건V1.STEP_COUNT
additionalProperties: false1건V1.EXTRA_FIELD
required1건V2.MISSING_REQUIRED_ARG
maximum/minimum1건V2.RANGE
pattern제공사별 지원 편차V1.SCHEMA가 goal 정규식을 본다
oneOf/anyOf—액션 37종 분기는 강제 디코딩 FSM을 폭발시킨다

스키마를 강제할수록 나빠졌다는 것이 이 표의 요약이다. 다만 args는 전 액션 파라미터의 평탄화 합집합을 싣는다(SchemaProfile.Full) — properties 없는 object로 두면 강제 디코딩이 매 스텝 args: {}만 뱉는다.

  2. 서픽스의 allowed_actions — 프리픽스 표만으로는 모델이 자기 행을 안정적으로 못 찾았다. V2.ACTION_NOT_ALLOWED가 최다 실패였다

7.1 프롬프트 캐시 적중률 95 %는 왜 도달 불가인가

회차적중률비고

우리 쪽 조건은 지켜졌다 — 프리픽스 SHA는 1종이다. 원인은 제공사 쪽이다.

암시적 캐싱의 성질 Gemini의 암시적 캐싱은 요청 단위로 전부 적중하거나 전부 미적중이고 그 판정이 비결정적이다 — cached_tokens 값이 프리픽스 크기의 정수배로만 나온다. 하한 95 %는 명시적 캐싱(Anthropic cache_control 블록)을 전제한 값이라 이 엔진 계열에서는 도달할 수 없다. 기준에 엔진 계열을 명시해야 한다는 것이 P3 게이트의 결론이었다.
8장 요약
  • 프리픽스는 캐시되고 서픽스는 매번 prefill 된다 — 이 비대칭이 모든 결정의 근거다.
  • 프리픽스 13,488토큰은 다섯 절이고 세 절이 마스터데이터에서 생성된다. SHA가 흔들리면 캐시가 전면 미적중이다.
  • 서픽스 300토큰 예산은 테스트가 아니라 조립기가 지킨다 — 넘치면 5단계로 덜어낸다.
  • 강제 디코딩을 신뢰하지 않는다. 유효 JSON 99 %에 어휘 통과 0 %였던 실측이 근거다.
  • 재시도는 1회. 두 번 실패하면 인접 버킷 재사용 → 아키타입 폴백으로 반드시 플랜이 나온다.
  • 비용 추정이 5.4배 빗나간 원인은 프리픽스 크기를 축소판으로 추정한 것 하나다.
