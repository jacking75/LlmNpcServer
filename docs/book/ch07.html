7장 — 플랜 실행 · 인터럽트 · 전환

플랜은 JSON이지만 실행은 여섯 개 상태를 가진 작은 상태 기계다. 이 장은 그 상태 기계와, 그것을 바깥에서 흔드는 두 힘 — 인터럽트(즉시)와 버킷 전환(예약) — 이 어떻게 충돌 없이 공존하는지를 본다.

1. 스텝 상태 기계

src/Npc.Runtime/PlanExecutor.cs — Step
for (int i = 0; i < _store.Count; i++)      // SoA 순회. await 도 LINQ 도 없다
{
    switch ((StepStatus)_store.StepStatus[i])
    {
        case StepStatus.Unspawned:
        case StepStatus.Done:      continue;                 // 아무것도 안 한다

        case StepStatus.Waiting:
            if (!SynthesizeTimeout(i, tick)) continue;      // 아직 기다린다
            ApplyFailPolicy(i);                            // 타임아웃 → 실패 정책
            break;

        case StepStatus.Completed: AdvanceStep(i);    break;
        case StepStatus.Failed:    ApplyFailPolicy(i); break;
        case StepStatus.Ready:
        default: break;
    }

    if ((StepStatus)_store.StepStatus[i] == StepStatus.Ready)
        Emit(i, tick, link);                               // 같은 틱에 바로 발행한다
}
상태 전이와 발행이 같은 틱에 일어난다 Completed → AdvanceStep → Ready → 같은 루프 반복 안에서 Emit. 이렇게 하지 않으면 스텝 하나 전진할 때마다 한 틱(100 ms)씩 손해를 본다.

2. 스텝 전진과 실패 정책

2.1 AdvanceStep — 스왑이 일어나는 유일한 자리

private void AdvanceStep(int npc)
{
    _store.StepRetries[npc] = 0;
    StepsAdvanced++;

        // ★ 스텝 경계다. 워커가 걸어둔 새 플랜이 있으면 여기서 갈아끼운다.
    if (Swapper is not null && Swapper.TryTake(npc, out PlanId swapped))
    {
        AssignPlan(npc, swapped);
        return;
    }

    CompiledPlan plan = PlanOf(npc);
    int next = _store.StepIndex[npc] + 1;

    if (next < plan.Steps.Length) { _store.StepIndex[npc] = (byte)next; …Ready; return; }
    if (plan.Loop)              { _store.StepIndex[npc] = 0;             …Ready; return; }

    _store.StepIndex[npc] = (byte)(plan.Steps.Length - 1);
    _store.StepStatus[npc] = (byte)StepStatus.Done;
}

2.2 실패 정책 네 가지가 실제로 하는 일

on_step_fail코드가 하는 일결과
retry_once StepRetries == 0이면 1로 올리고 Ready로 같은 명령이 한 번 더 나간다. 두 번째 실패는 fallback으로 떨어진다
replan 큐에 점수 50으로 넣고 AdvanceStep 다음 스텝은 진행하되 새 플랜을 요청한다. 멈추지 않는다
skip AdvanceStep만 실패한 스텝을 건너뛴다. 폴백 플랜의 정책
fallback 기본 SwitchToFallback — 아키타입 폴백으로 AssignPlan 플랜을 통째로 바꾼다. FallbacksTaken++

2.3 PlanOf — 회수된 개별 플랜에서 빠져나오기

private CompiledPlan PlanOf(int npc)
{
    if (_plans.TryFor(npc, _store.PlanId[npc], _tick, out CompiledPlan plan))
        return plan;

    SwitchToFallback(npc);          // ★ 되돌리는 것이 이 메서드의 요점
    return _plans[_store.PlanId[npc]];
}
이게 없으면 NPC가 최후 플랜에 갇힌다 개별 플랜은 512칸 링이라 LRU로 회수된다(9장). 예전 주인이 회수된 슬롯을 계속 읽으면 TryFor가 최후 플랜(Wait·Emote·Rest)을 돌려주는데, 그 상태로 두면 그 NPC는 영원히 대기만 한다. 그래서 false를 받은 순간 아키타입 폴백으로 되돌린다.

플랜 스토어가 이 판단을 못 하는 이유는 스토어가 NPC의 아키타입을 모르기 때문이다 — 그것은 NpcStore(런타임)에 있고, Npc.Planning은 Npc.Runtime을 참조하지 않는다.

3. 명령 발행 — 액션 이름이 없는 코드

src/Npc.Runtime/CommandEmitter.cs
public int Emit(in CompiledStep step, in EmitContext ctx,
                ReadOnlySpan<int> inventory, Span<NpcCommand> destination)
{
    ActionDef action = _data.Actions[step.Action];       // actions.json 이 정한다
    _binder.TryBind(step.Poi, bindContext, out PoiId boundPoi);

    foreach (EmitDef emit in action.Emits)              // 액션 이름이 여기 없다
    {
        var command = new NpcCommand { Kind = emit.Command, … };
        foreach (EmitMapping m in emit.Map)
            command = Apply(command, m, step, ctx, boundPoi, inventory);
        destination[written++] = command;
    }
    return written;
}

IEnumerable을 반환하지 않는다

호출자가 준 Span<NpcCommand>에 쓴다. 실행기는 _batch = new NpcCommand[MaxCommandsPerStep]을 기동 시 한 번 잡아두고 재사용한다. 한 스텝이 낼 수 있는 명령은 최대 4개다.

새 액션을 추가해도 이 파일을 안 고친다

actions.json에 emits를 적으면 끝이다. "Mine이면 이런 명령을 낸다"는 지식이 코드에 없기 때문이다 — 13장 확장 레시피 참조.

3.1 POI 바인딩 — 같은 곳에 몰리지 않게

가장 가까운 하나를 그대로 고르면 같은 버킷의 NPC 수백 마리가 전부 같은 POI로 몰린다. 대장장이 60명이 전부 같은 시장 좌판 앞에 서 있는 그림이 된다.

// 난수가 아니라 해시라서 리플레이가 일치한다.

4. 인터럽트 — 즉시 반응, 계획은 나중

인터럽트는 LLM이 개입하지 않는 유일한 행동 경로다. 반응 속도가 생명이라 결정론 규칙으로만 돈다.

4.1 존 이벤트는 따로 훑는다

src/Npc.Runtime/NpcServerLoop.cs — DrainEvents
if (ev.Kind is GameEventKind.ZoneStateChanged or GameEventKind.WeatherChanged)
    _interrupts.HandleZone(in ev, …);   // 그 존 전원을 평가
else
    _interrupts.Handle(in ev, …);       // ev.Npc 한 마리만
왜 갈랐나 ZoneStateChanged는 NPC를 지목하지 않는다(ev.Npc = 0). Handle 하나로는 0번 NPC만 평가된다 — 존 전체가 RegionUnderAttack을 받았는데 반응은 한 마리만 하는 셈이다. O(N)이지만 존 상태 변화는 드물고(공성 한 번에 몇 발), 이 한 틱의 비용이 곧 "1틱 내 즉시 반응"의 값이다.

6. 버킷 전환 — 5,000마리가 동시에 갈아타지 않게

시간대가 바뀌면 전원이 새 버킷의 플랜으로 갈아타야 한다. LLM 호출이 아니라 순수 배열 쓰기지만, 5,000회를 한 틱에 하면 스파이크다.

6.1 폭이 계기마다 다른 이유

계기대상지터 폭실시간 창왜
GameClock.TimeOfDayChanged전원±300틱60초 5,000마리가 갈아타는 정기 전환. 넓게 흩어야 스파이크가 없다
ZoneStateChanged그 존만±14틱2.9초 docs/14 §7이 공성에서 "3초 내 마을 전체 스왑 완료"를 요구한다. 같은 폭으로는 두 요구가 양립하지 않는다
WeatherChanged그 존만±14틱2.9초

존 인원 500마리 기준 틱당 약 17건이고, 그 정도는 스파이크가 아니다. 존 이벤트에서 전원을 다시 세지 않는다 — 공성 한 번에 존 이벤트가 여러 발 오는데 매번 5,000마리를 훑으면 완화하려던 스파이크가 그대로 돌아온다.

6.2 예약 자료구조 — 할당 0

평시 비용이 거의 0이다

전환이 없으면 Apply는 _pending == 0 검사 하나로 끝난다. 틱 루프가 매 틱 부르지만 부담이 없는 이유다.

이벤트 예약의 기준 틱은 "다음 틱"이다 Observe는 DrainEvents에서 불리고, 그 뒤에 시계가 한 틱 나아가 Apply가 처음 돈다. 지금 틱으로 예약하면 지터가 최솟값(−spread)인 NPC의 예약 시각이 이미 지나간 틱이 되어 다음 한 바퀴(601틱)까지 처리되지 않는다.

P1에 있던 실제 버그 플래그에서 추정하는 경로는 Alert·Disaster를 낼 수 없다 — 플래그가 Peace·War와 같기 때문이다. P1은 이 추정만 갖고 있었고, ordinal 내림차순으로 골라 평시 NPC 전원을 Alert로 판정하고 있었다. 프리베이크는 Peace를 먼저 채우므로, 채워둔 버킷을 아무도 조회하지 않는 상태였다. ZoneStateTable을 붙여 고쳤다.

이 테스트들은 스토어에 따라 결과가 달라진다 도달 집합 A(195버킷)로만 채웠을 때 두 테스트가 "War인데 아무 플랜도 갈아타지 않았다"로 멈췄다 — A는 평시(Peace·Alert)만 덮으므로 War 버킷이 스토어에 없고, 전환할 대상이 없으니 갈아타지 않는다. 항목 2(평시 히트율)와 항목 6(공성)이 요구하는 스토어가 다르다는 것이 여기서 드러났고, 둘을 동시에 만족시키는 집합이 978(도달 + 공성)이다. 자세한 것은 9장.
7장 요약
  • 스텝 상태는 여섯 개고, 전이와 발행이 같은 틱에 일어난다.
  • 플랜 스왑은 스텝 경계에서만. 인터럽트만 예외이고, 그때는 상관 ID 무효화가 진행 중 명령을 지운다.
  • 명령 발행 코드에 액션 이름이 없다 — actions.json의 emits가 전부 정한다.
  • POI 바인딩은 가까운 4개 후보 중 해시로 고른다. 난수가 아니라 해시라서 리플레이가 일치한다.
  • 인터럽트는 엣지 트리거다. 아니면 강제 액션 → 완료 → 재강제의 되먹임이 생긴다.
  • 전환 지터 폭이 두 가지인 이유는 정기 전환(60초 창)과 공성(3초 요구)이 양립하지 않기 때문이다.
