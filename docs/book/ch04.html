4장 — 플랜 DSL과 4단 검증기

LLM이 만들어 내는 산출물은 이것 하나뿐이다. 대사도, 설명도, 코드도 아니다 — 액션 3~10개를 늘어놓은 JSON 한 덩어리다. 이 장은 그 JSON이 어떻게 생겼고, 어떤 검사를 거쳐, 어떤 메모리 표현으로 바뀌어 실행되는지를 따라간다.

원문 · docs/03_PlanDSL_Spec.md 스텝 3~10 · 분기 없음 검증 4단

1. 플랜 문서 — LLM이 내는 유일한 것

planstore/plans/blacksmith@Morning.Peace.Fair.json
{
  "schema": 1,
  "goal": "restock_and_forge",          // ^[a-z][a-z0-9_]{2,31}$ — 로그·검수용 식별자
  "reasoning": "아침이라 광석부터 채운 뒤…",  // 200자 상한. 런타임은 무시한다
  "steps": [
    { "action": "MoveTo", "args": { "poi": "$nearest_field", "speed": "walk" }, "timeout_s": 300 },
    { "action": "Mine",   "args": { "resource": "iron_ore", "count": 6 },       "timeout_s": 900 },
    { "action": "MoveTo", "args": { "poi": "$workplace" },                    "timeout_s": 300 },
    { "action": "Craft",  "args": { "recipe": "iron_sword", "count": 2 },      "timeout_s": 1800 },
    { "action": "Store",  "args": { "item": "iron_sword", "amount": 2 },       "timeout_s": 120 },
    { "action": "MoveTo", "args": { "poi": "$home" },                         "timeout_s": 300 },
    { "action": "Sleep",  "args": { "until": "Morning" },                     "timeout_s": 7200 }
  ],
  "on_step_fail": "fallback",
  "loop": true
}

여기 없는 것들

  • 분기가 없다. if도 while도 없다
  • POI id가 없다. $workplace 같은 심볼뿐
  • NPC id가 없다. nearest:guard 같은 심볼뿐
  • 자연어가 없다. reasoning만 예외고 런타임이 무시한다
  • 절대 시각이 없다. 시간대 열거값만

왜 이렇게까지 줄이나

  • 플랜은 (아키타입 × 버킷) 단위로 수백 마리가 공유한다. 개체에 묶이면 캐시가 무의미해진다
  • 분기가 있으면 실행이 O(1)이 아니게 되고, 상태 공간이 커져 검증도 못 한다
  • 상황이 바뀌면 분기하지 않고 재계획한다 — 그게 L2가 있는 이유다

1.1 POI 심볼 9종 — 개체 바인딩은 런타임이 한다

심볼런타임이 무엇으로 바꾸나세우는 장소 플래그
$homeNPC 인스턴스의 home_poiAtHome
$workplaceNPC 인스턴스의 workplace_poiAtWorkplace
$market $tavern $temple $gate같은 존에서 가장 가까운 해당 종류AtMarket 등
$nearest_field그 아키타입이 접근 가능한 가장 가까운 fieldAtField
$nearest_safe가장 가까운 안전 지점 (gate 또는 home)없음 — 어느 쪽인지 모른다
$nearest_shelter실내로 판정되는 가장 가까운 POI없음
뒤의 둘이 플래그를 안 세우는 이유 검증기 3단은 "이 스텝이 끝나면 어떤 플래그가 서는가"를 시뮬레이션한다. $nearest_safe는 성문일 수도 집일 수도 있으므로 아무 장소 플래그도 세우지 않는다. 관대하게 잡아 "둘 다 설 수 있다"고 하면 V3 판정 자체가 무의미해진다 — 통과시키면 안 되는 플랜이 통과한다.

3. 3단 정합성 — 이 프로젝트의 실질적 품질 게이트

플랜을 실행하지 않고, 액션의 requires/grants/clears만으로 상태 전이를 앞에서 뒤로 시뮬레이션한다. 고전적인 GOAP 검사다.

3.1 실패 설명을 영어로 만드는 이유

src/Npc.Core/Validation/CoherenceValidator.cs
return ValidationResult.Fail(
    ValidationStage.Coherence, "V3.PRECONDITION_UNMET", i,
    $"{step.Action} requires {WorldFlagTable.Format(missing)} but no preceding step grants it. "
    + Remedy(missing)                                    // ★ 고치는 방법까지 적는다
    + $"State before this step: {WorldFlagTable.Format(state)}.");

실제로 나가는 문장은 이렇다.

Craft requires HasRawMaterial but no preceding step grants it.
Gather/Mine/Farm/Fish it first, or Withdraw a raw material at your home or workplace.
State before this step: AtWorkplace|HasFood|HasWater|HasTool|HasProduct|HasCoin|IsDay|RegionPeaceful.
설계 결정이유
영어로 쓴다이 문자열이 그대로 재시도 프롬프트에 실린다. 모델이 읽을 문장이다
비트마스크 숫자를 절대 안 쓴다0x8000을 주면 모델이 못 고친다. WorldFlagTable.Format이 이름으로 편다
아이템도 code가 아니라 이름같은 이유. V3.RESOURCE_IMBALANCE가 ItemName()을 부른다
처방(Remedy)을 붙인다"무엇이 틀렸다"보다 "이렇게 고쳐라"가 재시도 성공률을 올린다. 장소 플래그는 고치는 법이 하나(그 POI로 MoveTo)라 그걸 적어 준다
실패 설명 길이를 180자로 자른다재시도 서픽스가 300 토큰 예산의 두 배를 넘겼다(실측 665 토큰). 앞쪽에 핵심이 있어 잘라도 살아남는다

3.2 3단이 놓치는 것 — 그래서 4단이 있다

3단은 시간을 모른다

각 스텝이 몇 게임시간 걸리는지 보지 않는다. 그래서 "loop:true인데 한 사이클이 0.9 게임시간"인 플랜을 통과시킨다 — 하루 일과가 되어야 하는데 45분마다 반복하는 셈이다.

4단은 세계를 굴린다

DryRunValidator가 SimWorld를 축소해 1~2 사이클 돌린다. 틱을 10Hz로 굴리지 않고 액션 소요시간만큼 게임시간을 건너뛴다 — 그래서 건당 0.02 ms다(사양의 추정 "~50 ms"보다 2,500배 빠르다).

4단의 시드는 버킷에서 유도한다 ValidationContext.SeedOf(bucket) — 난수도 시각도 섞지 않는다. 같은 플랜은 언제 어디서 돌려도 같은 판정을 받아야 골든 테스트가 안정된다.

4. 컴파일 — JSON에서 실행 표현으로

실행기는 JSON을 보지 않는다. PlanCompiler.Compile이 만든 값 타입 배열만 본다.

4.1 진입 전제를 계산하는 방법 — 여기 미묘한 버그가 있었다

src/Npc.Core/Plan/CompiledPlan.cs — PlanCompiler.Compile
WorldFlags granted = WorldFlags.None, cleared = WorldFlags.None;
WorldFlags required = WorldFlags.None, forbidden = WorldFlags.None;

foreach (var step in document.Steps)
{
    StepFlags flags = vocabulary.FlagsOf(action);

        required  |= flags.Requires & ~granted;   // ★ 앞선 스텝이 세워주는 것은 빼고
    forbidden |= flags.Forbids  & ~cleared;
    granted = (granted & ~flags.Clears) | flags.Grants;
    cleared = (cleared & ~flags.Grants) | flags.Clears;
}
그냥 전부 OR 하면 무슨 일이 생기나 Mine이 HasRawMaterial을 세워주는데 Craft가 그것을 요구한다. 전부 OR 하면 이 플랜의 RequiredFlags에 HasRawMaterial이 들어가고, 그러면 플랜을 시작하기도 전에 원자재를 갖고 있어야 한다는 뜻이 된다. 결과: 인지 스캔이 매 틱 "이탈"이라고 답한다 → 재계획 큐가 즉시 포화한다.

4.2 on_step_fail — 스텝이 실패했을 때

정책동작언제 쓰나
fallback 기본아키타입 폴백 플랜으로 전환대부분. 안전한 기본값
retry_once같은 스텝을 한 번만 다시일시적 실패가 예상될 때 (경로 막힘)
skip그 스텝을 건너뛰고 다음으로폴백 플랜 자신. 폴백에서 또 폴백으로 갈 곳이 없다
replan재계획 큐에 점수 50으로 넣고 다음 스텝으로상황이 근본적으로 바뀐 경우

점수 50은 인지 스캔의 이탈 판정(최대 9.5)보다는 크고 인터럽트(1000+)보다는 작다 — 실제로 실패한 NPC는 "곧 이탈할지도 모르는" NPC보다 먼저 봐야 하지만, 도망치는 NPC보다는 급하지 않다.

경로내용버전 관리

pinned이 재프리베이크에 살아남는 방법 PlanStore.SetBucket은 PlanOrigin.Pinned인 버킷을 덮어쓰지 않는다. 등록조차 하지 않고 이미 걸려 있던 id를 그대로 돌려준다 — 레지스트리에 쓰레기를 남기지 않기 위해서다. 강제로 올리는 Pin()은 planstore/pinned/ 로드와 승격 도구만 부른다.
검증 실패분을 조용히 버리지 않는다 RejectedStore가 실패한 응답 텍스트를 실패 코드와 함께 planstore/rejected/에 남긴다. 이것을 버리면 품질 개선의 원자료가 사라진다 — 통과율 50 % → 78.3 %로 올린 T2-21 개선 루프가 전부 이 파일들을 읽고 한 작업이었다.

6. 골든 테스트 — 문자열이 아니라 속성을 본다

LLM 출력은 매번 다르고 그게 정상이다. 그래서 골든 픽스처 50건은 정확한 문자열 비교를 하지 않고 속성 단언만 쓴다.

단언 종류무엇을 보나W11 합격률
validates(DryRun)4단까지 통과하는가82.0 %
step_count_between(3..10)스텝 수98.0 %
ends_with_any(Sleep/Rest)일과가 휴식으로 끝나는가98.0 %
contains_action(Craft)그 아키타입다운 액션이 있는가90.9 %
produces_item_of(product)실제로 무언가를 만드는가90.0 %
differs_from(...)다른 버킷과 플랜이 달라야 한다100 %
acquires_before_use쓰기 전에 확보하는가100 %
avoids_flag_while금지 상태에서 실행 안 하는가100 %
not_contains(...)있으면 안 되는 액션100 %
전체 (3회 중 2회 이상 통과 = 합격)93.6 % (206/220)

differs_from이 100 %인 것이 중요하다 — 같은 아키타입이라도 아침과 밤의 플랜이 실제로 다르다는 뜻이고, 그게 "상황을 반영한다"의 조작적 정의다.

4장 요약
  • 플랜은 선형 스텝 3~10개다. 분기·POI id·NPC id·자연어가 전부 없다.
  • 검증은 4단이고 3단(정합성)이 실질적으로 가장 많이 잡는다. 실행하지 않고 플래그 전이만 시뮬한다.
  • 실패 설명은 영어 + 처방이다. 그 문자열이 그대로 재시도 프롬프트에 실린다.
  • 컴파일 시 진입 전제만 남긴다. 앞선 스텝이 세워주는 플래그를 요구로 넣으면 매 틱 이탈 판정이 난다.
  • pinned/는 재프리베이크가 덮어쓰지 않는다. rejected/는 품질 개선의 원자료다.
  • 골든 테스트는 속성 단언만 쓴다 — 매번 다른 출력이 정상이기 때문이다.
