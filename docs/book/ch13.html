부록 — 코드 맵 · 확장 레시피 · 용어집

앞 장들이 "왜 이런가"였다면 여기는 "어디에 있고 어떻게 손대나"다. 파일 하나하나가 무엇을 하는지, 새 액션·아키타입·링크를 추가하는 절차, 그리고 이 저장소에서 실제로 자주 나온 실수들이다.

4. 확장 레시피

4.1 새 액션 추가

전제 — 액션은 40개 상한이다. 지금 37개다. 넘기려면 하나를 빼거나 기존 액션의 파라미터로 흡수한다.

// ① masterdata/actions.json 맨 뒤에 추가 (code 는 38부터. 중간 삽입 금지)
{
  "id": "Bargain", "code": 38, "category": "social",
  "desc": "…",                                   // 프롬프트에 그대로 실린다. 신중히
  "params": { "item": {"type":"item_ref","required":true} },
  "requires": ["AtMarket"], "forbids": ["IsSleeping"],
  "grants": ["HasCoin"], "clears": ["HasProduct"],
  "default_timeout_s": 300,
  "emits": [{"command":"Interact","map":{"Item":"$item"}}],
  "completes_on": ["NpcActionCompleted"], "fails_on": ["NpcActionFailed"]
}

// ② 쓸 아키타입의 allowed_actions 에 추가 (archetypes.json)
// ③ 검증
dotnet run --project src/Npc.Host -- validate --masterdata ./masterdata
// ④ 프리픽스가 바뀌었으므로 플랜 전량 무효 → 프리베이크 재실행

런타임 코드는 한 줄도 안 고친다. CommandEmitter가 emits를 읽어 필드를 채우고, 카탈로그·검증기·프롬프트가 전부 이 JSON에서 나온다.

4.2 새 아키타입 추가

// ① archetypes.json 맨 뒤 (code 는 맨 뒤에만 붙인다 — 재배치 금지)
// ② 그 아키타입의 폴백 플랜을 fallback_plans.json 에 추가   ← V7 이 없으면 기동 실패
//    · loop: true · on_step_fail: skip · allowed_actions 만으로 구성 (V8)
// ③ population_weight 를 넣고 다른 것들을 줄여 합을 1.0 으로 (V5)
// ④ workplace_poi_type 에 해당하는 POI 정원이 인구를 감당하는지 (V10)
// ⑤ npc_instances.json 재생성
dotnet run tools/gen_npcs.cs
// ⑥ 버킷이 72개 늘어난다 → 프리베이크
코드는 고치지 않는다 아키타입 수는 archetypes.json 이 정하고 BucketSpace 가 들고 있다 (F-05). 기존 버킷 인덱스는 변하지 않는다 — 아키타입이 가장 바깥 차원이라 뒤에 붙는 것은 뒤에만 자리를 만든다. 기존 플랜 2,880개는 그대로 쓰고, 새 아키타입의 72칸만 프리베이크하면 된다. 권장 상한은 128 이고 하드 상한은 npc_ref payload 가 정하는 4,096 이다 — 실질 제약은 프롬프트 프리픽스의 토큰 비용이다.

4.3 새 월드 플래그 추가

// ① world_flags.json 의 reserved_bits (22·23·44~63) 중 하나를 쓴다
{ "bit": 44, "id": "HasContract", "group": "social", "desc": "…" }

// ② WorldFlags.g.cs 는 소스 생성기가 자동으로 갱신한다 — 손으로 쓰지 않는다
// ③ 누가 이 비트를 세우는가를 정한다:
//     · 아이템이면 items.json 의 grants
//     · POI 면 pois.json 의 grants
//     · 액션이면 actions.json 의 grants/clears
//     · 이벤트면 EventApplier 에 반영 코드 (← 이때만 코드를 고친다)
가장 위험한 실수 런타임이 세우지 않는 플래그를 액션이 요구하는 것. 검증기 3단은 MasterDataSet.InitialFlags에서 그 플래그를 세워 두고 판정하므로 검증은 통과한다. 그런데 런타임에서는 아무도 안 세우니 인지 스캔이 매 틱 이탈로 읽고 재계획 큐가 포화한다. 실제로 OnDuty가 그랬다 — 5,000마리 하루에 이탈 29,535건이었다.

4.4 새 인터럽트 규칙

// interrupts.json 에 추가. 재기동만 하면 즉시 반영된다 — 프리베이크 불필요.
{
  "id": "seek_shelter_in_storm", "priority": 60,
  "when": { "all_flag": ["WeatherHarsh"], "none_flag": ["AtHome","AtWorkplace"] },
  "then": { "action": "MoveTo", "params": { "poi": "$nearest_shelter" } },
  "replan": { "urgency": 40 }
}
  • then.action이 그 아키타입의 allowed_actions에 없으면 규칙을 건너뛴다
  • 우선순위가 같으면 id 오름차순으로 결정 — 매칭이 결정론이어야 리플레이가 된다
  • 조건이 오래 참으로 남는 규칙이면 엣지 트리거가 되먹임을 막아 준다 (자동)

8. 한 장 요약

절대 규칙 — 틱 루프

  • await 금지 (FlushAsync 하나 예외)
  • LLM 호출 금지 — 참조 자체가 없다
  • 힙 할당 금지 — new · LINQ · 문자열 보간 · 클로저
  • lock 금지 — Volatile + 원자 교체만
  • Dictionary 순회 금지 — 순서 비결정성
  • DateTime.Now · Stopwatch 금지

절대 규칙 — 패킷

  • 반환값 있는 전송 메서드 금지 (N1)
  • readonly record struct만 (N2)
  • string 필드 금지 (N3)
  • DateTime/TimeSpan 금지 — Tick만 (N4)
  • 모든 명령에 CorrelationId (N5)
  • 모든 이벤트에 Sequence (N6)
  • 처리는 멱등 (N7) · 배치가 기본 (N8)

절대 규칙 — 프롬프트

  • 프리픽스는 기동 시 1회 조립, 이후 불변
  • 프리픽스 토큰 하한 4,096 (상한 없음)
  • 서픽스 ≤ 300 토큰 (조립기가 지킨다)
  • 재시도 피드백은 서픽스에만
  • 플레이어 작성 문자열을 넣지 않는다
  • 프리픽스 SHA를 모든 요청 메트릭에 태그

작업 후 체크리스트

  • dotnet test 통과
  • dotnet format --verify-no-changes
  • 틱 루프를 건드렸으면 bytesPerTick = 0 확인
  • 패킷을 건드렸으면 Contracts_* 통과
  • 마스터데이터를 건드렸으면 무효화 범위 확인
  • 프롬프트를 건드렸으면 플랜 전량 무효 — 의도한 것인가
  • 문서와 어긋나면 같은 커밋에서 문서도 고친다
마지막으로 이 저장소를 관통하는 규칙은 하나다 — 모르는 것은 모른다고 적는다. 미측정을 빈칸으로 두지 않고 "미측정"이라 쓰고, 추정을 실측인 척하지 않으며, 게이트가 안 닫히면 기준을 고치는 대신 왜 안 닫히는지를 적는다. 코드를 고칠 때도 같은 태도를 유지하면, 다음 사람이 이 문서들을 근거로 쓸 수 있다.
