계기는 하나다 — bytesPerTick

bytesPerTick ✔

틱 루프가 틱마다 힙에 쓴 바이트. 틱 루프 안에서만 잰다. 0이 아니면 new·LINQ·문자열 보간·클로저 중 하나가 들어왔다는 뜻이고, 원인이 반드시 있다.

gen0Collections ✘

GC.CollectionCount(0) 이라 프로세스 전역이다. 대시보드 HTTP · 소켓 리시버 · JSON 직렬화 · 로깅이 전부 여기 들어간다. 이 값으로 틱 루프를 재면 잡음만 잰다.

표에서 읽는 것 넷

  1. 스캔/틱이 150에서 멈춘다 2,000부터

    500 → 53, 1,000 → 97, 2,000 → 150, 5,000 → 150. CognitionScheduler.MaxScansPerTick 이다. NPC 가 늘어도 매 틱 보는 수가 안 늘어난다 — 대신 한 마리를 다시 보기까지의 주기가 길어질 뿐이다. 이 교환이 스케일을 만든다.

  2. p99 가 10배에 11배 0.244 → 2.672 ms

    거의 선형이다. 인지 스캔은 상한에 걸렸지만 플랜 실행과 명령 발행은 NPC 수에 비례하기 때문이다. 그래도 예산 20 ms 의 13 %다.

  3. bytes/tick 이 전부 0

    NPC 가 10배가 되어도 틱 루프는 한 바이트도 안 쓴다. SoA 배열이라 NPC 가 늘어도 새 객체가 안 생긴다.

  4. 힙이 안 자란다 69.5 → 82.8 MB

    NPC 10배에 힙은 19 % 만 늘었다. NPC 상태가 5,000개의 객체가 아니라 몇 개의 배열이기 때문이다. NpcStore 의 핫 배열은 합쳐 ~100 KB 로 L2 에 들어간다.

부러뜨려 본다 — 틱 루프에 LINQ 한 줄

bytesPerTick 이 정말로 계기 노릇을 하는지 확인한다. 전용 브랜치에서 틱 루프에 할당을 하나 심는다.

src/Npc.Runtime/NpcServerLoop.cs (실습용 · 브랜치에서만)
// 틱 루프 안 어딘가에
int busy = _store.StepStatus.Count(s => s == (byte)StepStatus.Waiting);
전후
bytes/tick00 이 아니게 된다
gen00늘어나긴 하는데 대시보드를 켜도 늘어난다
틱 p992.672눈에 띄게 안 변할 수도 있다
여기서 배우는 것 p99 만 봐서는 회귀를 못 잡는다. 할당이 생겨도 당장은 안 느려진다 — 느려지는 것은 GC 가 도는 순간이고, 그건 부하가 몰릴 때 온다. bytesPerTick 은 증상이 나기 전에 원인을 잡는 계기다.

TickAllocationTests 가 CI 에서 같은 것을 잰다. 이 실습은 그 테스트가 무엇을 지키는지 몸으로 아는 과정이다.

차이가 나면먼저 볼 곳
bytes/tick ≠ 0무조건 회귀다. 틱 루프에 뭔가 들어왔다
p99 가 크게 올랐다POI 를 많이 늘렸나(거리표 커짐) · 플랜 스텝이 길어졌나
스캔/틱이 150 미만인데 올랐다인지 밴드 분포가 바뀌었다 — 플레이어 봇 수를 확인
명령 수가 크게 줄었다플랜이 실패하고 있을 수 있다. timeouts 를 같이 본다
힙이 계속 자란다회차를 길게(-Days 7) 돌려 누수인지 본다

확인한다

  • NPC 5,000 회차에서 수용 기준 넷 전부 OK
  • bytes/tick 이 모든 회차에서 0
  • 스캔/틱이 2,000 이상에서 150에 붙는다
  • 내 마스터데이터 회차가 기준선과 같은 판정
  • docs/measurements/ 에 diff 가 없다 — 원자료를 안 건드렸다

실측의 한계를 같이 적는다

이 표가 말하지 않는 것

① 이 회차는 --max-speed 다. 10Hz 페이싱 없이 최대 속도로 돈다. 실시간 3.9초에 게임 하루가 끝났다는 것은 여유가 많다는 뜻이지 실시간 부하를 잰 것이 아니다.

② LLM 이 꺼져 있다. 티어를 켜면 워커가 CPU 를 나눠 쓴다. GPU 사용률은 이 저장소에서 아직 미측정이다.

③ 소켓이 아니다. --loopback 이라 직렬화·네트워크 비용이 없다. --link tcp 회차는 따로 재야 한다.

재지 않은 것을 잰 것처럼 적지 않는다. 20장의 체크리스트에 그 목록이 있다.
