1부 · 일단 켠다

3장 · 눈으로 본다 — 게임서버 · NPC 서버 · 뷰어

1·2장은 같은 프로세스 안에서 돌렸다. 이번에는 진짜 소켓으로 세 프로세스를 붙인다. 그리고 누가 무엇을 아는지를 구분한다 — 게임서버는 좌표를 알고, NPC 서버는 이유를 알고, 뷰어는 둘 다 물어본다.

난이도 ★★☆☆ 40분 LLM 불필요 뷰어는 Windows 전용 선택 장
이 장은 건너뛰어도 된다 뷰어가 WinForms(net10.0-windows) 라 Windows 에서만 뜬다. 이 책의 나머지 20개 장은 OS 를 안 가린다.
다만 이 장 후반의 핸드셰이크 실험은 뷰어 없이도 돌아간다 — 게임서버를 --headless 로 띄우기 때문이다. Windows 가 아니라면 거기만 하고 4장으로 넘어간다.

무엇을 띄우나

누가 무엇을 아는가

뷰어가 게임서버 하나만 보면 될 것 같은데 NPC 서버에도 따로 붙는다. 이유가 있다.

아는 것게임서버NPC 서버
NPC 의 좌표·HP안다이벤트로 받은 만큼
지금 무슨 행동 중인가안다 (명령을 받았으니)안다
왜 그 행동을 하는가 (플랜·goal)모른다안다
몇 번째 스텝인가모른다안다
월드 플래그 (AtField·HasCoin…)모른다안다
플랜 출처 (bucket/fallback)모른다안다
이 장의 한 문장 플랜 id · 스텝 번호 · 월드 플래그는 게임서버가 알 수 없는 정보다. 링크에 그런 필드가 없고, 있어서도 안 된다 — 명령은 fire-and-forget 이고(N1), 패킷에는 문자열이 없다(N3). 게임서버를 경유해 중계하면 실제로는 존재하지 않는 결합을 테스트 베드가 만들어 낸다. 그래서 뷰어가 NPC 서버에 직접 붙는다.

띄운다

한 줄로

터미널 — Windows 
PS> ./testbed/run_demo.ps1 -Scenario day

게임서버 → NPC 서버 → 뷰어를 순서대로 띄우고, Ctrl-C 에 셋 다 내린다. 창을 하나 닫아도 나머지가 따라 내려간다. 첫 실행은 빌드 때문에 30초쯤 걸리고, 두 번째부터는 -NoBuild 를 준다.

옵션기본뜻
-Scenario day|siege|blackoutday데모 시나리오 3종
-Npcs N300게임서버와 NPC 서버에 같은 값이 간다
-TimeScale N60데모 시나리오의 틱 좌표가 60 기준이다
-Tier none|t1|t2|allnone재계획 티어. 기본이 none 이라 LLM 을 안 부른다
-NoBuild—빌드를 건너뛴다

손으로 셋을

스크립트가 하는 일은 이 셋이다. 무엇이 무엇에 붙는지 보려면 터미널 셋에 하나씩 넣는다.

  1. 게임서버 — 먼저 떠 있어야 한다
    터미널 1 
    PS> dotnet run -c Release --project testbed/Npc.TestGameServer -- `
      --npcs 300 --time-scale 60 --link-port 7010 --client-port 7020 `
      --scenario testbed/scenarios/demo_day.jsonl
    터미널 1 — 출력 
    game server: npcs=100 time-scale=60 bots=0 max-clients=4
masterdata: C:\github_edu\LlmNpcServer\masterdata (f37c02926c0b)
roster hash: d2e722de62bb
listening: link :7010 | client :7020
tick 50 | link down | cmd 0 | ev 155 | players 0 | clients 0 | ...

    두 해시를 기억한다. masterdata 해시는 0장의 content_hash 앞 12자리이고, roster hash 는 "NPC 몇 마리를 어떤 아키타입으로 배치했는가"의 지문이다. 이 둘이 NPC 서버와 같아야 링크가 붙는다. 아직 NPC 서버가 없으니 link down 이 정상이다.

  2. NPC 서버 — --link tcp 로 바꾼다
    터미널 2 
    PS> dotnet run -c Release --project src/Npc.Host -- `
      --link tcp --gs-port 7010 --npcs 300 --time-scale 60 --days 0 `
      --tier none --planstore ./planstore --port 5080 --dev-control

    1·2장의 --loopback 이 --link tcp 로 바뀐 것이 전부다. Npc.Runtime 도 Npc.Planning 도 한 줄 안 바뀌었다 — 링크는 갈아 끼우는 부품이고, 그게 IGameServerLink 가 존재하는 이유다.

    --days 0 은 무제한이다. --dev-control 은 뷰어의 킬스위치 버튼을 위해 필요하다 (없으면 POST /control/killswitch 라우트가 등록조차 안 된다 — 404다).

  3. 뷰어
    터미널 3 — Windows 전용 
    PS> dotnet run -c Release --project testbed/Npc.TestClient -- `
      --host 127.0.0.1 --port 7020 --npc-http http://localhost:5080

    --port 7020 은 게임서버로, --npc-http 는 NPC 서버로 간다. 주소가 둘인 것이 이 장의 요지다.

양쪽이 같아야 하는 값 셋 --npcs · --time-scale · --zone 은 게임서버와 NPC 서버가 같아야 한다. 하나라도 다르면 핸드셰이크에서 거절된다 — 그리고 그것이 의도된 동작이다. 아래에서 직접 어긋내 본다.

화면 보는 법

┌───────────────────────────────────────────────┬──────────────────────────┐

├───────────────────────────────────────────────┤  flags AtWorkplace|IsDay │

│ client ● 12ms  npc-link ●  gs 5,412  npc 5,410│                          │

맵에서 읽는 것

  • 존 배경원 테두리 — 회색 Peace · 주황 Alert · 빨강 War
  • NPC 사각 색 — 아키타입 40종을 황금각(137.5°)으로 갈랐다
  • NPC 테두리 — 흰색 Working · 반투명 Sleeping
  • 이동선 — 목표 POI 로 향하는 옅은 선. "왜 저기로 가는가"의 절반이 이 선이다

탭 넷

  • 인스펙터 — 2장의 /npc/{id} 를 1초마다 폴링한 것. 이 패널이 데모의 핵심이다
  • 로그 — 명령·이벤트 500줄. 여기서 처음으로 id 가 사람 말이 된다 (MoveTo poi=137 이 아니라 MoveTo smithy_001_05)
  • 제어 — 존 상태·날씨·시간 건너뛰기·고장 주입·킬스위치
  • 링크 — 양쪽 연결 상태와 /metrics 요약

키: W A S D 이동(Shift 달리기) · 좌클릭 선택 · Tab 다음 NPC · E/R 대화/공격(30m 안에서만) · 휠 줌 · Home 전체 보기 · Space 플레이어 추적

인스펙터가 2장의 그 화면이다 뷰어의 인스펙터 탭은 우리가 2장에서 만든 추적기와 같은 데이터를 본다 — GET /npc/{id} 하나다. 2장을 하고 왔다면 이 패널의 모든 줄이 이미 익숙할 것이다.

데모 3종 — 무엇을 볼 것인가

시나리오실시간볼 것
day약 17분 주입 이벤트가 0개다. 18:00 에 시간대가 Evening 으로 넘어갈 때 버킷 키가 바뀌어 인스펙터의 plan id 가 갈리는 것을 본다. 이벤트 없이 NPC 가 하루를 사는 것 자체가 이 프로젝트의 결과물이다
siege4분 tick 1200 에 town_center·gate_east 가 War 로 간다. 존 테두리가 빨개지는 순간 그 존의 NPC 전원이 동시에 다른 계획으로 갈아탄다. tick 2400 에 평화로 되돌린다 → 10장에서 이런 대본을 직접 쓴다
blackout3분 T2 → T1 → PlanStore 를 600틱 간격으로 끊는다. 볼 것은 "아무 일도 일어나지 않는다" — NPC 는 계속 움직이고 크래시가 없다. 인스펙터의 PlanKind 가 bucket → fallback 으로 내려가는 것이 성공 신호다 → 11장

부러뜨려 본다 — 핸드셰이크를 어긋낸다

이 절은 Windows 가 아니어도 된다. 게임서버를 --headless 로 띄우므로 뷰어가 필요 없다. samples/ch03_demo/handshake-fail.ps1 이 두 회차를 자동으로 돌린다.

터미널 
PS> ./samples/ch03_demo/handshake-fail.ps1 -Npcs 100 -Seconds 10
실측 출력 
① 어긋난 회차 — NPC 수가 하나 다르다
   게임서버 --npcs 100   ·   NPC 서버 --npcs 99
   ── 게임서버가 남긴 줄 ─────────────────────────────
   game server: npcs=100 time-scale=60 bots=0 max-clients=4
   roster hash: d2e722de62bb
   tick  50 | link down | cmd 0 | ev 155 | players 0 | clients 0 | ...
   tick 100 | link down | cmd 0 | ev 218 | players 0 | clients 0 | ...
   결과: 거절됨 — link down 이 계속되고 명령이 하나도 안 나갔다
         조용히 도는 대신 연결 시점에 죽는 쪽을 고른 것이다.

② 맞춘 회차 — 양쪽이 같다
   게임서버 --npcs 100   ·   NPC 서버 100
   ── 게임서버가 남긴 줄 ─────────────────────────────
   game server: npcs=100 time-scale=60 bots=0 max-clients=4
   roster hash: d2e722de62bb
   tick  50 | link up | cmd 213 | ev 396 | players 0 | clients 0 | ...
   tick 100 | link up | cmd 510 | ev 732 | players 0 | clients 0 | ...
   결과: link up · 명령이 흐른다

실험 통과 — 어긋나면 거절하고, 맞으면 붙는다.
여기서 배우는 것

NPC 수가 하나 달랐을 뿐인데 아예 안 붙는다. 그리고 우회 옵션이 없다 — "경고만 내고 붙여 줘" 같은 플래그를 만들지 않았다.

이유는 이 첨자가 배열 인덱스이기 때문이다. 게임서버의 42번 NPC 와 NPC 서버의 42번 NPC 가 다른 사람이면, 대장장이에게 밭을 갈라고 명령하게 된다. 그리고 증상은 크래시가 아니라 "가끔 이상하게 행동한다" 로만 나타난다 — 며칠을 태우는 종류의 사고다.

연결 시점에 죽는 편이 훨씬 싸다. 이것이 핸드셰이크에서 프로토콜 버전 · 배속 · 마스터데이터 해시 · 로스터 해시 넷을 다 보는 이유다.

스크립트가 무엇을 보는가

samples/ch03_demo/handshake-fail.ps1 — 판정부 
# 증거는 게임서버 쪽 콘솔에 있다 — roster hash 와 매 50틱의 link up/down 이다.
# NPC 서버는 거절당한 사실을 링크 상태로만 들고 있고 콘솔에 따로 찍지 않는다.
$gsLog  = Read-Log $gs
$linkUp = ($gsLog -match 'link up')

# NPC 서버 쪽에서는 "명령이 한 건도 안 나갔다" 로 확인한다
$s = Invoke-RestMethod "http://localhost:$Port/status"
$connected = ($s.link.commandsFlushed -gt 0)

NPC 서버는 거절당했다는 사실을 콘솔에 찍지 않는다. 링크 상태(Faulted)로만 들고 있다. 그래서 판정은 게임서버 콘솔의 link up/down 과 NPC 서버 /status 의 link.commandsFlushed 두 곳에서 본다. 실제 연동에서 "왜 안 붙지?" 를 만나면 이 두 곳을 먼저 본다.

다른 방식으로도 어긋내 본다

어긋내는 것어떻게결과
NPC 수양쪽 --npcs 를 다르게로스터 해시 불일치 → 거절
배속양쪽 --time-scale 을 다르게거절 (틱 좌표가 어긋난다)
마스터데이터NPC 서버만 --masterdata ./lab/… 로콘텐츠 해시 불일치 → 거절
존 필터한쪽만 --zone town_center로스터가 달라져 거절

알아 둘 한계 셋

전부 의도한 것이거나 근거가 있는 미완이다. 버그로 오해하지 않도록 적는다.

무엇내용
소켓 경로에서는 리플레이가 100% 일치하지 않는다 명령이 몇 틱 늦게 도착할 수 있고 그것이 스텝 경계를 바꾼다. 결함이 아니라 사실이다 — 실제 게임서버에 붙으면 원래 그렇다. 결정론이 필요한 회차는 --loopback 으로 돌린다 → 15장
킬스위치는 링크로 안 간다 NPC 서버 안쪽 상태이고 GameEvent 에 그런 종류가 없다 — 만들면 계약 규칙을 어긴다. 제어 패널 버튼은 POST /control/killswitch 를 직접 부르고, --dev-control 없이 뜬 서버에는 라우트가 아예 없어서 404다
상태바의 npc 틱이 늙는다 게임서버는 NPC 서버의 틱을 명령의 IssuedAt 에서 딴다. 하트비트에는 그 값이 없다. NPC 서버가 한동안 명령을 안 내면 멈춘 것처럼 보이는데, 그것도 정보다

확인한다

  • 게임서버 콘솔이 listening: link :7010 | client :7020 을 찍는다
  • NPC 서버를 띄우면 게임서버 콘솔이 link down → link up 으로 바뀐다
  • 게임서버의 cmd 카운트가 계속 증가한다
  • NPC 서버 /status 의 link.commandsFlushed 가 0보다 크다
  • (Windows) 뷰어 맵에 NPC 사각형과 이동선이 보인다
  • (Windows) 인스펙터에 plan id · 스텝 목록 · 플래그가 나온다 — 2장에서 본 그 값들이다
  • handshake-fail.ps1 이 실험 통과 로 끝난다

잘 안 될 때

증상원인과 조치
게임서버가 link down 이고 NPC 가 안 움직인다양쪽 --npcs·--time-scale 이 다르다. 두 콘솔의 roster hash 를 견준다
뷰어가 "게임서버를 찾는 중…" 에서 안 넘어간다게임서버 --client-port 와 뷰어 --port 가 같은지 본다 (기본 7020)
인스펙터가 "NPC 서버 미연결"NPC 서버가 안 떴거나 --port 가 다르다. 뷰어는 이 상태로도 계속 돈다
킬스위치 버튼이 "미연결" 만 뜬다NPC 서버에 --dev-control 이 없다
"마스터데이터 해시가 게임서버와 다르다" 경고두 프로세스가 서로 다른 masterdata/ 를 읽고 있다. 가장 찾기 어려운 종류의 사고다
창은 뜨는데 NPC 가 하나도 안 보인다AOI 가 플레이어 반경 1,200m 다. Home 키로 전체를 보고 무리 쪽으로 걸어간다

1부를 마치며

여기까지 코드를 한 줄도 안 썼다. 그런데 이만큼 확인했다.

1장에서

LLM 0회 호출로 명령 1만 건. NPC 5,000마리에 틱 p99 2.4ms · 틱당 할당 0B. 명령을 절반 버려도 안 멈춘다.

2장에서

NPC 한 마리의 플랜·스텝·플래그·인벤토리를 읽었다. 플랜 교체가 스텝 경계에서만 일어나는 것을 로그로 확인했다.

3장에서

--loopback 을 --link tcp 로 바꾸는 것만으로 소켓 너머에 붙었다. 런타임 코드는 한 줄도 안 바뀌었다.

2부부터는 세계를 바꾼다. 마을에 없던 것을 만들고, 없던 직업을 만들고, 없던 반응을 넣는다. 여전히 C# 은 안 쓴다 — JSON 만 고친다. 그 전에 0장에서 만든 lab.ps1 이 필요해진다.
