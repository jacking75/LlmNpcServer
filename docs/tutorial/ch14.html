무엇을 만드나

NPC 서버와 게임서버 사이에 끼어 앉아 프레임을 세는 투명 중계다. 읽기만 하고 안 고친다.

  프레임 집계  (12.1초)
  방향       종류                프레임          바이트      평균
  ------------------------------------------------------
  npc→gs   CommandBatch        179       24,940      139
  gs→npc   EventBatch           89       29,612      332

이 장의 한 문장 언어에 안 묶인 부분은 헤더 8바이트다. 그 8바이트만 읽으면 프레임 경계를 알 수 있고, 프레임 경계를 알면 중계도 계측도 된다. 페이로드를 해석해야만 할 수 있는 일은 그다음 이야기다.

헤더 8바이트

 0      1      2      3      4      5      6      7      8 ...
+------+------+------+------+------+------+------+------+---------------+
|      PayloadLength (u32)   | Kind | Ver  |   Reserved  |    Payload    |
+------+------+------+------+------+------+------+------+---------------+
        little-endian          u8     u8      u16 = 0     MemoryPack
필드값왜
PayloadLengthu32 LE · 상한 1 MiB길이 접두. 상한이 없으면 잘못된 4바이트 하나로 프로세스가 죽는다
Kindu8 · 1~6Hello · HelloAck · CommandBatch · EventBatch · Heartbeat · Bye
Veru8 = 1길이보다 먼저 본다 — 버전이 다르면 길이 해석 자체를 못 믿는다
Reservedu16 = 0정렬용. 지금은 안 쓴다
헤더를 손으로 쓰는 이유 MemoryPack 안에 길이를 또 넣지 않는다. 진실의 출처를 둘로 만들면 언젠가 어긋나고, 어긋나는 순간 스트림이 통째로 깨진다. 그래서 길이는 헤더에만 있다.

파이썬으로 프레임을 뗀다

samples/ch14_sniffer/sniff.py
HEADER = 8
KINDS = {1: "Hello", 2: "HelloAck", 3: "CommandBatch",
         4: "EventBatch", 5: "Heartbeat", 6: "Bye"}

def pump(src, dst, label, verbose):
    buf = bytearray()

    while True:
        chunk = src.recv(65536)
        if not chunk:
            break

        dst.sendall(chunk)          # 그대로 흘려보낸다 — 투명 중계
        buf += chunk

        # TCP 는 경계를 안 지켜 준다. 이 재조립이 정상 경로다.
        while len(buf) >= HEADER:
            length, kind, version, reserved = struct.unpack_from("<IBBH", buf, 0)

            if not (1 <= version <= 2):  # 버전을 먼저 — 받아 줄 범위다
                return
            if length > (1 << 20):      # 그다음 상한
                return
            if len(buf) < HEADER + length:
                break                   # 아직 다 안 왔다

            stats[(label, KINDS.get(kind))] += 1
            del buf[: HEADER + length]

struct.unpack_from("<IBBH", ...) 한 줄이 전부다. C# 쪽 FrameCodec.TryReadFrame 과 논리가 같다 — 버전을 먼저 보고, 길이 상한을 보고, 다 안 왔으면 그냥 더 읽는다.

집계에서 읽는 것 넷

  1. 핸드셰이크는 딱 한 왕복, 96바이트씩

    Hello 1프레임 96 B, HelloAck 1프레임 96 B. 그 뒤로는 배치만 흐른다. 연결당 고정비가 거의 없다.

  2. CommandBatch 프레임 수 = FlushAsync 횟수 179

    12초면 120틱인데 프레임은 179개다. 틱 수와 다르다 — 한 틱에 여러 번 flush 될 수도, 보낼 게 없어 건너뛸 수도 있다. N8("배치가 기본") 이 여기서 눈에 보인다.

  3. 배치가 실제로 뭉친다 평균 139 B / 332 B

    명령 하나가 56바이트다(v1 기준. 확장 슬롯을 켠 v2 는 72바이트다). 평균 139바이트면 프레임당 명령 두 개쯤 들어 있다는 뜻이다. 이벤트는 64바이트니 평균 332바이트면 네다섯 개다. 명령 하나에 프레임 하나였다면 헤더 오버헤드가 14 %가 된다.

  4. Heartbeat 이 24바이트다

    헤더 8 + 페이로드 16(long 둘). DateTime 이 없다(N4) — 살아 있는지는 틱과 시퀀스로만 말한다.

페이로드 — 여기부터는 MemoryPack

Kind페이로드크기
CommandBatchWireCommand[] (v1) · WireCommandV2[] (v2)원소 56 B · v2 는 72 B
EventBatchWireEvent[] (v1) · WireEventV2[] (v2)원소 64 B · v2 는 80 B
Hello / HelloAckWireHello / WireHelloAck프레임 96 B

크기가 고정인 것은 필드 순서를 큰 타입부터 놓았기 때문이다 (long → int → float → ushort → byte). 패딩이 생기면 크기가 달라지고 Wire_LayoutIsFrozen 테스트가 먼저 깨진다.

MemoryPack 을 못 쓰는 언어라면 — 두 갈래

① Npc.Wire 를 고친다. 이 프로젝트 하나만 다른 직렬화로 바꾸면 된다. Npc.Contracts 도 Npc.Runtime 도 안 바뀐다 — 와이어 DTO 를 계약과 따로 둔 이유가 정확히 이것이다. ([MemoryPackable] 을 계약에 붙이는 순간 계약이 직렬화기 버전에 묶인다.)

② 고정 크기를 이용한다. WireCommand[] 는 결국 56바이트 블록의 연속이다. MemoryPack 의 배열 헤더만 해석하면 나머지는 raw 로 읽을 수 있다.

어느 쪽이든 헤더 8바이트와 다섯 규칙은 그대로다.

바꿔 보기결과
스니퍼에서 버전 범위 검사를 뺀다당장은 잘 돈다. 버전이 올라가는 날 조용히 깨진다 — 실제로 v2 가 그날이었다(B-02)
프레임의 Ver 대신 핸드셰이크에서 협상한 버전으로 원소 크기를 고른다협상 직후 경계에서 두 버전이 섞여 도착하면 배치가 어긋나 스트림 전체가 쓰레기가 된다
재조립 없이 recv 한 번을 한 프레임으로 친다부하가 낮으면 통과하고 높으면 깨진다 — 가장 나쁜 종류의 버그
<IBBH 를 >IBBH(빅엔디언)로길이가 터무니없이 커져 상한 검사에 걸린다. 검사가 잡아 준다
중계에서 sendall 을 빼고 읽기만 한다핸드셰이크가 안 끝난다 — 중계는 양방향 다 흘려야 한다
