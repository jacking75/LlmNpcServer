5부 · LLM을 켠다

16장 · 티어를 켠다 — 무엇이 달라지고 무엇이 안 달라지나

15개 장을 LLM 없이 왔다. 이제 켠다. 그런데 늘어나는 것은 "플랜의 출처" 하나뿐이고, 틱 p99 도 틱당 할당도 안 변한다 — 그것이 이 설계의 전부다.

난이도 ★★★☆ 60분 API 키 또는 로컬 GPU 키 없이도 읽힌다
이 책이 실제로 돌린 것과 안 돌린 것

5부의 유료 호출은 이 책을 쓰면서 실행하지 않았다. 대신 저장소에 이미 있는 실측 산출물을 읽는다 — planstore/manifest.json(프리베이크 한 회차의 원자료)과 planstore/rejected/(반려 기록 766건)다.

돌린 것: 엔진 설정 점검 · 프리픽스 출력 · manifest 읽기 · 반려 집계. 안 돌린 것: 실제 LLM 호출. 안 돌린 것을 돌린 것처럼 적지 않는다.

PS> .\tools\dotllm\dotllm.exe serve --model .\models\Qwen3-8B-Q4_K_M.gguf --port 8080 --gpu-layers 99

옵션뜻
--tier none기본. 캐시 + 폴백만. --no-llm 과 같다
--tier t1로컬 개별 재계획까지
--tier t2외부 API 로 버킷 미스까지 채운다
--tier all둘 다
--t1-workers / --t2-workers워커 수 (기본 2 / 8). 틱 루프 밖의 별도 스레드다
--t1-engine / --t2-engineappsettings.Llm.json 의 엔진 id 를 직접 지정

무엇이 달라지고 무엇이 안 달라지나

안 달라져야 하는 것

  • 틱 p50 · p99 — LLM 은 틱 루프 밖이다
  • bytes/tick = 0
  • overruns = 0
  • 명령이 나가는 경로 전체

이게 달라지면 배선이 잘못된 것이다. 재계획 워커가 틱 루프 상태를 직접 고치고 있거나, 어딘가에서 await 가 틱 안으로 들어왔다는 뜻이다.

달라져야 하는 것

  • /metrics 의 llmCalls > 0
  • cost 패널의 enabled 가 true
  • replan.tiers 배열에 행이 생긴다
  • 일부 NPC 의 planKind 가 individual 로
  • 재계획 큐가 줄어들기 시작한다 — 꺼내 가는 워커가 생겼으니까
2장의 그 실험이 여기서 갈린다 1·2장에서 --player-bots 0 회차가 기준선과 한 건도 안 틀렸다. 인지 스캔은 "누구를 재계획 대상으로 고를까" 만 정하는데 --tier none 에서는 재계획 자체가 없었기 때문이다. 티어를 켜면 이 둘이 처음으로 갈라진다 — 플레이어 근처 NPC 가 개별 플랜을 받는다.

비용 패널 읽기

"cost": {

필드정상이상하면
uniquePrefixHashes12 이상이면 즉시 경보. 프리픽스에 동적 값이 섞였고 캐시가 전면 미적중이다
promptCacheHitRate실측 30.7~42.6 %0 이면 캐시가 아예 안 걸린다. 프리픽스 4,096 토큰 하한을 확인
tokenCapUsage< 1.01.0 에 닿으면 T2 → T1 강등 → 거절 순으로 내려간다
downgrades · rejections0예산이 부족하다
breakerStateClosedOpen 이면 제공사 장애로 회로가 끊겼다 — 폴백으로 계속 돈다
일일 캡을 우회하는 코드를 만들지 않는다 토큰 캡은 안전장치다. 넘으면 T2 를 끄고 T1 으로 내리고, 그것도 넘으면 거절한다. 거절돼도 NPC 는 캐시와 폴백으로 계속 돈다 — 11장에서 확인한 그대로다. 캡을 우회하면 그날 예산이 새벽에 다 타고, 그때는 진짜로 아무것도 못 만든다.

확인한다

  • check-engines.ps1 이 키가 채워진 엔진을 정확히 가려낸다
  • 기준선(--tier none)의 cost.enabled 가 false
  • 티어를 켠 뒤 llmCalls > 0 · cost.enabled = true
  • 틱 p99 와 bytes/tick 이 기준선과 같다
  • uniquePrefixHashes 가 1
