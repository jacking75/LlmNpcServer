프로토콜 — 네 단계

① 핸드셰이크 — 네 값이 같아야 한다

var hello = new WireHello
{
    ProtocolVersion = FrameCodec.Version,          // 1
    TickRate        = 10,
    TimeScale       = timeScale,                   // 같아야 한다
    NpcCount        = roster.Count,                // 같아야 한다
    StartTick       = 0,
    MasterData      = WireHash.FromHex(data.ContentHash),   // 같아야 한다
    Roster          = WireHash.FromHex(roster.Hash),        // 같아야 한다
};

await WriteFrameAsync(stream, LinkMessageKind.Hello, MemoryPackSerializer.Serialize(hello), ct);
해시를 같은 함수로 계산해야 한다

로스터 해시는 "어떤 NPC 를 어떤 순서로 뽑았는가" 의 지문이다. 직접 계산하면 반드시 어긋난다 — 그래서 이 미니 서버는 Npc.MasterData 를 참조해 NpcRoster.Select 를 그대로 부른다. 

MasterDataSet data = MasterDataLoader.Load(mdDir);
NpcInstanceTable instances = NpcInstanceTable.Load(Path.Combine(mdDir, "npc_instances.json"), data);
NpcRoster roster = NpcRoster.Select(instances, npcs);   // NPC 서버와 같은 함수

선택 규칙이 한 곳에만 있는 이유가 이것이다. 양쪽이 각자 뽑으면 첨자가 어긋나고, 어긋나면 대장장이에게 밭을 갈라고 명령하게 된다.

거절당하면 이렇게 찍는다

양쪽 값을 나란히 찍는 것이 중요하다. "거절됨" 만 나오면 어느 값이 다른지 알 수 없고, 3장에서 봤듯이 이건 며칠을 태울 수 있는 종류의 문제다.

② 프레임 — 헤더 8바이트는 손으로 쓴다

static async Task WriteFrameAsync(Stream stream, LinkMessageKind kind, byte[] payload, CancellationToken ct)
{
    var buffer = new ArrayBufferWriter<byte>(FrameCodec.HeaderSize + payload.Length);

    FrameCodec.WriteHeader(buffer, kind, payload.Length);   // 8바이트
    buffer.Write(payload);                                   // MemoryPack

    await stream.WriteAsync(buffer.WrittenMemory, ct);
    await stream.FlushAsync(ct);
}

static async Task<(LinkMessageKind, byte[])> ReadFrameAsync(PipeReader reader, CancellationToken ct)
{
    while (true)
    {
        ReadResult result = await reader.ReadAsync(ct);
        ReadOnlySequence<byte> buffer = result.Buffer;

        // TCP 는 경계를 안 지켜 준다. 다 안 왔으면 false 를 받고 더 읽는다 — 정상 경로다.
        if (FrameCodec.TryReadFrame(ref buffer, out var kind, out var payload))
        {
            byte[] bytes = payload.ToArray();
            reader.AdvanceTo(buffer.Start, buffer.End);
            return (kind, bytes);
        }

        reader.AdvanceTo(buffer.Start, buffer.End);
        if (result.IsCompleted) { throw new IOException("상대가 연결을 닫았다."); }
    }
}

③ 세계를 흉내 낸다

받은 명령을 언제 완료로 칠지 정하는 것이 게임서버의 일이다. 이 미니 서버는 규칙 하나로 끝낸다 — 이동은 N틱, 나머지는 1틱. 

foreach (WireCommand c in batch)
{
    bool isMove = c.Kind == (byte)NpcCommandKind.MoveTo;
    long due = tick + (isMove ? travelTicks : 1);

    pending[due].Add(new WireEvent
    {
        Kind        = (byte)(isMove ? GameEventKind.NpcArrived : GameEventKind.NpcActionCompleted),
        OccurredAt  = due,
        Npc         = c.Npc,
        Correlation = c.Correlation,   // N5 — 받은 값을 그대로
        Poi         = c.TargetPoi,
    });
}
TickSync 를 빼먹지 않는다 매 틱 하나씩 보낸다. 이게 없으면 NPC 서버의 게임 시계가 안 간다 — 시간대가 안 넘어가고, 버킷 전환이 안 일어나고, --days N 이 영원히 안 끝난다. 12장에서 같은 함정을 다른 모양으로 만났다.

4단계로 증축한다

단계만드는 것확인
①TCP 수신 + Hello 만 보낸다NPC 서버 로그에 접속이 뜬다
②HelloAck 를 읽고 수락 여부를 찍는다[handshake] 수락
③CommandBatch 를 읽어 카운트만cmd 가 계속 증가
④EventBatch 로 도착·완료·TickSyncNPC 가 실제로 이동·도착을 반복

③까지만 만들면 NPC 는 명령을 내다가 전부 타임아웃으로 넘어간다. ④를 붙이는 순간 timeouts 가 0으로 떨어진다 — 그 변화가 이 장의 확인점이다.

  • 게임서버가 [handshake] 수락 을 찍는다
  • cmd 카운트가 계속 증가한다

  • timeoutsSynthesized = 0 — 게임서버가 제때 답하고 있다
  • eventGapsDetected = 0
  • src/ 에 diff 가 하나도 없다 — 이 장은 본체를 안 고친다

NPC 서버 쪽 — 실측 
tick=152 · 명령=759 · 이벤트=861 · 갭검출=1
여기서 배우는 것

NPC 서버가 갭을 잡아냈다(eventGapsDetected = 1). 그리고 죽지 않았다 — tick 152 에서도 명령을 계속 내고 있다.

N6 이 있는 이유가 이것이다. 이벤트 유실은 조용히 일어난다. 시퀀스가 없으면 "NPC 몇 마리가 가끔 안 움직인다" 로만 나타나고, 원인을 찾을 수가 없다. 번호를 붙여 두면 유실 자체가 관측 가능한 사건이 된다.

더 부러뜨려 볼 것예상
--npcs 를 어긋내고 띄운다[handshake] 거절됐다: RosterMismatch — 양쪽 해시가 나란히 찍힌다
--time-scale 을 어긋낸다TimeScaleMismatch
게임서버를 죽였다 살린다NPC 서버가 재접속한다. 그동안의 명령은 유실되고 타임아웃이 오른다
TickSync 를 안 보낸다게임 시계가 멈춘다. 시간대가 안 넘어간다
Correlation 을 0으로 답한다어느 명령의 답인지 모르니 전부 타임아웃이 된다
