왜 유실을 전제로 만들었나

게임서버는 남이 만든다. 그리고 그 사이에는 소켓이 있다. 즉:

명령은 사라진다

역압으로 버려지고, 소켓이 끊기고, 게임서버가 바쁘면 무시한다. fire-and-forget(N1) 이라 보낸 쪽은 성공 여부를 모른다.

응답은 안 올 수 있다

명령이 도착해도 게임서버가 완료 이벤트를 안 낼 수 있다. NPC 는 Waiting 에서 영원히 멈춘다.

그래서 timeout_s

모든 플랜 스텝에 있다. 응답이 없으면 NPC 서버가 ActionFailed(Timeout) 을 스스로 만들어 다음으로 간다.

읽는 법

  1. 진행률이 0으로 수렴하지 않는다

    드롭 50 %에 진행률 56.9 %. 선형보다 낫다 — 한 스텝이 실패해도 on_step_fail: skip 으로 다음 스텝이 바로 나가기 때문이다. 이 열이 0에 가까워지면 그때가 진짜 고장이다.

  2. 타임아웃이 정확히 그 자리를 메운다

    13.0 % → 46.6 %. 합성 실패가 유실된 응답의 대체재다. 이 수치를 운영에서 보면 "링크가 새고 있다" 는 신호로 읽는다.

  3. 틱은 오히려 조금 빨라진다

    할 일이 줄었으니 당연하다. 고장이 성능 지표로는 안 보인다 — 그래서 timeouts 와 drops 를 따로 봐야 한다.

  4. bytes/tick 은 끝까지 0

    타임아웃 합성 경로에도 할당이 없다. 예외 경로가 정상 경로보다 비싸면 장애 때 성능이 무너지는데, 그런 설계가 아니다.

--drop-rate 와 --fail-rate 의 차이 --drop-rate 는 명령이 게임서버에 도착하지 못한다 — 응답 자체가 없다. --fail-rate 는 도착했는데 실패로 응답한다 — ActionFailed 가 온다. 전자는 침묵이고 후자는 거절이다. 침묵이 훨씬 다루기 어렵다(언제까지 기다릴지 정해야 하니까). 그래서 이 제품은 침묵 쪽을 기본 가정으로 잡았다.

② LLM 을 끊는다 — 킬스위치

시나리오 C 다. "만들 수 있는가"가 아니라 "끊겨도 도는가"를 본다.

터미널 
PS> ./samples/ch11_chaos/killswitch.ps1 -Npcs 200 -StepSeconds 5

① NPC 서버 기동 (--dev-control)

② 단계별로 끊는다
   차단 전            tick      4 · 명령     222 · 스텝      22 · 표본32 bucket 0 / fallback 32
   -> T2 차단 (fired=True)
   T2 차단 후         tick     55 · 명령     731 · 스텝     531 · 표본32 bucket 0 / fallback 32
   -> T1 차단 (fired=True)
   T1 차단 후         tick    105 · 명령    1261 · 스텝    1061 · 표본32 bucket 0 / fallback 32
   -> PlanStore 차단 (fired=True)
   PlanStore 차단 후  tick    156 · 명령    2030 · 스텝    1830 · 표본32 bucket 0 / fallback 32

③ 판정
   전부 끊은 뒤에도 스텝이 22 → 1830 로 계속 늘었다.
   NPC 는 멈추지 않았다. 이것이 이 장의 성공 신호다.
끊는 것남는 것NPC 는
T2캐시 + T1(로컬)아무 변화 없다
T1캐시만아무 변화 없다. 재계획이 전면 중단될 뿐
PlanStore아키타입 폴백 40개계속 움직인다. 행동이 덜 다양해질 뿐
왜 안 멈추나 — 한 줄 PlanStore.Resolve 는 절대 null 을 반환하지 않는다. 캐시가 비어도, LLM 이 전부 죽어도, 조회는 반드시 무언가를 돌려준다. 이 한 줄의 계약이 시나리오 C 를 통과시킨다.
위 회차에서 bucket 이 0인 이유 표본 32마리가 차단 전부터 전부 fallback 이었다. 이 저장소의 planstore/plans/ 는 2,880 중 718개만 채워져 있고, 그중 앞쪽 첨자의 NPC 가 쓰는 버킷은 비어 있었기 때문이다.

bucket → fallback 이 내려가는 것을 보고 싶으면 17장의 프리베이크를 먼저 하거나, 차단 전에 추적기로 planKind=bucket 인 NPC 를 찾아 그 첨자를 -Npc 로 준다. 못 본 것을 봤다고 적지 않는다 — 이 책의 규칙이다.

--dev-control 이 없으면

터미널 
PS> curl -X POST "http://127.0.0.1:5093/control/killswitch?target=T2"
404 Not Found

401 이 아니라 404 다. 조건부 인증이 아니라 조건부 등록이기 때문이다 — --dev-control 없이 뜨면 그 라우트가 아예 만들어지지 않는다. 상태를 바꾸는 HTTP 를 기본으로 열어 두면, 대시보드가 열려 있는 동안 누구든 티어를 끊을 수 있다. 실수 하나로 열리는 문을 만들지 않는다.

확인한다

  • 드롭률을 0.5까지 올려도 진행률이 0으로 수렴하지 않는다
  • 타임아웃 비율이 드롭률을 따라 단조 증가한다
  • 모든 회차에서 bytes/tick = 0 · 크래시 없음
  • 킬스위치 3단을 다 눌러도 스텝이 계속 늘어난다
  • --dev-control 없이 띄우면 /control/killswitch 가 404
