10장 · 사건 대본을 쓴다 — 시나리오 jsonl

지금까지는 아무 일도 안 일어나는 하루를 봤다. 이제 날씨를 바꾸고 역병을 풀어 놓는다. 한 줄짜리 이벤트가 존 하나의 NPC 전원의 플랜 키를 동시에 갈아 끼우는 것을 본다.

난이도 ★★☆☆ 40분 LLM 불필요 사본 불필요 — 대본만 만든다

무엇을 만드나

jsonl 대본 둘과, 대본 유무를 나란히 견주는 스크립트를 만든다.

이 장이 끝나면 
PS> ./samples/ch10_scenario/run.ps1 -Npcs 200

회차      p99(ms) bytes/tick 이벤트    명령     스텝     인터럽트 이월
기준선     0.173   0          131050 109278 104032 200  0
weather 0.146   0          130678 109216 104249 200  0
plague  0.109   0          127695 106673 101081 201  0
siege   0.131   0          127489 105095  98098 201  0
이 장의 한 문장 이벤트 한 줄이 수백 마리의 플랜 키를 동시에 바꾼다. 그런데 틱 p99 는 안 오르고 이벤트 이월도 0이다 — 대량 전환을 여러 틱에 나눠 처리하기 때문이다. 한 틱에 다 갈면 그것 자체가 사고다.

대본의 문법

samples/ch10_scenario/plague.jsonl
{"_comment": "역병이 존을 타고 번진다. --time-scale 600 기준."}
{"at_tick": 120, "event": "ZoneStateChanged", "zone": "riverside", "code": "Alert"}
{"at_tick": 240, "event": "ZoneStateChanged", "zone": "riverside", "code": "Disaster"}
{"at_tick": 240, "event": "ZoneStateChanged", "zone": "farmlands", "code": "Alert"}
...
필드뜻
at_tick이 틱에 주입한다. 배속에 묶여 있다 — 아래에서 다시 본다
eventGameEventKind 의 이름. ZoneStateChanged · WeatherChanged · …
zone대상 존. zones.json 의 id 여야 한다 — 오타면 조용히 무시된다
code값. 지역 상태 Peace·Alert·War·Disaster / 기후 Fair·Cold·Storm
_comment주석. 로더가 무시한다 — 대본에 의도를 적어 두는 자리다
target"event": "KillSwitch" 전용. T2·T1·PlanStore → 11장
왜 이벤트만 주입하나 대본은 게임서버가 할 일을 흉내 내는 것이다. NPC 서버 안쪽 상태(플랜·플래그)를 직접 건드리는 문법이 없는 이유가 그것이다. 세계를 미는 것은 언제나 상대방이고, NPC 서버는 받아서 반응할 뿐이다. 유일한 예외가 KillSwitch 인데, 그건 이벤트가 아니라 NPC 서버 자신의 스위치다.

틱 좌표 — 대본을 배속에 맞춘다

가장 흔한 실수 at_tick 은 배속에 묶여 있다. 배속 600으로 쓴 대본을 60으로 돌리면 사건이 10배 이른 시각에 터진다 — 아무도 밭에 안 나간 새벽에 폭풍이 오고, 화면상으로는 "아무 일도 안 일어난 것처럼" 보인다.
터미널 — 환산표를 먼저 뽑는다 
PS> ./samples/ch10_scenario/tick-calc.ps1

시간대 경계 — 게임 첫날 (시작 06:00 Dawn)
  시간대         시각            ts 60      ts 600     ts 3600
  ------------------------------------------------------
  Dawn        05:00         13800        1380         230
  Morning     07:00           600          60          10
  Noon        11:00          3000         300          50
  Afternoon   14:00          4800         480          80
  Evening     18:00          7200         720         120
  Night       22:00          9600         960         160

  하루 = ts 60: 14400틱   ts 600: 1440틱   ts 3600: 240틱

PS> ./samples/ch10_scenario/tick-calc.ps1 -At "18:00"

게임 day 0 18:00
  --time-scale 60     at_tick    7200   (실시간 12분)
  --time-scale 600    at_tick     720   (실시간 1.2분)
  --time-scale 3600   at_tick     120   (실시간 0.2분)

Dawn 행이 13,800(ts 60)으로 크게 나오는 것은 시작이 06:00 이라 05:00 은 다음 날이기 때문이다. 첫날의 Dawn 은 tick 0 이다.

공식
1틱 = 실시간 0.1초10Hz 고정
1틱 = 게임 time_scale / 10 초ts 600 → 60 게임초
게임 하루 = 864000 / time_scale 틱ts 600 → 1,440틱

대본 둘

① weather.jsonl — 기후

Fair → Cold(11:00) → Storm(14:00) → Fair(18:00). 기후는 버킷 키의 네 번째 축이라, 바뀌면 그 존 NPC 의 플랜 키가 통째로 갈린다. 그리고 Storm 은 WeatherHarsh 를 세워 8장의 인터럽트를 건드린다.

② plague.jsonl — 지역 상태

강가 → 농지 → 마을 남쪽 → 중심가로 번지고 역순으로 회복한다. 지역 상태는 버킷 키의 세 번째 축이다. 중심가는 인구 1,247로 가장 커서 전환 비용이 제일 크다.

표에서 볼 것 셋

  1. 대본이 세계를 실제로 바꾼다

    plague·siege 는 명령이 3,000~4,000건 줄었다. 존이 Disaster·War 로 가면 그 버킷의 플랜이 달라지고, 덜 돌아다니는 계획으로 갈아타기 때문이다. 대본은 장식이 아니다.

  2. 틱이 안 느려졌다 전부 p99 < 0.2 ms

    수백 마리가 동시에 플랜을 갈아타는 순간이 있는데도 예산(20ms) 근처에 못 간다. 버킷 전환을 한 틱에 다 하지 않고 나눠 처리하기 때문이다 (BucketTransition).

  3. 이월이 전부 0이다

    backlogs 는 "한 틱 상한에 걸려 다음 틱으로 넘긴 이벤트 뭉치" 다. 대본이 이벤트를 밀어 넣어도 밀리지 않았다는 뜻이다. 이 값이 계속 오르면 이벤트 처리가 세계보다 느린 것이고, 그때는 링크를 먼저 본다.

표로는 안 보이는 것 "어느 NPC 가 언제 갈아탔는가" 는 이 표에 안 나온다. 그건 2장의 추적기로 본다. 
PS> dotnet run -c Release --project src/Npc.Host -- `
      --loopback --npcs 200 --time-scale 600 --days 1 --no-llm --port 5080 `
      --scenario ./samples/ch10_scenario/plague.jsonl

PS> ./samples/ch02_watch/watch-npc.ps1 -Npc 7 -Seconds 120
at_tick 120 근처에서 plan #… -> #… 줄이 뜨면 그게 전환이다.

부러뜨려 본다

바꿔 보기결과왜
존 이름에 오타 (riverside → riverisde) 조용히 무시된다 대본은 검증기를 안 거친다. 가장 조심할 지점 — 대본을 쓰면 반드시 지표로 확인한다
배속만 60으로 바꾼다 사건이 10배 이른 시각에 at_tick 은 배속에 묶여 있다. 환산표를 다시 뽑는다
at_tick 을 하루 밖으로 (예: 99999) 아무 일도 안 일어난다 --days 1 이면 1,440틱에서 끝난다
같은 틱에 이벤트 100줄 여전히 이월 0 한 틱 이벤트 상한에 걸리면 다음 틱으로 넘긴다 — 밀리지 사라지지 않는다
