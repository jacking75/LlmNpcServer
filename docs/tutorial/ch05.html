왜 items 가 먼저인가

4장의 지도에서 화살표는 items → pois 방향이었다. POI 는 resources 로 아이템을 가리키기 때문이다. 거꾸로 하면 이렇게 된다.

순서를 거꾸로 했을 때 
# pois.json 에 resources: ["honey"] 를 먼저 넣고 검증하면
FAIL V3  pois.json: apiary_001_12 가 없는 아이템 'honey' 을 낸다.

검증기가 막아 주니 사고가 나지는 않는다. 다만 되돌아오는 시간이 든다. 순서를 지키는 이유는 안전이 아니라 속도다.

① 아이템 — honey

masterdata/items.json
    { "id": "map",            "code": 82, "category": "product", "grants": ["HasProduct"], "stack": 10 },
    { "id": "honey",          "code": 83, "category": "raw",     "grants": ["HasRawMaterial"], "stack": 30 }
  ],
필드뜻고를 때
code배열 첨자. 재배치 금지, 추가는 뒤에만지금 최대가 82니까 83
categoryraw·product·food·drink·tool·weapon·currency벌통에서 거두는 것이니 raw
grants이 파일의 핵심. 이 아이템을 가지면 서는 플래그HasRawMaterial
stack한 칸에 몇 개까지30
grants 가 왜 핵심인가 코드 어디에도 "빵을 가지면 HasFood" 같은 규칙이 없다. 인벤토리 변경 이벤트를 받으면 그 NPC 가 가진 아이템들의 grants 를 전부 OR 해서 WorldFlags 를 다시 계산할 뿐이다. 그래서 아이템을 추가하는 것만으로 새로운 행동 조건이 생긴다 — 코드를 한 줄도 안 고치고.

② 장소 — 양봉장 둘

masterdata/pois.json
    {
      "id": "apiary_001_12",
      "code": 244,
      "zone": "highland_pasture",
      "type": "field",
      "subtype": "apiary",
      "pos": { "x": -420.0, "y": 0.0, "z": -980.0 },
      "capacity": 12,
      "open_hours": { "from": "Dawn", "to": "Evening" },
      "grants": ["AtField"],
      "allowed_archetypes": ["shepherd", "herbalist"],
      "resources": ["honey"]
    },
필드왜 이 값인가
code 244 · 2451부터 연속이어야 한다. 거리표의 첨자가 code - 1 이다
type field기존 pasture·farm 과 같은 부류. $nearest_field 심볼이 여기로 풀린다
subtype apiary새 subtype 이다. 7장에서 양봉가의 workplace_poi_type 이 된다
grants AtField도착하면 서는 플래그. Gather 가 요구하는 것이 이것이다
capacity 12동시에 몇 명까지. 둘이면 24명 — V10 이 이 총합을 본다
resources honey여기서 무엇을 거둘 수 있나. ①에서 만든 아이템이라야 한다 (V3)
왜 grants 가 AtApiary 가 아닌가 월드 플래그는 64비트 고정이고 지금 42개를 쓴다(bit 0~43 중 22·23은 예약). 장소 종류마다 비트를 하나씩 주면 금방 바닥난다. 그래서 플래그는 부류(AtField·AtWorkplace·AtMarket…)만 두고, 구체적인 장소는 POI id 로 구분한다. 새 장소를 만들 때 플래그를 새로 만들 필요는 거의 없다 — 그게 이 설계의 의도다.

③ 거리표를 다시 굽는다

poi_distances.bin 은 N×N 행렬이다. POI 가 243개면 243×243, 245개가 되면 245×245여야 한다. 손으로 못 고치고 생성기를 돌린다.

터미널 
PS> cd lab/ch05
PS> dotnet run ../../tools/gen_poi_distances.cs

poi_distances.bin: POI 245개 · 120,058 bytes (117.2 KB) · 최대 거리 5241.0m
생성기가 왜 실습장 안에서 도는가 gen_poi_distances.cs 는 --masterdata 인자를 안 받는다. NpcServer.sln 이 있는 폴더를 위로 찾아 올라가 그 아래 masterdata/ 를 읽는다.

그래서 0장의 lab.ps1 이 실습장마다 같은 이름의 빈 파일을 하나 둔다. 그러면 실습장이 작은 저장소 루트가 되고, 생성기가 원본이 아니라 사본을 고친다. patch.ps1 이 이 트릭에 기대고 있다.

가장 중요한 확인 commands 는 같은데 events 와 timeouts 는 다르다. 플랜(무엇을 할까)은 안 바뀌었고 세계(어디까지 얼마나 걸리나)만 바뀌었기 때문이다. 이 구분이 이 제품의 뼈대다 — 플랜은 L1 캐시에 있고 세계는 게임서버에 있다.
  • validate 가 아이템 83 · POI 245 로 올라간다
  • poi_distances.bin 이 245개 기준으로 다시 구워진다
  • content_hash 가 f37c0292… 에서 바뀐다
  • 확인 3단 6항목이 전부 OK
  • 원본 masterdata/ 는 그대로다 — git status 가 깨끗하다
