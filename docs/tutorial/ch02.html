1부 · 일단 켠다

2장 · NPC 한 마리를 끝까지 따라간다

1장에서는 수천 건의 명령을 봤다. 이번에는 그중 한 마리를 찍어서 왜 저기로 가는가에 답한다. 관측 엔드포인트 네 개를 읽고, 변화만 찍어 주는 추적기를 40줄로 만든다.

난이도 ★☆☆☆ 30분 LLM 불필요 OS 무관 터미널 2개

무엇을 만드나

GET /npc/7 을 주기적으로 읽어서 바뀐 것만 한 줄로 찍는 스크립트다. 전부 찍으면 초당 수십 줄이라 아무것도 안 보인다. 변화만 남기면 하루가 30줄로 줄어든다.

먼저 — /npc/{id} 가 무엇을 주나

1장의 실행을 다시 띄우고, 터미널을 하나 더 열어 한 마리를 찍어 본다.

터미널 1 — 배속을 60으로 낮춰서 띄운다 
PS> dotnet run -c Release --project src/Npc.Host -- `
      --loopback --npcs 20 --time-scale 60 --days 1 --no-llm --port 5080
1장과 다른 점 하나 — 배속 1장은 --time-scale 600 이었다. 이번엔 60 이다. 배속 600에서는 1틱이 게임 60초라 timeout_s: 300 인 스텝이 5틱이면 만료된다 — 스텝이 자연스럽게 끝나는 게 아니라 계속 타임아웃으로 넘어가서, 관찰하면 NPC 가 안절부절 못하는 것처럼 보인다. 배속 60이면 1틱이 게임 6초라 이동이 실제로 완료된다.

대신 게임 하루가 실시간 24분이다. 끝까지 볼 필요는 없다 — 몇 분만 보고 Ctrl-C 한다.
터미널 2 — 한 마리를 찍는다 
PS> Invoke-RestMethod http://localhost:5080/npc/7 | ConvertTo-Json -Depth 5

돌아오는 것을 네 덩어리로 끊어 읽는다.

① 이 NPC 는 누구인가

homePoi 와 workPoi 가 중요하다. 플랜에는 house_002_12 같은 구체적 이름이 없고 $home·$workplace 같은 심볼만 있다. 같은 플랜 하나를 목동 수백 명이 공유하고, 각자의 집으로 알아서 간다. 이 심볼 치환이 플랜 캐시를 성립시키는 장치다 → 6장에서 직접 쓴다.

전부 fallback 으로 보여도 정상이다 planstore/plans/ 는 생성물이라 .gitignore 대상이다. 저장소를 새로 받았으면 비어 있고, 그러면 모든 NPC 가 fallback 이다. NPC 는 똑같이 하루를 산다 — 행동이 덜 다양할 뿐이다. bucket 을 보고 싶으면 17장에서 직접 구우면 된다.

PlanStore.Resolve 는 절대 null 을 반환하지 않는다. 캐시가 비어도, LLM 이 전부 죽어도, 플랜 조회는 반드시 무언가를 돌려준다. 그래서 "LLM 전면 차단" 시나리오가 통과한다 → 11장

flags 가 이 세계의 어휘다. 액션마다 전제조건이 있고, 그 전제조건은 전부 이 플래그로 쓰여 있다. masterdata/actions.json 에서 세 개만 꺼내 보면 이렇다.

그래서 위 로그에서 MoveTo(NearestField) 다음에 곧바로 flags +AtField 가 서고, 그제서야 Gather 가 돌아간다. 플래그가 안 서 있으면 그 스텝은 실행되지 않는다. 이 표를 사람이 손으로 쓰는 것이 6장이고, LLM 이 이 표를 보고 플랜을 짜는 것이 8장이다.

recent 는 자연어 요약이 아니라 값 8개짜리 링 버퍼다. "어제 대장장이와 싸웠다" 같은 문장이 아니라 (Kind, At, Subject, Salience) 구조체다. LLM 프롬프트에 실릴 때 300토큰 예산 안에 들어가야 하기 때문이다. 중요도(salience)가 낮은 것부터 밀려난다.

추적기를 만든다

한 번 찍어 보는 것으로는 변화가 안 보인다. 폴링해서 달라진 것만 찍자. 전체 코드는 samples/ch02_watch/watch-npc.ps1 이고 약 200줄인데, 핵심은 이 모양이다.

samples/ch02_watch/watch-npc.ps1 — 뼈대 
$prev = $null

while ($true) {
    $t = Invoke-RestMethod "$BaseUrl/npc/$Npc"

    if ($prev) {
        $changes = @()

        # ① 스텝이 넘어갔나
        $ps = Get-CurrentStep $prev
        $cs = Get-CurrentStep $t
        if ((Format-Step $ps) -ne (Format-Step $cs)) {
            $changes += "step $(Format-Step $ps) -> $(Format-Step $cs)"
        }

        # ② 플랜이 갈렸나 — 이 줄이 이 스크립트의 핵심이다
        if ($prev.planId -ne $t.planId -or $prev.planKind -ne $t.planKind) {
            $changes += "plan #$($prev.planId)[$($prev.planKind)] -> #$($t.planId)[$($t.planKind)]"
        }

        # ③ 플래그가 서거나 졌나 — 집합 차이로 구한다
        $gone = @($prev.flags | Where-Object { $t.flags -notcontains $_ })
        $came = @($t.flags   | Where-Object { $prev.flags -notcontains $_ })

        # ④ 인벤토리 증감 — "wool × 115" 를 파싱해 델타로
        # ⑤ 존 · POI 이동

        foreach ($c in $changes) { Write-Host "[t=$($t.tick)] $c" }
    }

    $prev = $t
    Start-Sleep -Milliseconds $IntervalMs
}
왜 폴링인가 /npc/{id} 는 SoA 배열을 읽기만 하고 값을 복사해 나간다. 락도 없고 쓰기도 없다. 한 틱 낡은 값을 볼 수 있지만 추적에는 그걸로 충분하다 — 다음 폴링에 새 값이 온다. 락을 잡으면 그 자체가 틱 예산을 먹는다. 관찰이 관찰 대상을 느리게 만들면 안 된다.

같은 이유로 개별 플랜은 LRU 를 갱신하지 않고 들여다본다. 대시보드를 열어 둔 것만으로 게임 상태가 달라지면 안 되기 때문이다.
터미널 2 — 추적 시작 
PS> ./samples/ch02_watch/watch-npc.ps1 -Npc 7 -Seconds 40

이 로그에서 볼 것 넷

  1. 플랜이 실제로 실행된다

    0 MoveTo → 1 Gather → 2 Gather → 3 MoveTo(Home) → 4 Store 순서로 스텝이 넘어간다. 목동이 목초지로 가서 · 양털과 우유를 모으고 · 집에 가서 · 저장하고 · 다시 나간다. 아무도 이 시나리오를 손으로 쓰지 않았다 — LLM 이 만든 플랜이고, 런타임은 그것을 첨자로 조회해 실행할 뿐이다.

  2. 상태 변화가 스텝 완료 직후에만 일어난다

    [t=5010] 을 보면 세 줄이 같은 틱이다 — 스텝 전진 · POI 이동 · 플래그 변화가 한 덩어리로 일어난다. 틱 중간에 상태가 흔들리는 일이 없다. 이것이 스텝 경계다.

  3. 플랜 교체도 스텝 경계에서만 일어난다 확인 포인트

    [t=5181] 과 [t=5267] 두 번 플랜이 갈렸는데, 두 번 다 스텝 전진과 같은 틱이다. 우연이 아니라 규칙이다 — 스텝 중간에 플랜을 바꾸면 이미 보낸 명령의 상관 ID 가 꼬인다. (예외는 인터럽트뿐이다. 그건 즉시 갈아탄다 → 8장)
    무엇이 이 교체를 일으켰는지는 6·9장의 주제다. 여기서는 "경계에서만 갈린다"만 확인한다.

  4. PlayerNearby 가 섰다 졌다 한다

    가상 플레이어 봇(--player-bots, 기본 20)이 돌아다니면서 근처를 스칠 때마다 플래그가 선다. 이 플래그가 인지 LOD 등급을 올리고, 등급이 올라가면 재계획 우선순위가 올라간다. 티어를 켜면 이 NPC 가 개별 플랜을 받을 후보가 된다 → 16장
    --player-bots 0 으로 돌리면 이 줄이 하나도 안 나온다.

배속이 관찰을 바꾼다

1장의 배속 600으로 같은 NPC 를 보면 완전히 다른 로그가 나온다. 같은 코드, 같은 플랜인데도.

실측 — 같은 NPC, 배속 600 
[t=   100] step 1 Gather -> 3 Trade        // 스텝 2를 건너뛰었다
[t=   106] step 3 Trade -> 0 MoveTo(NearestField)
[t=   112] step 0 MoveTo(NearestField) -> 1 Gather
[t=   118] step 1 Gather -> 2 MoveTo(Market)
[t=   124] step 2 MoveTo(Market) -> 4 MoveTo(Home)  // 스텝 3을 건너뛰었다
왜 스텝을 건너뛰나 배속 600에서 1틱 = 게임 60초다. timeout_s: 300 인 MoveTo 는 5틱이면 만료된다. 게임서버 대역이 목적지에 도착시키기 전에 시간이 먼저 지나가고, NPC 서버는 ActionFailed(Timeout) 을 합성한다. 폴백 플랜의 on_step_fail 이 skip 이므로 그 스텝을 건너뛰고 다음으로 간다.

버그가 아니라 설계다. 명령은 유실된다고 가정하고 만들었고, 배속을 올리는 것은 그 가정을 인위적으로 자주 성립시키는 일이다. 다만 관찰용으로는 못 쓴다 — NPC 의 하루를 보려면 배속 60쯤이 맞다.

bytesPerTick: 0 틱 루프를 재는 계기는 이것 하나뿐이다. gen0Collections 로 재면 안 된다 — 그 값은 프로세스 전역이라 대시보드 HTTP·소켓·JSON 직렬화가 전부 섞인다
byLod: [0,11,0,9] 인지 LOD 밴드별 인원. 첨자가 곧 밴드다 — 0 시야내(매 틱) · 1 동일존(10틱마다) · 2 원거리(100틱마다) · 3 비활성(안 봄). 플레이어 근처에 아무도 없으면 0번이 비고, 그게 정상이다
byStepStatus: [0,20,0,…] 첨자가 곧 상태다 — 0 Ready · 1 Waiting · 2 Done · 3 Unspawned · 4 Completed · 5 Failed. 20마리 전원이 Waiting, 즉 응답을 기다리는 중이다. 정상 구동의 기본 모습이다

확인한다

  • 추적기 머리말에 아키타입 · 집 · 일터 · 플랜 · 스텝 목록이 전부 나온다
  • 스텝이 0 → 1 → 2 → … 순으로 차례로 넘어간다 (배속 60에서)
  • 스텝 전진 · POI 이동 · 플래그 변화가 같은 틱에 묶여 나온다
  • plan #… -> #… 줄이 나온다면 반드시 step 줄과 같은 틱이다
  • 인벤토리 증감이 Gather·Store 스텝 직후에만 찍힌다
  • /metrics 의 byLod 합과 byStepStatus 합이 둘 다 total 과 같다

부러뜨려 본다

① 없는 NPC 를 물어본다

터미널 
PS> Invoke-RestMethod http://127.0.0.1:5080/npc/999 | ConvertTo-Json -Compress

{"found":false,"npc":999,"tick":4535,"archetype":null,"zone":null,"poi":null,
 "planId":0,"planKind":null,"flags":null,"steps":null,"recent":null}

PS> ./samples/ch02_watch/watch-npc.ps1 -Npc 999
그 첨자에 NPC 가 없다: 999 (--npcs 보다 작아야 한다)

500 이 아니라 200 에 found: false 다. "없는 것을 물어보는 것"은 오류가 아니라 정상적인 질문이기 때문이다. 대시보드가 첨자를 넘겨 가며 훑을 때 예외로 죽으면 안 된다.

첨자는 0 부터 --npcs - 1 까지다. 이 값은 NpcStore 배열의 인덱스이지 게임 세계의 영구 ID 가 아니다 — 그래서 양쪽 프로세스의 --npcs 가 같아야 한다. 3장에서 이 첨자를 어긋내면 무슨 일이 나는지 직접 본다.

잘 안 될 때 하나 localhost 로 요청이 몇십 초씩 걸리면 127.0.0.1 로 바꿔 본다. 일부 환경에서 localhost 가 IPv6(::1)부터 시도하다 지연된다. 추적기도 -BaseUrl http://127.0.0.1:5080 을 받는다.

② 플레이어를 없애 본다

터미널 1 
PS> dotnet run -c Release --project src/Npc.Host -- `
      --loopback --npcs 20 --time-scale 60 --days 1 --no-llm --port 5080 --player-bots 0
터미널 2 — 실측 
PS> $m = Invoke-RestMethod http://127.0.0.1:5083/metrics
PS> "byLod       : " + ($m.npc.byLod -join ', ')
PS> "scanPerTick : " + $m.replan.scanPerTick

byLod        : 0, 0, 0, 20      // 20마리 전원이 마지막 칸(비활성)
byStepStatus : 0, 20, 0, 0, 0, 0, 0, 0
scanPerTick  : 0               // 인지 스캔이 아예 안 돈다

추적 로그에서 PlayerNearby 줄이 완전히 사라진다. byLod 는 [0, 0, 0, 20] — 전원이 비활성 밴드로 몰렸고, scanPerTick 은 0 이다. 아무도 안 보고 있으니 아무도 볼 필요가 없다.

그런데 행동은 안 바뀐다 1장의 대조 실험에서 봤듯이 --player-bots 0 회차의 명령·스텝·타임아웃은 기준선과 한 건도 다르지 않다. 인지 스캔은 누구를 재계획 대상으로 고를까만 정하는데, --tier none 에서는 재계획 자체가 없기 때문이다. 16장에서 티어를 켜면 이 두 회차가 처음으로 갈라진다.
