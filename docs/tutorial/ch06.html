LLM이 만드는 것과 똑같은 자료구조를 사람이 직접 쓴다. 2장에서 따라다닌 그 목동의 하루를 6스텝에서 10스텝으로 다시 쓰고, 일부러 네 가지로 틀리게 써서 검증기 4단이 각각 어디서 잡는지 본다.

이 장이 끝나면 — 2장의 추적기가 내가 쓴 스텝을 찍는다 
npc #7  shepherd
  플랜 #17 [fallback]  goal=graze_store_and_sell  loop=True
  스텝
    0. MoveTo -> NearestField   timeout 600s
    1. Gather x5   timeout 900s
    2. Gather x5   timeout 900s
    3. MoveTo -> Home   timeout 600s
    4. Store x5   timeout 300s
    5. Eat   timeout 300s
    6. MoveTo -> Market   timeout 600s
    7. Trade x5   timeout 600s
    8. MoveTo -> Home   timeout 600s
    9. Sleep   timeout 7200s
이 장의 한 문장 플랜은 스텝 배열 하나다. LLM 이 만드는 것도 이것이고, 사람이 쓰는 것도 이것이고, 캐시에 들어가는 것도 이것이다. 이 장을 하고 나면 8장 이후의 LLM 출력이 낯설지 않다.

플랜의 문법

samples/ch06_plan/fb_shepherd_v2.json
{
  "id": "fb_shepherd",
  "archetype": "shepherd",
  "goal": "graze_store_and_sell",
  "steps": [
    { "action": "MoveTo", "args": { "poi": "$nearest_field" },        "timeout_s": 600 },
    { "action": "Gather", "args": { "resource": "wool", "count": 5 },  "timeout_s": 900 },
    { "action": "Gather", "args": { "resource": "milk", "count": 5 },  "timeout_s": 900 },
    { "action": "MoveTo", "args": { "poi": "$home" },                "timeout_s": 600 },
    { "action": "Store",  "args": { "item": "milk", "count": 5 },      "timeout_s": 300 },
    { "action": "Eat",    "args": {},                                  "timeout_s": 300 },
    { "action": "MoveTo", "args": { "poi": "$market" },              "timeout_s": 600 },
    { "action": "Trade",  "args": { "item": "wool", "amount": 5 },     "timeout_s": 600 },
    { "action": "MoveTo", "args": { "poi": "$home" },                  "timeout_s": 600 },
    { "action": "Sleep",  "args": { "until_time": "Morning" },         "timeout_s": 7200 }
  ],
  "on_step_fail": "skip",
  "loop": true
}
필드뜻규칙
id플랜 이름아키타입의 fallback_plan 이 이 값을 가리킨다 (V7)
goal이 플랜이 무엇을 위한 것인가추적기와 Npc.Narrate 가 그대로 보여 준다
steps[].action액션 카탈로그의 id그 아키타입의 allowed_actions 안에 있어야 한다 (V8)
steps[].args액션의 params 대로actions.json 이 정한 이름·타입·범위
steps[].timeout_s응답이 없으면 이만큼 뒤에 실패로 친다모든 스텝에 있다. 명령은 유실되니까
on_step_failskip · abort · retry폴백은 skip 이다. 폴백에서 또 폴백으로 갈 곳이 없다
loop끝나면 처음으로 돌아가나폴백은 반드시 true (V7)

심볼 — 플랜 하나를 수백 명이 공유하는 장치

플랜에 house_002_12 같은 구체적 이름이 없다. $home 뿐이다.

심볼무엇으로 풀리나도착하면 서는 플래그
$homeNPC 인스턴스의 home_poiAtHome
$workplaceNPC 인스턴스의 workplace_poiAtWorkplace
$nearest_field가장 가까운 type: field POIAtField
$market · $nearest_safe · …부류별 최근접그 POI 의 grants
이것이 캐시를 성립시킨다 같은 플랜 하나를 목동 125명이 공유하고, 각자 자기 집·자기 목초지로 간다. 심볼이 없으면 NPC 마다 다른 플랜이 필요하고, 그러면 캐시가 성립하지 않는다. 플랜 2,880개로 NPC 5,000마리를 돌리는 근거가 이 한 줄이다.

여기서 볼 것 셋

  1. 내가 쓴 그대로 돈다

    goal 이름도, 스텝 목록도, timeout_s 도 파일에 쓴 값 그대로다. 런타임은 이 배열을 첨자로 읽어 실행할 뿐 아무것도 해석하지 않는다.

  2. 스텝을 건너뛴다 3 → 6 · 3 → 5 · 6 → 8

    on_step_fail: "skip" 이기 때문이다. Store 나 Trade 가 실패하면 그 스텝을 버리고 다음으로 간다.
    왜 실패하나? Trade 는 HasProduct 나 HasCoin 중 하나를 요구하는데 양털은 raw 라 HasProduct 를 안 세운다. 코인이 떨어지면 팔 수가 없다. 이런 것이 플랜을 손으로 쓸 때 걸리는 함정이고, 그래서 돌려 봐야 한다.

  3. 인벤토리가 스텝 완료 직후에만 움직인다

    Gather 가 끝난 틱에 milk +5. 틱 중간에 슬금슬금 오르지 않는다. 상태 변화는 전부 스텝 경계에서 원자적으로 일어난다.

실측 — 네 개가 서로 다른 층에서 걸린다 
// ① 허용 안 된 액션 — 마스터데이터 규칙
FAIL V8  fallback_plans.json: 'fb_shepherd' 이 shepherd 에게 허용되지 않은 액션 'Mine' 을 쓴다.

// ② 순환하지 않는 폴백 — 마스터데이터 규칙
FAIL V7  fallback_plans.json: 'fb_shepherd' 이 loop:true 가 아니다. 폴백은 무한히 지속 가능해야 한다.

// ③ 스텝이 11개 — 플랜 검증기 1단 (Schema)
FAIL LOAD  fallback_plans.json: 'fb_shepherd' 이 검증기 Schema 단에서 걸렸다.
           V1.STEP_COUNT (스텝 -1): 스텝이 11개다. 3~10 이어야 한다.

// ④ 전제조건 불성립 — 플랜 검증기 3단 (Coherence)
FAIL LOAD  fallback_plans.json: 'fb_shepherd' 이 검증기 Coherence 단에서 걸렸다.
           V3.PRECONDITION_UNMET (스텝 0): Gather requires AtField but no preceding step
           grants it. Insert a MoveTo step with poi $nearest_field before it.
           State before this step: HasFood|HasWater|HasTool|HasCoin|IsDay|RegionPeaceful.

플랜 검증기 4단

단계무엇을 보는가대표 실패
1 Schema모양이 맞나 — 스텝 수, 필수 필드, 값 범위V1.STEP_COUNT
2 Vocabulary쓴 이름이 실재하나 — 액션·아이템·POI 심볼V2.UNKNOWN_ACTION
3 Coherence이 순서로 실제 가능한가 — GOAP 시뮬로 플래그를 굴려 본다V3.PRECONDITION_UNMET
4 DryRunSim 월드에서 실제로 완주하나도달 불가 · 정원 초과
④번 메시지를 다시 읽는다 "Insert a MoveTo step with poi $nearest_field before it."
이건 사람에게만 하는 말이 아니다. LLM 이 실패했을 때 재시도 프롬프트에 그대로 실리는 문장이다. 검증기가 "틀렸다"가 아니라 "이렇게 고쳐라"까지 말하도록 만든 이유가 그것이다 — 재시도 1회로 통과율을 끌어올리려면 피드백이 구체적이어야 한다. 18장에서 다시 만난다.
스텝 3~10 이라는 상한

11스텝 플랜을 쓰면 Schema 단에서 거절된다. 왜 10인가 — 스텝이 길수록 LLM 출력이 길어지고(비용), 중간에 하나만 실패해도 뒤가 다 무너지고(견고성), 상황이 바뀌면 통째로 버려진다(재계획 낭비).

하루를 다 담고 싶으면 스텝을 늘리는 게 아니라 loop: true 로 반복시키고 시간대별로 다른 버킷 플랜을 쓰는 것이 이 설계의 답이다. 아침 플랜과 저녁 플랜은 애초에 다른 캐시 키다.

사람 말로 읽어 본다

플랜이 의도대로 읽히는지는 JSON 을 노려봐서는 알기 어렵다. Npc.Narrate 가 기록을 사람 말로 풀어 준다.

터미널 
# ① 링크를 기록하며 돌린다
PS> dotnet run -c Release --project src/Npc.Host -- `
      --link record --trace ./lab/ch06/day1.jsonl `
      --npcs 20 --time-scale 60 --days 1 --no-llm --max-speed --no-dashboard `
      --planstore ./nonexistent --masterdata C:\…\lab\ch06\masterdata

# ② 사람 말로 푼다
PS> dotnet run -c Release --project tools/Npc.Narrate -- `
      --trace ./lab/ch06/day1.jsonl --npc 7 --time-scale 60 --population 20

읽어서 말이 되면 성공이다. 이 도구가 "플랜을 사람이 검수할 수 있다"의 실물이고, 18장에서 LLM 이 만든 플랜을 검수할 때 같은 도구를 쓴다.

확인한다

  • apply.ps1 (변형 없이) 이 검증 통과 로 끝난다
  • 추적기 머리말의 스텝 목록이 내가 쓴 그대로다
  • goal 이 graze_store_and_sell 로 보인다
  • 변형 4종이 각각 V8 · V7 · Schema · Coherence 에서 걸린다
  • Coherence 메시지가 고치는 방법까지 알려 준다
