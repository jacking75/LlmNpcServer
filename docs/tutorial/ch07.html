왜 코드를 건드리게 되는가

플랜 캐시의 키는 (아키타입 × 시간대 × 지역상태 × 기후) 네 축이다. 그리고 조회는 해시맵이 아니라 배열 첨자 하나다.

src/Npc.Core/Planning/BucketKey.cs
public const int ArchetypeCount = 40;
public const int TimeOfDayCount = 6;
public const int RegionStateCount = 4;
public const int ClimateCount = 3;

/// 전체 키 수. 40 × 6 × 4 × 3.
public const int TotalKeys = ArchetypeCount * TimeOfDayCount * RegionStateCount * ClimateCount;

/// 0..2879. 전단사다.
public int ToIndex() => ((((A.Value * 6) + (int)T) * 4) + (int)R) * 3 + (int)C;
이 한 줄이 성능의 근거다 PlanStore 는 CompiledPlan[2880] 고정 배열이면 충분하다. 틱 루프에서 플랜을 찾는 비용이 곱셈 세 번과 덧셈 세 번이고, 해시도 락도 할당도 없다. 1장에서 본 틱당 할당 0바이트의 일부가 여기서 나온다.

대가는 아키타입 수가 컴파일 타임에 고정된다는 것이다. 늘리려면 다시 컴파일해야 한다. 이것이 이 설계가 명시적으로 치른 값이고, 7장은 그 값을 실제로 치러 보는 장이다.

code 를 중간에 끼우면 안 되는 이유

code 는 버킷 첨자의 최상위 자리다. 41번째를 40이 아니라 가운데(예: 5)에 끼워 넣고 뒤를 밀면, 첨자 ((5×6+T)×4+R)×3+C 가 가리키던 플랜이 전부 다른 직업의 것이 된다.

미리 구워 둔 플랜 2,880개가 통째로 어긋난다. 그리고 증상은 크래시가 아니라 "대장장이가 밭을 간다"다 — 오류 하나 없이 잘못된 세계가 돈다. 추가는 언제나 뒤에만.

여기서 한 번 걸렸다 — $workplace vs $nearest_field

처음엔 첫 스텝을 $workplace 로 썼다. 양봉가의 일터는 양봉장이니 자연스러워 보인다. 그런데 검증기가 막았다. 

V3.PRECONDITION_UNMET (스텝 1): Gather requires AtField but no preceding step grants it.
State before this step: AtWorkplace|HasFood|HasWater|HasCoin|IsDay|RegionPeaceful.

Coherence 단은 $workplace → AtWorkplace, $nearest_field → AtField 로 모델링한다. 양봉장 POI 가 AtField 를 grants 하더라도, 검증기의 시뮬은 심볼 종류로 판정한다. 그래서 $nearest_field 로 바꿨다.

검증기가 실제보다 보수적인 지점이다. 이런 곳은 검증기를 고치는 게 아니라 플랜을 검증기가 읽을 수 있게 쓰는 쪽이 싸다 — LLM 도 같은 제약 아래서 쓴다.

이것은 고장이 아니라 계산서다

테스트들이 40·2880·"폴백 40" 을 하드코딩하고 있다. "테스트가 사양이다" 라는 원칙의 뒷면이다 — 사양을 바꾸면 사양서도 같이 고쳐야 한다.

이름들을 보면 아키타입 수가 어디까지 퍼져 있는지가 한눈에 보인다: 마스터데이터 · 버킷 키 · 플랜 스토어 · 대시보드 히트맵 · 프리베이크 대상 선정 · 프롬프트 서픽스 예산 · 서술 도구의 어휘집. 이 목록이 곧 "아키타입 하나 추가"의 실제 범위다.

그래서 실무에서는 아키타입 추가는 가벼운 콘텐츠 작업이 아니라 스키마 변경이다. 40개 안에서 desc·traits·allowed_actions·기본 goal 을 바꾸는 것으로 해결되는지 먼저 본다. 기존 직업의 성격을 바꾸는 것은 JSON 한 파일이고 테스트가 하나도 안 깨진다. 정말로 41번째가 필요할 때만 이 장의 절차를 밟는다.
