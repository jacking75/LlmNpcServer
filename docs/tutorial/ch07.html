아키타입 수는 어디서 오나

플랜 캐시의 키는 (아키타입 × 시간대 × 지역상태 × 기후) 네 축이다. 그리고 조회는 해시맵이 아니라 배열 첨자 하나다.

src/Npc.Core/Planning/BucketKey.cs
public const int TimeOfDayCount = 6;
public const int RegionStateCount = 4;
public const int ClimateCount = 3;

/// 한 아키타입이 갖는 버킷 수. 6 × 4 × 3 = 72. 아키타입 수와 무관하다.
public const int PerArchetype = TimeOfDayCount * RegionStateCount * ClimateCount;

/// 첨자. 전단사다. 이 식에 아키타입 수가 들어가지 않는다.
public int ToIndex() => ((((A.Value * 6) + (int)T) * 4) + (int)R) * 3 + (int)C;
src/Npc.MasterData/MasterDataSet.cs — BucketSpace
/// 아키타입 수. archetypes.json 이 정한다.
public int ArchetypeCount { get; }

/// 전체 버킷 키 수. 아키타입 수 × 72.
public int TotalKeys => ArchetypeCount * BucketKey.PerArchetype;
이 한 줄이 성능의 근거다 PlanStore 는 CompiledPlan[TotalKeys] 고정 배열이면 충분하다. 틱 루프에서 플랜을 찾는 비용이 곱셈 세 번과 덧셈 세 번이고, 해시도 락도 할당도 없다. 1장에서 본 틱당 할당 0바이트의 일부가 여기서 나온다.

배열 길이는 기동 시 한 번 잡는다. 틱 루프는 첨자로만 읽으므로, 길이가 데이터에서 오더라도 조회 비용은 그대로다.
예전에는 코드를 고쳐야 했다

BucketKey.ArchetypeCount = 40 이라는 컴파일 상수였다. 아키타입 하나를 넣으려면 C# 을 고치고 다시 빌드해야 했고, 파일은 41 인데 바이너리가 40 인 상태가 되면 41번째 직업의 버킷 72칸이 조용히 사라졌다 — 가장 찾기 어려운 종류의 오류다.

F-05 에서 상수를 없앴다. 기존 첨자는 변하지 않는다 — 아키타입이 가장 바깥 차원이라 뒤에 붙는 것은 뒤에만 자리를 만든다. 그래서 프리베이크된 플랜 2,880개가 첨자 때문에 깨지는 일은 없다.

권장 상한은 128, 하드 상한은 npc_ref payload 12비트가 정하는 4,096 이다. 실질 제약은 둘 다 아니고 프롬프트 프리픽스의 토큰 비용이다 — 아키타입 카탈로그가 프리픽스에 전부 실린다(실측 11,967 토큰 · 아키타입 40).

code 를 중간에 끼우면 안 되는 이유

code 는 버킷 첨자의 최상위 자리다. 41번째를 40이 아니라 가운데(예: 5)에 끼워 넣고 뒤를 밀면, 첨자 ((5×6+T)×4+R)×3+C 가 가리키던 플랜이 전부 다른 직업의 것이 된다.

미리 구워 둔 플랜 2,880개가 통째로 어긋난다. 그리고 증상은 크래시가 아니라 "대장장이가 밭을 간다"다 — 오류 하나 없이 잘못된 세계가 돈다. 추가는 언제나 뒤에만.

여기서 한 번 걸렸다 — $workplace vs $nearest_field

처음엔 첫 스텝을 $workplace 로 썼다. 양봉가의 일터는 양봉장이니 자연스러워 보인다. 그런데 검증기가 막았다. 

V3.PRECONDITION_UNMET (스텝 1): Gather requires AtField but no preceding step grants it.
State before this step: AtWorkplace|HasFood|HasWater|HasCoin|IsDay|RegionPeaceful.

Coherence 단은 $workplace → AtWorkplace, $nearest_field → AtField 로 모델링한다. 양봉장 POI 가 AtField 를 grants 하더라도, 검증기의 시뮬은 심볼 종류로 판정한다. 그래서 $nearest_field 로 바꿨다.

검증기가 실제보다 보수적인 지점이다. 이런 곳은 검증기를 고치는 게 아니라 플랜을 검증기가 읽을 수 있게 쓰는 쪽이 싸다 — LLM 도 같은 제약 아래서 쓴다.

치러야 할 진짜 대가 — 프리베이크 전량

검증도 통과했고 세계도 돈다. 테스트도 안 깨진다 — 코드를 고치지 않았고, 테스트가 아키타입 수를 TestPaths.ArchetypeCount 로 읽기 때문이다.

실측 
PS> dotnet test -c Release --no-build "--filter" "Category!=Golden&Category!=Gate&Category!=Load"

통과!  - 실패: 0, 통과: 1284, 전체: 1284
그런데 플랜 스토어는 전량 무효다

아키타입 카탈로그는 프롬프트 프리픽스에 실린다. 양봉가를 넣으면 프리픽스가 바뀌고, 프리픽스 SHA-256 이 바뀌면 프리베이크된 플랜 2,880개가 전부 무효다 — 다른 어휘로 만들어진 플랜이기 때문이다.

첨자가 아니라 내용의 문제다. F-05 가 없앤 것은 첨자 파손이고, 프리픽스 무효화는 여전히 남는 대가다. 

프리픽스   변경 (+81 tok, SHA 56a0c601→…) → 플랜 스토어 전량 무효
프리베이크 2,952건 · 추정 $5.25 · 약 3분 (도달집합만 하면 $0.38)
따라오는 것왜비용
poi_distances.bin 재생성POI 둘이 늘었다수 초
npc_instances.json 재생성인구 분포가 바뀌었다수 초
프리베이크프리픽스 해시 변경 → 전량 무효2,952건 · 약 $5.25
게임서버 재배포구조 해시 변경 → 핸드셰이크 거절배포 1회
코드 수정—없다 (F-05)
그래서 실무에서는 아키타입 추가는 가벼운 콘텐츠 작업이 아니라 재배포 + 재생성 작업이다. 기존 40개 안에서 desc · traits · allowed_actions · 기본 goal 을 바꾸는 것으로 해결되는지 먼저 본다 — 그쪽도 프리픽스를 건드리면 같은 대가를 치르지만, desc 만 고치는 것과 카탈로그에 항목을 더하는 것은 토큰 증가폭이 다르다. 정말로 41번째가 필요할 때만 이 장의 절차를 밟는다.
