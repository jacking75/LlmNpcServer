8장 · 반사신경을 넣는다 — 인터럽트

LLM이 절대 손대지 않는 영역이다. 반응 속도가 필요한 판정은 전부 결정론 규칙으로 짠다. "폭풍이 오면 밭에 있던 사람은 즉시 집으로" 규칙을 하나 넣고, 시나리오로 폭풍을 때려 발동을 숫자로 확인한다.

난이도 ★★★☆ 50분 LLM 불필요 사본에서 한다

무엇을 만드나

이 장이 끝나면 — 규칙 하나로 발동이 375건 늘어난다 
// 규칙 없이 (기준선)
ticks 1440 · … · interrupts 200 · replan-q 200 · llm 0

// shelter_from_storm_in_field 를 넣고
ticks 1440 · … · interrupts 575 · replan-q 200 · llm 0
이 장의 한 문장 인터럽트는 "먼저 도망치고, 새 계획은 나중에 받는다"의 구현이다. 즉시 행동은 그 틱에 나가고, 재계획은 우선순위 큐에 점수로만 들어간다. 둘을 분리했기 때문에 LLM 이 느려도 반응은 안 느려진다.

왜 LLM 이 이걸 안 하나

LLM 이 하는 일

  • 하루 일과를 미리 짠다
  • 느려도 된다 — 실측 요청당 3.7~5.1초
  • 비싸도 된다 — 수천 NPC 가 공유한다
  • 틀려도 된다 — 4단 검증기가 거른다

인터럽트가 하는 일

  • 지금 이 틱에 반응한다
  • 0.1초 안에 끝나야 한다
  • NPC 5,000마리에 매 틱 돈다
  • 틀리면 그대로 화면에 나간다

그래서 인터럽트는 마스터데이터에 사람이 쓰는 규칙이고, 판정은 플래그 비트 연산이다. 판단 기준: 반응 속도가 필요하면 규칙, 조합의 다양성이 필요하면 LLM.

규칙의 문법

masterdata/interrupts.json — 기존 규칙 하나
{
  "id": "flee_on_threat",
  "priority": 100,
  "when": {
    "any_flag": ["ThreatNearby", "InCombat"],
    "archetype_trait": { "courage": "<40" }
  },
  "then":   { "action": "Flee", "params": { "poi": "$nearest_safe" } },
  "replan": { "urgency": 100 }
}
필드뜻
priority여럿이 동시에 맞으면 높은 것이 이긴다. 같으면 id 오름차순
when.any_flag하나라도 서 있으면 참
when.all_flag전부 서 있어야 참
when.none_flag하나도 서 있지 않아야 참
when.event이 종류의 이벤트를 받은 틱에만 참
when.archetype_trait성향 비교. "<40" ">=40" "==50"
when.combat_capable아키타입이 싸울 수 있는가
then즉시 실행할 액션 하나
replan.urgency재계획 큐에 들어갈 점수. 나중에 새 플랜을 받는다
cooldown_s 가 없는 이유

"10초에 한 번만 발동" 같은 시간 기반 억제가 이 스키마에 없다. 넣으면 편할 텐데 안 넣었다.

시간 기반 억제는 실행 시각에 의존하고, 실행 시각은 리플레이마다 미세하게 다르다. 그러면 같은 입력으로 다른 결과가 나오고 리플레이 100% 일치가 깨진다.

대신 엣지 트리거다 — 조건이 거짓 → 참으로 넘어가는 순간에만 한 번 걸린다. 폭풍이 계속돼도 매 틱 재발동하지 않는다. 같은 효과를 시계 없이 얻는다.

규칙을 하나 쓴다

기존 seek_shelter 는 WeatherHarsh + InWilderness 만 본다. 밭에서 일하던 NPC 는 비를 다 맞는다. 그 틈을 메운다.

samples/ch08_interrupt/apply.ps1 이 넣는 규칙
{
  "id": "shelter_from_storm_in_field",
  "priority": 42,
  "when": {
    "all_flag": ["WeatherHarsh", "AtField"],
    "none_flag": ["IsSleeping", "InCombat"]
  },
  "then":   { "action": "MoveTo", "params": { "poi": "$home" } },
  "replan": { "urgency": 45 }
}
고른 값왜
priority 42seek_shelter(40)보다 높고 rest_when_exhausted(45)보다 낮다. 야생보다 밭이 급하고, 탈진보다는 덜 급하다
all_flag둘 다 참일 때만. 폭풍이어도 실내면 안 걸린다
none_flag 에 InCombat싸우는 중에 비 때문에 집에 가면 안 된다
urgency 45도망은 즉시, 새 하루 계획은 큐에서 순서를 기다린다

폭풍을 때린다

samples/ch08_interrupt/storm.jsonl
{"_comment": "--time-scale 600 기준. 1틱 = 게임 60초, 시작 06:00(Dawn)."}
{"at_tick": 100, "event": "WeatherChanged", "zone": "farmlands",        "code": "Storm"}
{"at_tick": 100, "event": "WeatherChanged", "zone": "highland_pasture", "code": "Storm"}
{"at_tick": 400, "event": "WeatherChanged", "zone": "farmlands",        "code": "Fair"}
{"at_tick": 400, "event": "WeatherChanged", "zone": "highland_pasture", "code": "Fair"}
{"at_tick": 700, "event": "WeatherChanged", "zone": "farmlands",        "code": "Storm"}
{"at_tick": 700, "event": "WeatherChanged", "zone": "highland_pasture", "code": "Storm"}

폭풍 → 갬 → 폭풍 이다. 두 번 때리는 이유가 있다 — 엣지 트리거가 정말로 두 번만 걸리는지 보려면 조건이 한 번 내려갔다 올라와야 한다.

틱 좌표는 배속에 묶여 있다 --time-scale 600 에서 1틱 = 게임 60초다. at_tick 100 은 게임 07:40 이다. 배속을 바꾸면 대본의 시각이 통째로 달라진다 — 10장에서 환산표를 만든다.

숫자 읽기

  1. 왜 375건인가 — 400건이 아니라

    기준선이 200이고 규칙을 넣으니 575다. 순증가분 375건이 내 규칙의 몫이다.
    NPC 200명 × 폭풍 2회 = 400 이 상한인데 375다. 차이 25는 폭풍이 칠 때 밭에 없던 NPC로 설명된다 — all_flag: [WeatherHarsh, AtField] 가 정확히 그 뜻이다. (정확한 내역까지 세려면 2장의 추적기로 개별 NPC 를 봐야 한다.)

  2. 틱이 안 느려졌다 0.155 → 0.137 ms

    규칙을 하나 더 봤는데 오히려 미세하게 빨라졌다(측정 잡음 범위다). 인터럽트 판정은 WorldFlags 64비트에 대한 AND/OR 몇 번이라 규칙 수에 거의 영향을 안 받는다. 규칙을 아끼지 않아도 된다.

  3. 재계획 큐는 그대로다

    replan.urgency 45 로 큐에 넣었는데 깊이가 안 늘었다. --tier none 이라 꺼내 가는 워커가 없기 때문이다. 16장에서 티어를 켜면 이 값이 움직이기 시작한다.

  • validate 가 인터럽트 15 로 올라간다
  • interrupts 가 200 → 575
  • bytes/tick 이 여전히 0
  • 틱 p99 가 예산(20ms) 안에서 사실상 안 변한다

부러뜨려 본다

바꿔 보기예상왜
all_flag → any_flag 발동이 폭증한다 폭풍이면 실내에 있어도, 밭에 있으면 맑아도 걸린다. 조건이 헐거우면 NPC 가 계속 집에 간다
none_flag 에서 InCombat 제거 전투 중에 도망친다 우선순위 100짜리 전투 규칙과 42짜리 이 규칙이 부딪힌다. priority 가 왜 있는지 여기서 보인다
priority 를 110 으로 위협보다 비를 먼저 피한다 flee_on_threat(100)를 이긴다. 우선순위는 세계관의 표현이다
없는 액션(Fly)을 then 에 FAIL V3 interrupts.json 의 액션 참조도 카탈로그에 있어야 한다
시나리오가 안 먹는 것 같으면

① 존 이름을 확인한다. zone 은 zones.json 의 id 여야 한다. 오타면 조용히 무시된다.

② 배속을 확인한다. at_tick 은 배속에 묶여 있다. --time-scale 60 으로 돌리면 tick 100 이 게임 06:10 이라 아직 아무도 밭에 안 나가 있다.

③ 플래그가 실제로 서는지 본다. 2장의 추적기로 +WeatherHarsh 가 찍히는지 확인한다. 안 찍히면 이벤트가 그 NPC 의 존에 안 닿은 것이다.
