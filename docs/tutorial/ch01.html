1부 · 일단 켠다

1장 · 5분 만에 NPC를 살린다

명령 한 줄로 NPC 20마리가 게임 하루를 산다. 밭에 나가고, 캐고, 팔고, 집에 가서 잔다. 그동안 LLM은 한 번도 부르지 않는다. 이 장에서 쓰는 코드는 0줄이다.

난이도 ★☆☆☆ 20분 LLM 불필요 OS 무관 0장 결과에 의존하지 않음

무엇을 만드나

아무것도 안 만든다. 이미 만들어진 것을 켜고 관찰한다. 이 장의 목표는 화면 하나를 얻는 것이다 — 그리고 그 화면의 숫자 한 쌍이 이 제품의 핵심 주장을 통째로 담고 있다.

이 장이 끝나면 이 두 줄을 읽을 수 있다 
tick p50 0.013ms · p99 0.108ms · max 6.566ms · overruns 0 · gen0 0 · bytes/tick 0 · heap 70.6MB
ticks 1440 · game day 1 · events 15175 · commands 11825 · steps 11118 · timeouts 1381 ·
scan/tick 3 · interrupts 20 · replan-q 20 · drops link 0 sim 0 · backlogs 0 · llm 0
이 장의 한 문장 llm 0 인데 commands 11825 다. LLM을 한 번도 안 불렀는데 게임서버로 명령이 1만 건 넘게 나갔다. 플랜은 이미 만들어져 있었고, 런타임은 그것을 실행만 했다. "LLM은 게임 크리티컬 패스에 없다"는 주장의 실물이 이 두 숫자다.

한 줄로 돌린다

터미널 — 저장소 루트에서 
PS> dotnet run -c Release --project src/Npc.Host -- `
      --loopback --npcs 20 --time-scale 600 --days 1 --no-llm --port 5080

이게 전부다. 옵션 여섯 개의 뜻은 이렇다.

옵션뜻바꾸면
--loopback 게임서버 대역(Npc.Sim)을 같은 프로세스 안에 붙인다. 소켓을 안 쓴다 --link tcp 로 바꾸면 진짜 소켓 너머의 게임서버에 붙는다 → 3·13장
--npcs 20 NPC 수 5,000까지 올려도 틱 예산 안에 있다 → 아래 대조 실험
--time-scale 600 실시간 1초 = 게임 600초. 1틱(0.1초) = 게임 60초 낮추면 NPC 의 하루를 자세히 볼 수 있다 → 2장
--days 1 게임 1일을 돌고 스스로 끝난다. 0이면 무제한 배속 600에서 게임 1일 = 1,440틱 = 실시간 약 144초
--no-llm --tier none 의 별칭. LLM 을 한 번도 안 부른다 16장에서 처음으로 뗀다. 그때까지 15개 장이 이 상태로 진행된다
--port 5080 대시보드·메트릭 HTTP 포트 여러 개를 동시에 띄우려면 다르게 준다
스크립트로도 된다 samples/ch01_first_run/run.ps1 같은 명령을 대신 치면서 옵션의 뜻을 먼저 화면에 적어 주고, 끝난 뒤 종료 요약을 짚어 준다. 
PS> ./samples/ch01_first_run/run.ps1 -Npcs 20

첫 줄 — 틱 루프가 건강한가

값실측기준뜻
p50 · p990.013 · 0.108 msp99 ≤ 20 ms한 틱을 처리하는 데 걸린 시간. 예산은 100ms 틱의 20%다
max6.566 ms—최댓값. 대개 첫 몇 틱의 JIT 컴파일이다
overruns00예산을 넘긴 틱 수
gen00—Gen0 GC 횟수. 이 값으로 틱 루프를 재지 않는다 (프로세스 전역이라 HTTP·직렬화가 섞인다)
bytes/tick00틱 루프가 틱당 힙에 쓴 바이트. 틱 루프를 재는 계기는 이것 하나뿐이다
heap70.6 MB—관리 힙. 계속 자라면 누수다
여기서 볼 것 bytes/tick 0 이 우연이 아니다. NPC 상태를 class Npc 객체 5,000개가 아니라 SoA(struct of arrays) 배열로 들고, 틱 루프 안에 new·LINQ·문자열 보간·클로저를 하나도 안 쓰기 때문이다. 19장에서 일부러 LINQ 한 줄을 넣어 이 값이 0이 아니게 되는 것을 본다.

둘째 줄 — 세계가 실제로 돌았나

왜 타임아웃이 1,381건이나 되나 스텝 11,118건 중 12%가 타임아웃으로 끝났다. 고장이 아니다 — 배속을 600으로 준 결과다. 1틱이 게임 60초이므로 timeout_s: 300 인 스텝은 5틱이면 만료된다. 게임서버 대역이 이동을 마치기 전에 시간이 먼저 지나간다.

중요한 것은 그래도 NPC 가 멈추지 않는다는 점이다. 응답이 안 오면 NPC 서버가 ActionFailed(Timeout) 을 스스로 만들어 다음 스텝으로 넘어간다. "명령은 유실된다고 가정한다"가 설계이고, 이 숫자가 그 설계가 도는 증거다. 배속을 60으로 낮추면 이 비율이 6%로 떨어진다.

이 표에서 볼 것 다섯

  1. LLM 열이 전부 0이다

    옵션을 어떻게 바꾸든 --no-llm 인 한 LLM 은 안 불린다. 명령은 최대 279만 건이 나갔다. 플랜은 이미 있었고 런타임은 실행만 했다.

  2. bytes/tick 이 전부 0이다

    NPC 를 100배로 늘려도 틱 루프는 힙에 한 바이트도 안 쓴다. 이 열이 0이 아니게 되는 순간이 회귀다.

  3. NPC 100배에 p99 는 23배다 0.105 → 2.368 ms

    선형보다 낫고, 여전히 예산 20ms 의 12% 다. 5,000마리는 이 제품의 설계 목표치다.

  4. --npcs 5000 의 스캔/틱이 정확히 150이다

    우연이 아니라 상한값이다 (CognitionScheduler.MaxScansPerTick). 5,000마리를 매 틱 전수 조사하지 않고 150마리만 본다. 이 상한 하나가 "NPC 를 늘려도 인지 비용은 O(1)" 을 만든다 → 6장

  5. --drop-rate 0.2 에서 명령은 줄고 타임아웃은 늘었다 명령 26,746 → 20,509 타임아웃 3,980 → 5,802

    명령 5건 중 1건을 일부러 버렸는데 NPC 는 멈추지 않았다. 합성한 타임아웃이 그 자리를 메웠기 때문이다. 11장에서 더 세게 흔든다.

덤으로 보이는 것 둘

① --player-bots 0 의 명령·스텝·타임아웃이 기준선과 한 건도 안 틀리다. 플레이어가 없으면 인지 스캔은 0이 되는데(스캔/틱 0), 행동은 똑같다. 인지 스캔은 누구를 재계획 대상으로 고를까만 정하고, --tier none 에서는 재계획 자체가 없으니 결과가 안 바뀐다. 16장에서 티어를 켜면 이 두 회차가 갈라진다.

② 배속은 "같은 것을 빨리 보기"가 아니다. 배속 600은 스텝의 16%가 타임아웃이고, 배속 60은 6%다. 배속을 올리면 다른 세계가 된다 — 게임서버가 이동을 마치기 전에 시간이 지나가기 때문이다. NPC 의 하루를 제대로 보려면 배속을 60쯤으로 낮춘다. 2장이 그렇게 한다.

확인한다

  • 실행이 스스로 끝난다 — --days 1 이면 1,440틱 뒤에 종료 요약을 찍고 나간다
  • 종료 요약에 llm 0 인데 commands 가 수천~수만
  • bytes/tick 0 · overruns 0 · drops link 0 sim 0
  • 도는 동안 /status 가 응답하고 tick 이 계속 증가한다
  • 브라우저로 /dashboard 가 열린다
  • variants.ps1 이 8행짜리 표를 찍고 bytes/tick 열이 전부 0

여기서 배우는 것 이 서버는 명령이 도착한다고 믿지 않는다. 모든 플랜 스텝에 timeout_s 가 있고, 응답 이벤트가 안 오면 로컬에서 실패를 만들어 진행을 재개한다. 실제 게임서버에 붙이면 명령은 반드시 유실되므로, 이 경로가 예외가 아니라 기본이다. 11장에서 이 경로만 집중적으로 흔든다.
