## 1. 워밍업 유무 비용 차이 (T3-11)

재측정:

```powershell
# 회차마다 --generated-at 를 다르게 준다. 같은 값이면 두 번째 실행이
# 첫 번째가 만든 캐시를 물려받아 비교가 성립하지 않는다.
dotnet run -c Release --project tools/Npc.Prebake -- `
    --model poe-gemini-2.5-flash-lite --warmup-experiment 8 --generated-at W8-r1
```

엔진 `poe-gemini-2.5-flash-lite` (Poe 경유 · Gemini 2.5 Flash Lite) · 프리픽스 13,488 tok ·
버킷 `blacksmith@Dawn.Peace.Fair` · 2026-07-26.

각 회차는 프리픽스 맨 앞에 회차 고유 소금을 한 줄 붙여 **두 조건 모두 콜드 캐시**로 시작한다.

| 회차 | 동시 | 워밍업 없음 (파동 캐시 적중) | 워밍업 있음 (파동 캐시 적중) | 비용 차이 |
|---|---:|---:|---:|---:|
| r1 | 8 | 35.8 % · $0.008985 | 35.8 % · $0.011094 | **−23.5 %** |
| r2 | 8 | 35.8 % · $0.008835 | 59.7 % · $0.008452 | +4.3 % |
| r3 | 8 | 23.9 % · $0.009960 | 71.6 % · $0.007652 | +23.2 % |
| c32a | 32 | 68.6 % · $0.024934 | 68.6 % · $0.027638 | **−10.8 %** |
| c32b | 32 | 71.6 % · $0.023726 | 68.6 % · $0.027823 | **−17.3 %** |

- 동시 8 평균: 캐시 적중 **31.8 % → 55.7 %** (1.75배). 비용 차이 평균 **+1.3 %** — 분산이 ±23 %로 부호가 흔들린다.
- 동시 32: 워밍업 없이도 이미 68~72 % 가 적중한다. 워밍업은 **비용을 올린다** (−10.8 %, −17.3 %).

### 판정 — 이 엔진 계열에서 워밍업은 비용을 줄이지 않는다

`docs/13 §4` 는 "워밍업을 빼면 N 개가 전부 cache miss 로 시작해 write 할증(1.25~2배)을 N 번 낸다"고 했다.
**그 전제가 이 엔진에 없다.**

| 전제 | 실측 |
|---|---|
| 동시 N 개가 전부 miss 로 시작한다 | **아니다.** 파동 안에서 먼저 도착한 요청이 캐시를 만들고 나머지가 물려받는다 — 동시 32에서 워밍업 없이 68.6 % 적중 |
| write 에 할증이 붙는다 | **없다.** Gemini 의 암시적 캐싱은 write 할증이 없고 적중분이 오히려 0.25배로 싸다 |
| 그래서 워밍업 1회가 N 번의 할증을 막는다 | **막을 것이 없다.** 요청 1개가 늘어나는 만큼 순손실이다 |

`cached_tokens` 값이 13,298 tok(요청당 프리픽스 캐시 크기)의 정수배로만 나온다 —
요청 단위로 전부 적중하거나 전부 미적중이고, **어느 요청이 적중할지는 비결정적이다.**
같은 콜드 조건의 "워밍업 없음"이 23.9 %와 35.8 % 사이에서 흔들린 것이 그 때문이다.

### 그래도 워밍업을 기본으로 켜 둔다

세 가지 이유이고, 셋 다 비용 논거가 아니다.

1. **Anthropic 계열에서는 §4 의 전제가 성립한다.** 명시적 캐싱(`cache_control` 블록)은 write 할증이 실제로 있다.
   다만 그 실측은 **이 저장소의 어느 엔드포인트로도 못 한다** — OpenAI 호환 경유로는 `cache_control` 을 실어 보낼 수 없다.
2. **회차 전체의 예비 점검이다.** 2,880건을 던지기 전에 키·엔드포인트·프리픽스·스키마가 실제로 통하는지 요청 하나로 확인한다.
3. **비용이 무시할 수준이다.** 2,880건 회차에서 요청 1개는 0.03 % 다.

`docs/13 §4·§8` 의 "비용 3배" 표현을 이 실측으로 고쳤다.

## 3. 전수 드라이런 (T3-15)

재측정:

```powershell
dotnet test -c Release --filter DryRun_ChecksEveryBucketWithinBudget `
    --logger "console;verbosity=detailed"
```

2,880 버킷을 아키타입 폴백 플랜으로 전부 채우고 4단을 굴린 값이다 (2026-07-26).

| 병렬도 | 소요 | 건당 | 판정 |
|---:|---:|---:|---|
| 16 (`ProcessorCount`) | **0.02 s** | 0.01 ms | 게이트 60초 대비 **3,000배 여유** |
| 1 (직렬) | 0.04 s | 0.02 ms | 직렬로도 게이트를 통과한다 |

- 2,880건 전량 통과. 폴백은 V7 이 기동 시점에 4단 통과를 보장하므로 기대값대로다.
- 병렬도를 1 → 16 으로 올려도 2배밖에 안 빨라진다 — **이 단계는 병렬화가 필요한 곳이 아니다.**

### `docs/13 §8` 의 "~50ms" 는 실측의 2,500배였다

§8 은 건당 소요를 "~50ms" 로 적어 두고 **추정치라고 명시**해 놓았다 (`docs/13` T3-15).
실측은 **0.02ms** 다. 드라이런이 10Hz 틱을 굴리지 않고 액션 소요시간만큼 게임시간을 건너뛰기 때문이다
(`DryRunValidator` → `SimWorld.RunCycles`).

따라서 T3-15 의 "미달 시 병렬도를 올리기 전에 T2-13 의 건당 소요부터 기록" 조항은 **발동하지 않는다.**
표본을 줄일 이유도 없다 — `--dryrun-sample` 기본값 1.0(전수)을 그대로 쓴다.
