## 2. 항목별 근거

### 항목 1 — 생성 완료율

파일럿 288버킷만 돌렸으므로 `generated 195 / 2880 = 6.8%` 다. 기제는 통과했다:
2,880 중 95% 를 채운 스토어에서 전 버킷이 유효한 플랜을 받고, 미생성분은 아키타입 폴백으로
해소되며 `Resolve` 가 null 을 반환하지 않는다 (`Gate_ColdBucketsResolveToFallback`).

**전량 회차를 돌리면 판정된다.** 파일럿의 통과율 67.7% 를 그대로 외삽하면 완료율은
`67.7% + 인접 재사용 21.2% = 88.9%` 로 95% 에 미달한다 — 이것은 **P2 게이트 미달(통과율 90%)이
그대로 이어지는 문제**이고 P3 의 결선 문제가 아니다 (`W6_compile_stats.md §8`).

### 항목 2·3 — wall-clock 과 비용

`W8_prebake.md §4` 의 외삽표를 그대로 옮긴 것이다. **동시성을 올려 5분을 맞추지 않았다** —
`docs/13 §7` 이 "기준을 맞추려고 동시성을 올려 429 를 맞지 않는다"고 정해 두었다.
429 는 동시 24 까지 한 번도 나지 않았으므로 상향 여지는 있지만, 그 값은 **먼저 재고 절반을 쓰는**
순서를 지켜야 한다 (`AdaptiveConcurrency.RecommendedStart`).

### 항목 4 — 프롬프트 캐시 적중률

프리픽스 SHA 는 1종이라 우리 쪽 조건은 지켜졌다. 42.6% 인 원인은 제공사 쪽이다 —
Gemini 암시적 캐싱은 요청 단위로 전부 적중하거나 전부 미적중이고 그 판정이 비결정적이다
(`W8_prebake.md §1`). **하한 95% 는 명시적 캐싱(Anthropic `cache_control`)을 전제한 값**이라
이 엔진 계열에서는 도달할 수 없다. 기준에 엔진 계열을 명시해 다시 적어야 한다.

### 항목 5 — 시나리오 A 캐시 히트율

`prebake_priority` 순으로 95%(2,736건)를 채운 스토어에 NPC 500 · 플레이어 봇 20 을 올려
게임 7일(10,080틱)을 완주시켰다.

| 지표 | 값 |
|---|---:|
| 히트율 | **100.00 %** |
| 버킷 히트 | 8,986 |
| 미스 (폴백 해소) | **0** |
| 채운 버킷 | 2,736 |
| 콜드 버킷 | 144 |
| 틱 | 10,080 |

비워 둔 5%(144건)는 우선순위가 뒤로 미룬 `Disaster` 계열 꼬리이고, 7게임일 주행에서
그 버킷이 **한 번도 조회되지 않았다.** `prebake_priority` 정렬이 실제로 덜 쓰이는 버킷을
뒤로 보낸다는 것이 이 값으로 확인된다 — 중단된 회차라도 실제로 쓰이는 버킷은 채워져 있다.

시나리오 파일(`scenarios/*.jsonl`)을 물리면 `RegionState` 가 흔들려 꼬리 버킷도 조회되기 시작한다.
그 회차는 P4(T4-15 부하 매트릭스)에서 같이 잰다.

### 항목 9 — 검수 채택률

**사람이 해야 한다.** 도구(`tools/review.ps1`)와 승격 도구(`tools/pin_plan.ps1`)는 완성됐고

## 2.5 도달 집합 회차 (2026-07-28) — 항목 1~4 는 그래도 열리지 않는다

264버킷 도달 집합을 실제로 돌렸다 ($0.3727 · 96.9초 · 생성 195 · 통과율 73.9 % ·
캐시 45.4 % · 429 0회). 자세한 내역은 [`reach264_prebake.md`](reach264_prebake.md).

**그런데 항목 1·2·3·4 는 여전히 판정되지 않는다.** `Phase3GateTests.RequireFullRun` 이
`생성/2880` 을 보고 "부분 회차의 manifest 다 (생성 완료율 6.8 %)" 로 멈춘다.

**이것은 테스트의 결함이 아니라 게이트 기준과 프로젝트 방침이 어긋난 것이다.**

| | 게이트가 전제하는 것 | 프로젝트가 택한 것 |
|---|---|---|
| 프리베이크 범위 | 전량 2,880 | **도달 집합 264** (`RnD_Report` 권고 2) |
| 항목 1 분모 | 2,880 | — |
| 결과 | 완료율 6.8 % → 영구 미달 | |

도달 집합 방침을 유지하는 한 **항목 1 은 정의상 닫히지 않는다.**
분모를 "전량 2,880" 에서 **"선언된 대상 집합"** 으로 바꾸면 195/264 = 73.9 % 인데,
그것도 95 % 기준에는 미달이다 — 그 미달의 원인은 P2 통과율이고 P3 의 문제가 아니다.

> **기준을 고쳐서 통과시키지 않았다.** 게이트를 스스로 고쳐 통과시키면 게이트가 거짓이 된다.
> 분모를 바꿀지는 사람이 정할 일이고 `TASKS.md §3` 에 결정 대기로 올렸다.

한편 **P4 게이트 항목 2(히트율 ≥ 98 %)는 이 회차로 닫혔다** — 98.67 %.
같은 산출물이 P3 에서는 아무것도 못 닫고 P4 에서는 닫는 이유는, P3 항목들이
**"얼마나 만들었나"** 를 보고 P4 항목 2 는 **"만든 것이 실제로 쓰이나"** 를 보기 때문이다.

## 2.6 항목 2·3·4 가 아직 미판정인 이유 — `RequireFullRun`

셋 다 같은 곳에서 막힌다.

```
부분 회차의 manifest 다 (생성 완료율 18.2 %).
이 항목은 전량 2880 회차에서만 판정된다 —
지금 값(wall-clock 178s · $0.6990 · 캐시 69.3 %)은 외삽의 근거일 뿐이다.
```

**항목 4 의 기준 개정(3-A)은 오늘 효과가 없다.** 실측 69.3% 는 새 하한 40% 를 여유 있게 넘지만
`RequireFullRun` 이 그 앞에서 멈춘다. 기준이 틀렸던 것과 회차 범위가 부족한 것은 **다른 문제**이고,
개정한 것은 앞쪽뿐이다.

`RequireFullRun` 은 원래 **"288버킷 파일럿의 115초를 상한 300초 통과로 세지 않는다"** 는 방어였고
그 방어 자체는 여전히 옳다. 문제는 판정선이 `생성/2880 ≥ 95%` 라는 것이다 —
**전량 회차를 돌리지 않기로 했으므로**(2026-07-28 결정 8번) 이 선은 넘을 수 없다.

**2026-07-28 결정 15-A — 판정선을 (b) 로 바꿨다.**

```
전:  생성/2,880 >= 95%          → 도달 집합 방침에서 영원히 미달
후:  counts.target > 0 && !partial   → "선언한 범위를 완주했는가"
```

`RequireFullRun` → `RequireCompleteRun`. manifest 에 `counts.target`(이번 회차가 만들기로
선언한 버킷 수)을 추가했고, `counts.generated` 는 **스토어 총계**로 확정했다(결정 13).

**방어는 자리를 옮겼지 사라지지 않았다.** 원래 목적("파일럿 115초를 상한 300초 통과로 세지 않는다")은
이제 **측정치에 범위 꼬리표를 강제**하는 것으로 지킨다 — 항목 2·3·4 의 실패 메시지가 항상
`[대상 N버킷 · 스토어 M/2880]` 을 찍는다.

> **아직 셋 다 미판정이다.** 현재 `manifest.json` 은 이 스키마 이전에 쓰인 것이라
> `target` 이 없다. **다음 프리베이크 회차부터 판정된다** — 그때 항목 4 는 통과할 것이고
> (실측 69.3 % > 하한 40 %), 항목 2·3 은 978 집합 기준으로 178초·$0.699 라 역시 통과할 것이다.
> 다만 **그 값은 978버킷의 값이지 2,880버킷의 값이 아니다** 는 꼬리표를 달고 통과한다.
