1. 아키텍처

프로세스는 셋이다. 각자 다른 소켓으로 이어져 있고, 셋 다 상대가 없어도 죽지 않는다.

왜 셋으로 나눴나

NPC 서버 우리가 만드는 것

무엇을 할지 정하는 쪽. 플랜을 고르고 명령을 낸다. 세계를 밀지 않는다 — 시간이 흐르는 것조차 게임서버가 보내 주는 TickSync 로만 안다.

게임서버 대역 상대역

세계를 미는 쪽. 이동·상호작용·욕구를 계산하고 결과를 이벤트로 돌려준다. 실제 게임서버가 할 일을 최소한으로 흉내낸다.

클라이언트 사람의 눈

보는 쪽. 지도·로그·제어판. 게임서버와 NPC 서버 둘 다에 붙는다 — 이유는 아래.

왜 클라이언트가 NPC 서버를 직접 보는가. 플랜 id·스텝 번호·월드 플래그는 게임서버가 알 수 없는 정보다. 링크에 그런 필드가 없고(N1·N3) 있어서도 안 된다. 게임서버를 경유해 중계하면 실제로는 존재하지 않는 결합을 테스트 베드가 만들어 낸다.

그래서 인스펙터 패널만 GET /npc/{id} 로 NPC 서버를 1초마다 직접 긁는다. 지도·로그는 게임서버에서 온다.

프로젝트 의존

화살표는 "참조한다" 다. testbed 는 단방향 잎 — 아무도 참조하지 않는다.

Npc.Contracts   외부 NuGet 0. 참조하는 프로젝트 없음          ← 링크 계약 (N1~N8)
Npc.Core        외부 NuGet 0. Contracts 만
Npc.MasterData  Core
Npc.Runtime     Core, MasterData, Contracts, Planning         ← 틱 루프
Npc.Planning    Core, MasterData
Npc.Wire        Contracts (+ MemoryPack)                      ← 전송 표현
Npc.Gateway     Contracts, Wire                               ← TcpGameServerLink
Npc.Sim         Contracts, MasterData
Npc.Host        전부

testbed/Npc.TestBed.Protocol   Wire
testbed/Npc.TestGameServer     Sim, MasterData, Wire, Protocol
testbed/Npc.TestClient         MasterData, Protocol           ← net10.0-windows

여기 두 줄이 이 프로젝트의 핵심 제약이다.

  • Npc.Runtime 은 Npc.Wire 를 참조하지 않는다 — 런타임이 전송 표현을 알 이유가 없다.
  • Npc.Runtime 은 Npc.Llm 을 참조하지 않는다 — 참조가 생기면 틱 루프에 LLM 이 들어올 길이 열린다.

Npc.Wire 가 따로 있는 이유도 같다. [MemoryPackable] 을 NpcCommand 에 붙이는 순간 계약 프로젝트가 직렬화기 버전에 묶인다. 그래서 와이어 DTO 를 따로 두고 1:1 로 매핑한다.

손으로 — 스크립트가 하는 일 셋

# 0) 빌드
dotnet build -c Release

# 1) 게임서버 — 먼저 떠 있어야 한다
#    (나머지 둘은 재접속을 돌리므로 순서가 어긋나도 죽지는 않는다)
dotnet run -c Release --project testbed/Npc.TestGameServer -- `

    --scenario testbed/scenarios/demo_siege.jsonl

# 2) NPC 서버
dotnet run -c Release --project src/Npc.Host -- `
    --link tcp --gs-port 7010 --npcs 300 --time-scale 60 --days 0 `
    --tier none --planstore ./planstore --port 5080 --dev-control

# 3) 클라이언트
dotnet run -c Release --project testbed/Npc.TestClient -- `
    --host 127.0.0.1 --port 7020 --npc-http http://localhost:5080

--npcs·--time-scale·--zone 은 양쪽이 같아야 한다. 하나라도 다르면 핸드셰이크에서 거절된다 — 그것이 의도된 동작이다.

첨자가 어긋난 채로 도는 것보다 연결 시점에 죽는 편이 싸다. 어긋나면 대장장이에게 밭을 갈라고 명령하게 되고, 증상은 "가끔 이상하게 행동한다" 로만 나타난다.

3. 어떻게 동작하나

핸드셰이크 — 넷을 맞춰 본다

게임서버가 먼저 말을 건다. 접속한 쪽이 아니라 받는 쪽이 Hello 를 보낸다 — 세계의 규격을 아는 쪽이 게임서버이기 때문이다.

거절 코드무엇이 다르다고치는 법
ProtocolVersion와이어 버전양쪽을 같은 커밋으로 빌드
MasterDataMismatchMasterDataSet.ContentHash두 프로세스가 같은 masterdata/ 를 보게 한다
RosterMismatchNpcRoster.Hash--npcs·--zone 을 맞춘다
TimeScaleMismatch--time-scale맞춘다

우회 옵션은 없다. "일단 붙게 해 주는 플래그" 를 만들지 않는 것이 이 설계의 요점이다 — 그 플래그가 있으면 첨자가 어긋난 회차가 조용히 돌게 된다.

프레임 — 8바이트 헤더

TCP 는 경계를 지켜 주지 않는다. 한 번의 읽기에 프레임이 반만 오거나 세 개가 붙어 온다. 그래서 길이 접두를 붙인다.

링크 kind Npc.Wire

Hello 1 · HelloAck 2 · CommandBatch 3 · EventBatch 4 · Heartbeat 5 · Bye 6

sizeof(WireCommand) == 56, sizeof(WireEvent) == 64 — 테스트가 못 박는다.

클라 kind Npc.TestBed.Protocol

서버→클라 1~63: SrvHello 1 · Snapshot 2 · ZoneStates 3 · CommandLog 4 · EventLog 5 · LinkStatus 6 · Pong 7

클라→서버 64~127: CliHello 64 · Input 65 · Interact 66 · Attack 67 · Select 68 · Control 69 · Ping 70

번호를 갈라 둔 이유: 로그에서 방향을 헷갈리지 않는다.

10단계 틱 루프

게임서버가 100ms 마다 이 열 단계를 돈다. 순서가 계약이다 — Npc.Host 의 루프백 드라이버와 같은 순서여야 루프백과 소켓을 비교할 수 있다.

NPC 서버는 게임서버를 기다리지 않고, 게임서버도 NPC 서버를 기다리지 않는다. 락스텝이 없는 것이 이 테스트 베드의 핵심이다 — 링크가 없는 동안에도 세계는 흐르고, 그때 쌓인 이벤트는 배수해 버린다.

그 대가로 결정론이 성립하지 않는다. 8. 알려진 한계를 본다.

명령 한 바퀴 — MoveTo 가 NpcArrived 로 돌아오기까지

⑦ 이 깨지면 NPC 가 영원히 멈춘다. 그런데 평소에는 아무 일도 안 일어나므로 일부러 깨뜨려야 보인다. 그래서 게임서버에 --drop-rate 가 있고, 종단 테스트가 0.3 으로 300틱을 돌려 "합성 타임아웃 > 0 · 멈춘 NPC 0" 을 못 박는다.

N1~N8 — 링크가 지켜야 하는 여덟

테스트로 강제된다. 어기면 빌드가 아니라 테스트가 깨진다(Category=Contracts).

#규칙왜
N1명령은 fire-and-forget. 반환값 있는 메서드를 IGameServerLink 에 추가하지 않는다RPC 왕복을 만드는 순간 네트워크 RTT 가 틱 루프를 막는다
N2모든 패킷은 readonly record struct참조 필드·가변 컬렉션이 들어오면 할당과 경합이 따라온다
N3패킷에 string 금지. 전부 강타입 ID프롬프트 인젝션을 "넣지 마라" 가 아니라 "넣을 수 없다" 로 만든다
N4패킷에 DateTime/TimeSpan 금지. 시간은 Tick(long)만결정론
N5모든 명령에 CorrelationId응답을 명령에 이어 붙일 유일한 끈
N6모든 이벤트에 Sequence. 갭 검출 → 경보이벤트가 새는 것을 조용히 넘기지 않는다
N7이벤트 처리는 멱등. 2회 주입 → 상태 해시 동일재접속·재전송이 상태를 흔들지 않는다
N8배치가 기본. Enqueue + FlushAsync 만 노출한 번의 Flush = 한 개의 프레임

4. 무엇을 바꾸며 테스트하나

"이걸 보고 싶다" → "이걸 만진다" 표다. 위에서 아래로 갈수록 비용이 커진다.

① 실행 중에 — 제어 패널 (재빌드 없음)

클라이언트의 제어 탭. 전부 Control 메시지 하나로 게임서버에 가고, NPC 서버는 이 패널의 존재를 모른다.

만지는 것무엇이 일어나나어디서 확인
존 상태 → WarZoneStateChanged 주입 → 그 존의 버킷 키가 바뀌어 플랜이 갈린다지도의 존 테두리가 빨개진다 · 인스펙터의 plan id
날씨 → StormWeatherChanged 주입같음
시간 건너뛰기게임서버 틱을 점프상태바의 게임 시각
⚠ 진행 중인 이동·작업이 한꺼번에 끝난다. 시나리오 회차에서는 쓰지 않는다
고장 주입 슬라이더명령을 확률로 버리거나(drop) 실패시킨다(fail)로그 패널의 ActionFailed · /metrics 의 합성 타임아웃
선택 NPC despawnNpcDespawned → TargetGone 경로그 NPC 를 상대하던 다른 NPC 의 스텝이 실패한다
킬스위치 T2/T1/PlanStoreNPC 서버의 티어를 끊는다인스펙터의 PlanKind 가 bucket → fallback

킬스위치만 다른 길로 간다. 그것은 NPC 서버 안쪽 상태라 링크로 보낼 수단이 없다 (GameEvent 에 그런 종류가 없고, 만들면 N 규칙을 어긴다). 제어 패널의 버튼은 POST /control/killswitch 를 직접 부른다.

--dev-control 없이 기동한 NPC 서버에는 그 라우트가 아예 없어서 404 이고, 화면에는 "미연결" 로만 나온다. 조건부 401/403 이 아니라 조건부 등록인 이유는 그쪽이 실수 하나로 열리기 때문이다.

at_tick 이 없는 줄은 주석으로 넘어간다. 모르는 존 id·이벤트 이름·킬스위치 대상은 로드 시점에 예외다 — 오타를 조용히 넘기면 데모 도중 아무 일도 안 일어나고, 그때는 원인을 한참 찾게 된다.

KillSwitch 줄은 게임서버가 무시하고 NPC 서버만 처리한다. 그래서 같은 파일을 양쪽에 준다.

5. 자동 테스트

7. 막히면

증상원인과 조치
게임서버가 link down 이고 NPC 가 안 움직인다양쪽 --npcs·--time-scale 이 다르면 핸드셰이크에서 거절된다. 두 콘솔의 roster hash 를 견준다
클라이언트가 "게임서버를 찾는 중…" 에서 안 넘어감게임서버의 --client-port 와 클라이언트의 --port (기본 7020)
인스펙터가 "NPC 서버 미연결"NPC 서버가 안 떴거나 --port 가 다르다. 클라이언트는 이 상태로도 계속 돈다
킬스위치 버튼이 "미연결" 만 뜬다NPC 서버에 --dev-control 이 없다
"마스터데이터 해시가 게임서버와 다르다" 경고두 프로세스가 다른 masterdata/ 를 본다. POI 이름과 위치가 어긋난 채 그럴듯한 화면이 나오는, 가장 찾기 어려운 사고다
창은 뜨는데 NPC 가 안 보인다AOI 가 플레이어 반경 1,200m 다. Home 으로 월드 전체를 보고 무리 쪽으로 걸어간다
빌드가 파일 잠김으로 실패데모 프로세스가 bin/Release DLL 을 잡고 있다. 먼저 내린다
테스트가 간헐적으로 실패할당·벽시계 예산 테스트가 부하에 민감하다. 단독으로 다시 돌려 본다

무엇내용
결정론이 성립하지 않는다"리플레이 100% 일치" 는 루프백 경로의 게이트다. 소켓에서는 명령이 몇 틱 늦게 도착할 수 있고 그것이 스텝 경계를 바꾼다. 결함이 아니라 사실이다 — 실제 게임서버에 붙으면 원래 그렇다. 재현이 필요하면 --link record 로 이벤트 열을 기록해 --link replay 로 되민다
InCombat 테두리가 안 켜진다전투 상태를 들고 있는 자리가 게임서버 어디에도 없어서 비웠다. HP 같은 것으로 흉내내면 화면이 거짓말을 한다
상태바의 npc 틱이 늙는다게임서버는 NPC 서버의 틱을 명령의 IssuedAt 에서 딴다. 하트비트에 그 값이 없다. NPC 서버가 조용하면 멈춘 것처럼 보이는데 그것도 정보다
고장 슬라이더가 시작 옵션과 겹친다슬라이더는 --fail-rate 를 대체하지 않고 앞에 선다. 떼면 그 옵션으로 시작한 회차가 클라이언트가 붙는 순간 조용히 무고장이 된다
SkipTime 은 리플레이 대상이 아니다틱을 점프시키면 진행 중인 이동·작업의 만료가 전부 지나가 다음 틱에 한꺼번에 끝난다. 데모 편의 기능이다
클라이언트는 Windows 전용net10.0-windows + WinForms. Npc.Tests 는 이 프로젝트를 참조하지 않는다 — 참조하면 CI 전체가 Windows 전용이 된다

미해결 — 시간대가 바뀌어도 버킷 플랜을 안 갈아탄다 (2026-08-01 확인).

게임 하루를 돌려도 플랜 id 가 아키타입 폴백과 @Morning 버킷 둘뿐이고 Noon·Afternoon·Evening·Night 버킷으로 한 번도 가지 않는다. --loopback 에서 그대로 재현되므로 소켓 경로와 무관하다 — 테스트 베드의 문제가 아니다.

그래서 지금 demo_day 는 보여 주려던 것(저녁 시간대 전환 → 대량 플랜 스왑)을 못 보여 준다. demo_siege(존 전환)와 demo_blackout(폴백 강등)은 영향이 없다. 경위와 다음 걸음은 TASKS.md §3 결정 대기에 있다.
