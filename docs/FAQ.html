LlmNpcServer FAQ

기존 MMORPG NPC 서버와의 차이, 적합한 적용 범위, LLM 행동 플랜을 만들기 위한 사전 준비, 전투 반응과 NPC 대화 확장 방법을 정리한 누적형 문서다.

누적 업데이트 문서 행동 플랜결정론적 런타임 게임서버 연동대화 확장
LLM의 역할실시간 실행기가 아니라 행동 플랜 컴파일러다.
가장 적합한 영역대규모 생활형·환경 반응형 NPC다.
현재 대화 범위대사 ID 기반이며 자유대화는 별도 확장이 필요하다.
검색어와 일치하는 FAQ가 없다.
Q1

기존 MMORPG NPC 서버보다 어떤 이점이 있는가?

가장 큰 이점은 NPC의 실시간 판단 능력이 아니라 대규모 NPC 행동 콘텐츠를 자동 제작하면서도 런타임의 성능과 결정론을 유지한다는 점이다.

전통적인 FSM·행동 트리·스크립트 서버를 전부 대체하기보다는, 기존 게임서버 옆에서 비전투·생활형 NPC의 행동 플랜을 공급하고 실행하는 보조 NPC 서버로 사용할 때 가치가 크다.

관점기존 FSM·BT·스크립트LlmNpcServer
행동 제작NPC와 상황별로 사람이 작성한다.LLM이 허용된 액션으로 상황별 플랜을 조합한다.
런타임규칙과 스크립트를 직접 실행한다.검증·저장된 플랜을 결정론적으로 실행한다.
상황 변화새 분기와 이벤트 스크립트가 필요하다.시간대·지역 상태·기후 버킷별 플랜을 교체한다.
LLM 장애일반적으로 LLM을 사용하지 않는다.틱 루프와 분리되어 기존 플랜으로 계속 동작한다.
재현성높다.저장 플랜과 기록·재생으로 LLM 없이 재현한다.
비용 구조실행은 저렴하지만 제작 공수가 크다.생성 비용이 있지만 다수 NPC가 플랜을 공유한다.
핵심 설계

LLM을 실행기가 아니라 컴파일러로 사용한다. NPC가 행동할 때마다 LLM에 묻지 않고, 미리 생성한 JSON 플랜을 10Hz 결정론적 런타임에서 실행한다.

플랜 공유

아키타입 × 시간대 × 지역 상태 × 기후의 최대 2,880개 플랜을 5,000 NPC가 공유한다.

장애 격리

외부 API 지연이나 실패가 게임 틱을 직접 지연시키지 않는다.

검수 가능

플랜은 사람이 읽고 수정·고정·버전 관리할 수 있는 JSON이다.

단계적 폴백

외부 API, 로컬 LLM, 캐시, 수동 폴백 사이에서 강등된다.

게임 지속

재계획 큐가 포화돼도 NPC는 기존 플랜을 계속 실행한다.

교체 가능한 링크

TCP·루프백·기록·리플레이 링크로 통합과 시험을 분리한다.

현재 실측에서는 5,000 NPC가 게임 시간 7일과 10,080틱을 완주했고, 캐시 히트율은 98.67%, 틱 p99는 0.801ms였다. 결정론 리플레이도 바이트 단위 동일 판정을 통과했다.

Q2

어떤 경우에 사용하면 좋은가?

이 서버는 NPC 한 명의 정교한 전투보다 세계 전체가 살아 움직이는 느낌이 중요한 게임에 특히 잘 맞는다.

  • 도시 주민, 상인, 경비병, 농부처럼 수천 명의 생활형 NPC가 필요한 경우다.
  • 낮·밤, 날씨, 전쟁, 재난, 지역 치안에 따라 NPC 행동이 달라져야 하는 경우다.
  • 라이브 이벤트가 잦아 행동 스크립트 작성 공수가 커진 경우다.
  • LLM을 사용하되 네트워크 지연과 비결정성을 런타임에 넣을 수 없는 경우다.
  • 생성된 행동을 사람이 검수하고 고정한 뒤 운영에 반영하려는 경우다.
  • 기존 게임서버를 유지하면서 NPC 판단을 별도 서비스로 분리하려는 경우다.
  • NPC 규모·캐시·재계획 전략을 검증하는 R&D 또는 프로토타입인 경우다.
현실적인 첫 적용점

기존 전투·퀘스트 AI는 유지하고, 대규모 생활형 NPC와 월드 이벤트 반응만 LlmNpcServer에 맡기는 방식이 가장 안전하다.

Q3

어떤 경우에는 적합하지 않으며, 현재 한계는 무엇인가?

정밀 전투 AI

보스 패턴, PvP 봇, 프레임 단위 판정에는 기존 결정론적 전투 AI가 더 적합하다.

소수의 고유 NPC

각 NPC가 독자적인 연출과 퀘스트 스크립트를 가져야 한다면 수작업 통제력이 유리하다.

무제한 즉흥 행동

실제 행동은 마스터데이터와 제한된 DSL 안에서만 가능하다.

작은 프로젝트

별도 NPC 서버와 TCP 연동 비용이 제작 공수 절감보다 클 수 있다.

현재는 상용 완성품이 아니라 R&D 구현체다.

203개 태스크 중 196개가 완료됐지만 플랜 다양성은 목표 60%보다 낮은 37.1%이며, GPU 부하와 사람 대상 품질 평가도 완결되지 않았다.

따라서 현재 평가는 “검증된 범용 상용 NPC 서버”보다 구조와 성능 가능성이 구체적으로 증명된 기술 검증 구현체가 적절하다.

Q4

LLM이 상황별 플랜을 만들려면 무엇을 사전에 준비해야 하는가?

자연어 설명 몇 줄이 아니라 게임 세계의 어휘와 규칙을 구조화한 마스터데이터가 필요하다. LLM은 이 데이터에 없는 행동을 새로 발명하는 것이 아니라 허용된 원자 액션을 조합한다.

순서준비 항목정의하는 내용예시
1world_flags.jsonNPC가 인지할 수 있는 상태를 정의한다.PlayerNearby, ThreatNearby, OnDuty
2items.json장비·재료·소지품과 상태 효과를 정의한다.검, 도구, 식량, 화폐
3actions.json행동 파라미터, 전제, 효과, 게임서버 명령을 정의한다.Patrol, Attack, Talk
4존·POI·거리이동 목적지와 위치 관계를 정의한다.성문, 감시탑, 시장, 안전지대
5archetypes.json역할, 허용 액션, 성향, 목표, 근무 시간, 장비를 정의한다.성문 경비병, 상인, 농부
6상황 버킷플랜을 공유할 상황 축을 정의한다.시간대 × 평시/전쟁 × 날씨
7interrupts.json위협·피해·상호작용에 즉시 반응하는 규칙을 정의한다.공격, 도주, 도움 요청
8수동 폴백 플랜LLM과 캐시가 모두 실패해도 지속할 기본 일과를 정의한다.근무 → 귀가 → 수면
9NPC 인스턴스스폰 위치, 집, 근무지, 초기 장비를 개체에 바인딩한다.501번 경비병의 북문 근무지

게임서버가 책임져야 하는 것

NPC 서버는 행동 의도를 명령으로 보낸다. 실제 경로 탐색, 충돌 회피, 시야·은신 판정, 적대 관계, 명중·피해·사망 판정은 게임서버가 권위 있게 처리해야 한다.

개체별 차이를 크게 만들려면

현재 인스턴스 데이터는 집·근무지·스폰 위치 중심이고, 기본 플랜은 아키타입과 상황 버킷 단위로 공유된다. NPC마다 서로 다른 순찰로·경계 반경·세력·대화 성격을 지정하려면 다음과 같은 개체별 행동 파라미터와 심볼 바인딩을 추가하는 편이 좋다.

{
  "id": 501,
  "archetype": "hostile_gate_guard",
  "zone": "north_gate",
  "workplace_poi": "gate_north",
  "patrol_route": ["gate_north", "watchtower_north", "wall_corner_ne"],
  "aggro_radius": 20,
  "faction": "red_kingdom",
  "dialogue_profile": "red_guard_01"
}

위 예시는 권장 확장 형태이며 현재 npc_instances.json 스키마에 모두 구현된 필드는 아니다.

마스터데이터 레퍼런스액션 카탈로그아키타입
Q5

“지정된 위치를 순찰하다가 플레이어가 보이면 공격”은 어떻게 설계하는가?

평상시 순찰은 플랜으로, 플레이어 감지와 공격은 결정론적 인터럽트로 나눈다. 적을 발견한 뒤 LLM 응답을 기다리면 안 되기 때문이다.

평상시 플랜

{
  "goal": "guard_north_gate",
  "steps": [
    {
      "action": "Patrol",
      "args": {
        "route": ["gate_north", "watchtower_north", "wall_corner_ne"],
        "laps": 3
      }
    },
    {
      "action": "Guard",
      "args": { "poi": "gate_north", "duration_s": 600 }
    }
  ],
  "loop": true
}

위협 발생 흐름

STEP 1게임서버가 시야·은신·세력을 판정한다.
STEP 2적대 플레이어 감지 이벤트를 보낸다.
STEP 3인터럽트가 순찰을 중단하고 어그로를 건다.
STEP 4게임서버가 이동·공격·피해를 판정한다.
STEP 5전투 종료 후 원래 순찰 플랜으로 복귀한다.
왜 인터럽트인가

인터럽트는 사람이 작성한 결정론 규칙이며 LLM이 생성하지 않는다. 공격, 도주, 긴급 대피처럼 반응 속도와 재현성이 중요한 행동은 이 경로에 둔다.

필요한 사전 데이터

  • 성문·감시탑 등 2~8개의 순찰 POI와 실제 이동 가능한 경로가 필요하다.
  • Patrol·Guard·Attack을 허용한 전투 가능 아키타입이 필요하다.
  • OnDuty가 켜지는 근무 시간과 무기 인벤토리가 필요하다.
  • 플레이어의 세력·적대 여부·은신·시야를 판단하는 게임서버 로직이 필요하다.
  • 대상 이탈·사망·전투 종료 후 순찰로 복귀시키는 이벤트와 규칙이 필요하다.

Q6

그 공격 시나리오는 현재 구현에서 어디까지 가능한가?

기능상태설명
플레이어 접근 수신가능PlayerProximity로 접근·이탈·거리를 받는다.
근접 상태 반영가능PlayerNearby 플래그를 설정한다.
전투·피해 시 위협 반응가능CombatStarted·DamageTaken이 ThreatNearby를 설정한다.
위협 시 공격·도주가능용기와 전투 가능 여부에 따라 Attack·Flee·Retreat을 실행한다.
적대 플레이어 선제공격확장 필요플레이어가 보인다는 사실과 적대 대상이라는 판단이 현재 분리되어 있다.
플레이어 대상 바인딩연결 필요계약에는 TargetPlayer가 있으나 현재 Attack은 npc_ref·TargetNpc 중심이다.
현재 그대로는 “보이는 모든 플레이어를 선제공격”하지 않는다.

PlayerProximity는 PlayerNearby만 설정하고, 기존 공격 인터럽트는 ThreatNearby를 조건으로 사용한다.

선제공격 NPC를 만들려면 게임서버의 적대 판정, HostilePlayerNearby에 해당하는 상태나 이벤트, $nearest_hostile_player 같은 대상 바인딩, 플레이어를 대상으로 하는 공격 액션 연결이 필요하다.

이벤트 적용기명령 계약인터럽트 규칙
Q7

NPC가 플레이어 또는 다른 NPC와 대화하는 것이 가능한가?

미리 작성된 대사를 ID로 재생하는 대화는 가능하지만, 플레이어와의 실시간 자유대화는 현재 범위에 없다.

현재 가능 주제형 대화

Talk과 Gossip이 greeting·trade·rumor·warning 같은 주제를 고르고 Speak 명령으로 대사 ID를 보낸다.

확장 필요 자유대화

현재 명령 계약은 문자열이 아니라 DialogueId만 전달하며 자연어 생성은 범위 밖이라고 명시한다.

STEP 1플레이어가 NPC와 상호작용한다.
STEP 2PlayerInteracted 이벤트가 들어온다.
STEP 3NPC가 warning 같은 주제를 선택한다.
STEP 4게임서버가 대사 ID에 해당하는 문장을 재생한다.

이 방식은 응답이 빠르고 안전하며 번역·음성·검수·등급 심의를 관리하기 쉽다.

Q8

실시간 LLM 자유대화를 추가하려면 어떻게 확장해야 하는가?

행동 플랜 컴파일러에 대화를 억지로 넣기보다 행동 서버와 대화 서버를 분리하는 구조가 적합하다.

행동 서버

이동·순찰·일과·전투 반응을 결정하고 검증된 명령을 보낸다.

대화 서버

플레이어 발화, NPC 성격, 퀘스트 상태, 세계관 지식으로 답변을 생성한다.

게임서버

아이템 지급, 거래, 퀘스트 변경, 전투 등 실제 상태 변경을 최종 승인한다.

대화 서버에 필요한 데이터

  • NPC의 이름, 말투, 성격, 가치관과 금지 행동이 필요하다.
  • NPC가 알 수 있는 세계관·지역·직업 지식의 범위를 정해야 한다.
  • 현재 퀘스트 상태, 플레이어와의 관계와 평판을 제공해야 한다.
  • 최근 대화 요약과 장기 기억의 저장·삭제 정책이 필요하다.
  • 프롬프트 인젝션, 욕설, 개인정보, 스포일러에 대한 안전 규칙이 필요하다.
  • LLM 지연·장애·비용 한도 초과 시 사용할 고정 대사가 필요하다.
  • 거래·퀘스트·보상은 제한된 도구 계약으로 게임서버 승인을 받아야 한다.

권장 응답 형식

{
  "text": "이 앞은 통행할 수 없다. 북문으로 돌아가라.",
  "emotion": "stern",
  "intent": "warn",
  "suggested_action": "deny_entry"
}
LLM이 게임 상태를 직접 변경하게 해서는 안 된다.

대화 모델은 행동을 제안할 수 있지만 아이템 지급, 퀘스트 변경, 공격 시작, 문 개방 같은 실제 효과는 게임서버가 권한과 조건을 검증한 뒤 실행해야 한다.

권장 도입 순서

  1. 전체 NPC에 현재의 DialogueId 기반 고정 대화를 적용한다.
  2. 퀘스트 제공자나 주요 인물처럼 소수의 핵심 NPC에만 자유대화를 붙인다.
  3. LLM 응답이 늦거나 실패하면 즉시 고정 대사로 폴백한다.
  4. 품질·비용·안전성이 검증된 뒤 기억과 퀘스트 도구를 단계적으로 추가한다.

정리하면 LlmNpcServer는 행동과 정해진 대사 재생까지 수용하며, 실시간 자연어 대화는 별도 대화 서비스와 게임서버 계약 확장이 필요한 상태다.
