## 2. 골든 시나리오 회귀 테스트 (W11)

모델·프롬프트·마스터데이터를 바꿔도 플랜 품질이 퇴행하지 않는지 확인한다.

### 픽스처 50건

```jsonc
// tests/golden/blacksmith_evening_war_cold.json
{
  "id": "G-014",
  "input": {
    "bucket": "blacksmith@Evening.War.Cold",
    "flags": ["AtWorkplace","HasTool","IsHungry","RegionUnderAttack","WeatherHarsh"],
    "inventory": { "coal": 3, "iron_ore": 0 }
  },
  "assertions": [
    { "kind": "validates",        "stage": "DryRun" },
    { "kind": "contains_action",  "action": "Craft" },
    { "kind": "produces_item_of", "category": "product" },
    { "kind": "not_contains",     "action": "Wander" },
    { "kind": "ends_with_any",    "actions": ["Sleep","Rest"] },
    { "kind": "step_count_between", "min": 4, "max": 9 },
    { "kind": "acquires_before_use", "item": "iron_ore", "action": "Craft" },
    { "kind": "avoids_flag_while", "flag": "InWilderness", "when": "WeatherHarsh" }
  ]
}
```

**속성(property) 단언만 쓴다. 정확한 문자열 비교는 절대 하지 않는다.** LLM 출력은 매번 다르고, 그게 정상이다. 우리가 보장할 것은 "무기를 만든다"이지 "정확히 3자루를 만든다"가 아니다.

### 단언 종류

| kind | 의미 |
|---|---|
| `validates` | 지정 단계까지 검증 통과 |
| `contains_action` / `not_contains` | 특정 액션 포함/배제 |
| `produces_item_of` | 결과물이 특정 카테고리 (`items.json` 의 `category`) |
| `ends_with_any` | 마지막 스텝 |
| `step_count_between` | 스텝 수 범위 |
| `acquires_before_use` | 소비 전에 획득하는가 (정합성) |
| `avoids_flag_while` | 특정 상황에서 특정 상태 회피 |
| `differs_from` | 지정한 다른 버킷의 플랜과 다른가 ← **다양성 단언** |

### 실행

```
dotnet test --filter Category=Golden
  → 50건 × 3회 생성(변동성 흡수) = 150 호출
  → 각 단언의 3회 중 2회 이상 통과를 합격으로
  → 합격률 ≥ 90% 를 CI 게이트로
```

3회 실행하는 이유는 LLM 출력이 확률적이기 때문이다. 1회로 판정하면 테스트가 산발적으로 깨져서 아무도 안 믿게 된다.

## 3. 결정론 리플레이 (W11)

```
1. 시나리오 A를 RecordingGameServerLink 로 실행
     → run1/commands.jsonl, run1/events.jsonl, run1/plans.jsonl
2. 같은 로그를 ReplayGameServerLink 로 재생 (LLM 호출 없음, 기록된 플랜 사용)
     → run2/commands.jsonl
3. run1/commands.jsonl == run2/commands.jsonl  (바이트 동일)
```

### 결정론을 깨는 것들 — 전부 제거해야 한다

| 원인 | 대응 |
|---|---|
| `DateTime.Now` / `Stopwatch` | 게임 로직에서 전면 금지. `Tick`만 사용 (§02 N4) |
| `Random` 무시드 | 모든 난수는 `(npcId, tick)` 해시 기반 |
| `Dictionary` 순회 순서 | 순회 순서에 의존하는 로직 금지. 정렬된 배열 사용 |
| 병렬 실행 순서 | 틱 루프는 단일 스레드. 워커 결과는 스텝 경계에서만 반영 |
| LLM 응답 | 리플레이에서는 기록된 플랜을 사용 (LLM 미호출) |
| `HashSet`/`HashCode` 랜덤화 | `<UseRandomizedStringHashAlgorithm>false</>` 또는 문자열 해시 미사용 |

**이 테스트가 통과하면 버그 재현이 가능해진다.** 리스크 R5의 해소 지점이며, 상용 전환 논의에서 가장 자주 나오는 질문("비결정적인 걸 어떻게 디버깅하나")에 대한 답이다.

## 4. 장애 주입 — 시나리오 C (W11)

```jsonl
{"at_tick": 6000,  "event": "KillSwitch", "target": "T2"}
{"at_tick": 12000, "event": "KillSwitch", "target": "T1"}
{"at_tick": 18000, "event": "KillSwitch", "target": "PlanStore"}
```

| 단계 | 남은 것 | 기대 동작 |
|---|---|---|
| T2 차단 | 캐시 + T1 | 아키타입 플랜 요청이 T1으로 페일오버. 지연 상승, 동작 유지 |
| T1까지 차단 | 캐시만 | 재계획 전면 중단. 기존 버킷 플랜으로 계속 동작 |
| PlanStore까지 차단 | 폴백만 | 40개 폴백 플랜으로 5,000 NPC 동작 |

**검증 기준: 세 단계 모두에서 NPC가 멈추지 않고, 크래시가 없고, 틱 시간이 예산 내다.**

추가 장애:

```
[ ] 링크 단절 (LinkState.Faulted) → 명령 축적 → 복구 시 재개
[ ] 이벤트 시퀀스 갭 주입 → 경보 발생, 동작 유지
[ ] 명령 드롭율 5% → 타임아웃 합성으로 플랜 진행 유지
[ ] 외부 API 429 폭주 → AIMD 감속, 크래시 없음
[ ] 외부 API 타임아웃 30초 → 서킷 브레이커 개방
```

## 5. 링크 교체 검증 (W11)

§02 문서의 최종 검증. **NPC 서버 코드 무변경**이 조건이다.

```
같은 시나리오를 4가지 링크로 실행:
  1. NullGameServerLink       → 명령 폐기. 크래시 없이 완주 (성능 기준선)
  2. LoopbackGameServerLink   → 정상 동작 (기준)
  3. RecordingGameServerLink  → Loopback 데코레이트. 결과 동일 + 로그 생성
  4. ReplayGameServerLink     → 3의 로그 재생. 명령 시퀀스 동일

검증: git diff 에 src/Npc.Runtime, src/Npc.Core, src/Npc.Planning 변경 0
```

`TcpGameServerLink`는 미구현이지만, **컴파일은 되어야 한다.** 인터페이스를 만족하는 골격이 존재한다는 것 자체가 "나중에 붙일 수 있다"의 최소 증거다.

## 6. 블라인드 A/B 평가 (W12) — **이 프로젝트의 핵심 판정**

### 설계

```
대상: 사내 기획자·개발자 12명 이상 (게임 도메인 이해자)
자료: NPC 하루 행동 로그를 사람이 읽을 수 있는 서술로 변환한 것

  A군: LLM 생성 플랜으로 동작한 NPC 20마리
  B군: 사람이 손으로 짠 폴백 플랜으로 동작한 NPC 20마리
  (아키타입·시간대·지역상태를 짝지어 매칭)

절차:
  1. 40건을 무작위 순서로 제시. 어느 쪽인지 알려주지 않는다
  2. 각 건에 대해 두 질문:
     Q1. 이 NPC는 LLM이 계획했는가, 사람이 계획했는가? (강제 선택)
     Q2. 이 NPC의 행동이 상황에 얼마나 잘 맞는가? (1~5)
  3. 추가로 짝지은 A/B를 나란히 제시하고 "어느 쪽이 더 자연스러운가" 선택
```

### 서술 변환 예시

```
[NPC #1247 · 대장장이 · 공성 중 · 겨울 저녁]
06:20  집에서 일어남
06:45  대장간 도착
07:00  광석 재고 없음 확인
07:10  광산으로 이동 (뛰어서)
07:50  철광석 8개 채굴
09:30  대장간 복귀
09:45  철검 3자루 제작 시작
12:20  제작 완료, 창고에 보관
12:30  빵을 먹음
13:00  성문으로 이동, 경비대장에게 검 전달
14:00  대장간 복귀, 추가 제작
19:30  귀가
20:00  취침
```

**로그를 이 형태로 바꾸는 도구를 만들어야 한다** (`tools/Npc.Narrate`). 대사 생성이 아니라 액션 시퀀스의 기계적 번역이므로 LLM이 필요 없다.

### 판정 기준

| 결과 | 해석 | 결론 |
|---|---|---|
| Q1 정답률 ≈ 50% (구분 불가) + Q2에서 A ≥ B | LLM 플랜이 사람 수준 | **오써링 자동화로 가치 확정.** 런타임 LLM은 선택 사항 |
| Q1 정답률 ≈ 50% + Q2에서 A < B | LLM 플랜이 열등한데 티만 안 남 | 프롬프트·모델 개선 필요. 현 상태로는 부적합 |
| Q1 정답률 > 70% (A가 티남) + Q2에서 A > B | LLM 플랜이 눈에 띄게 더 좋음 | **최상 결과.** 런타임 투입 검토 |
| Q1 정답률 > 70% + Q2에서 A < B | LLM 플랜이 어색함 | 실패. 액션 카탈로그·검증기 강화 필요 |

**"구분 불가"는 실패가 아니다.** 사람이 만든 것과 구분이 안 되는 것을 2,880개를 3분에 만들었다면, 그것이 곧 성공이다. 이 프레이밍을 평가 설계 단계에서 참가자에게 미리 설명하지 않는 것이 중요하다(편향 방지).

### 통계 처리

```
n = 12명 × 40건 = 480 판정
Q1: 이항검정. H0 = 정답률 0.5
Q2: 짝지은 t검정 (A vs B), 효과크기 Cohen's d
쌍대 비교: 부호검정
신뢰구간 95% 를 반드시 병기한다
```

12명 × 40건이면 정답률 ±4.5%p 정도의 정밀도가 나온다. 참가자가 6명 미만이면 결론을 내지 말고 표본을 늘린다.

## 7. 오써링 공수 정산 (W12)

```
분모 (수작성):   docs/measurements/authoring_time.jsonl  (W4에서 기록)
                 40개 × 평균 M분

분자 (LLM):      planstore/manifest.json  의 wall_clock_s
               + docs/measurements/review_W8.jsonl 의 검수 시간
```

### 정직하게 계산하는 법

```
LLM 경로 총 공수
  = 프롬프트/스키마 설계 (1회, W5~W6에 실제로 든 시간)
  + 프리베이크 실행 (3분)
  + 검수 (2,880 × 평균 검수분)
  + 수정 (edit 판정분 × 평균 수정분)

수작성 경로 총 공수
  = 2,880 × 평균 작성분   ← W4의 40개 실측을 외삽
```

**함정 두 가지를 피한다.**

1. **프롬프트 설계 공수를 빼먹지 않는다.** W5~W6의 통과율 개선 루프에 들어간 시간은 실제 비용이다. 다만 이건 **1회성**이므로, 버킷 수가 늘어날수록 희석된다는 점을 함께 제시한다.
2. **"사람은 애초에 2,880개를 만들지 않는다"** 는 사실을 명시한다. 현실의 대안은 "2,880개 수작성"이 아니라 "40개만 만들고 나머지는 포기"다. 따라서 비교는 두 축으로 제시한다.
   - 축 A: 같은 결과물(2,880개)을 만드는 비용 비교 → 절감률
   - 축 B: 같은 비용으로 얻는 결과물 비교 → 커버리지 배수 (40개 → 2,880개, 72배)

**축 B가 더 정직하고 더 설득력 있다.**

## 8. 비용 실측 정산 (W12)

| 항목 | 실측 출처 |
|---|---|
| 프리베이크 1회 비용 | `manifest.json.cost_usd` |
| 시나리오 A 7게임일 런타임 비용 | 메트릭 누적 |

## 9. R&D 보고서 구성 (W12)

```
1. 요약 — 판정과 권고 (1페이지)
2. 무엇을 만들었나 — 데모 3종 스크린샷/영상
3. 기술 검증 결과
   3.1 처리량·지연 실측 vs 계획 추정
   3.2 캐시 아키텍처 효과 (히트율, 요청 절감)
   3.3 비용 실측
   3.4 가용성 (시나리오 C)
4. 품질 검증 결과
   4.1 검증 통과율과 실패 원인 분포
   4.2 블라인드 A/B 결과 (통계 포함)
   4.3 플랜 다양성
5. 오써링 공수 — 축 A(절감률) / 축 B(커버리지 배수)
6. 발견과 예상 밖의 것
   - 버킷 히트맵: 실제로 쓰인 버킷 비율 (2,880 중 몇 개?)
   - 4B vs 8B 품질 차이
   - dotLLM prefill 병목의 실제 영향
7. 상용 전환 시 남는 과제
   - 실제 네트워크 구현 (§02 §7)
   - GPLv3 (별도 프로세스 경계 유지 / 법무 확인)
   - 다중 월드 스케일 비용
   - continuous batching 부재 → llama.cpp/vLLM 전환 검토
8. 권고
```

### 6번 "발견"이 보고서에서 제일 가치 있을 가능성이 높다

특히 **버킷 히트맵**. 2,880개를 만들었는데 실제로 쓰인 게 300개라면, 그건 "버킷 차원을 잘못 설계했다"가 아니라 **"다음 버전은 1/10 비용으로 만들 수 있다"** 는 발견이다.

## 11. 프로젝트가 실패로 끝날 수 있는 경우와, 그때 남는 것

정직하게 적어둔다. 아래 어느 경우라도 **버려지는 것은 LLM 부분뿐이고, 나머지는 남는다.**

| 실패 양상 | 그래도 남는 자산 |
