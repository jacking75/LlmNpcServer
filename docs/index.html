LLM NPC 서버

로컬·외부 LLM을 행동 플랜 컴파일러로 써서 MMORPG NPC 5,000마리의 하루 일과를 상황별로 자동 생성하고, 결정론적 런타임이 그것을 10Hz로 실행하며 게임서버에 명령을 송출한다.

사내 R&D · 기술 검증 .NET 10 · C# Windows 10/11 x64 프로젝트 9 + 도구 2 태스크 132 / 164 완료 문서 기준일 2026-07-27

한 문장 요약 — LLM은 느리게 플랜을 만들고, 런타임은 빠르고 재현 가능하게 실행한다. LLM이 전부 죽어도 NPC는 멈추지 않는다.

처음 보는 사람은 1 → 2 → 3 그림 → 4 애니메이션 순으로. 코드를 봐야 하는 사람은 5 구현 안내 → 6 분석 가이드로 바로 가도 된다. 움직이는 그림이 거슬리면 왼쪽 애니메이션 버튼으로 전부 멈출 수 있다.

01이건 무슨 프로젝트인가

MMORPG에서 마을 NPC 수천 마리에게 "사람 같은 하루"를 만들어 주려면, 지금까지는 기획자가 스크립트를 일일이 작성해야 했다. 이 프로젝트는 그 작업을 LLM에게 시킬 수 있는지, 시켰을 때 성능·비용·품질·가용성이 실제 서비스에 견딜 수준인지를 12주 동안 숫자로 확인한 R&D다.

✅ 만드는 것

  • NPC 서버 (Npc.Host) — 본체
  • 게임서버 경계 (IGameServerLink + 패킷 정의)
  • 게임서버 대역 (Npc.Sim) — 진짜 게임서버 없이 검증하기 위한 가짜 월드
  • 플랜 2,880개 — 사람이 읽고 고칠 수 있는 JSON

❌ 안 만드는 것

  • 실제 MMORPG 게임서버 — 이미 있거나 남이 만든다
  • 실제 네트워크 전송(소켓·직렬화) — 인터페이스·패킷 정의까지만
  • 게임 클라이언트 · 렌더링
  • NPC 자연어 대사 — Speak(DialogueId)로 ID만 송출
  • 전투 AI · 패스파인딩 — 게임서버 소관

📍 지금 상태

  • P1(코어·런타임)·P5(검증) 태스크 완료
  • P4(스케줄러·티어링) 미착수 → 런타임 LLM 경로는 아직 실측이 없다
  • 빌드 경고 0 · 오류 0, 테스트 795건 통과
  • 최종 수용 기준 16개 중 9 통과 · 7 미달

이름에 대한 오해 하나만 먼저. IGameServerLink의 "GameServer"는 상대방을 가리킨다. "게임서버가 구현할 인터페이스"가 아니라 "게임서버로 향하는, NPC 서버의 아웃바운드 포트"다. 이 저장소는 NPC 서버 쪽만 만든다.

이 구조가 나온 이유

부딪힌 문제이 프로젝트의 답
소비자 GPU 1장으로 NPC 5,000마리를 주기적으로 재계획하면 용량의 2.4배를 넘는다 플랜을 (아키타입 × 상황) 단위로 캐시한다. 개별 재계획은 예산 안에서 우선순위로 선별
LLM을 오래 돌리면 컨텍스트가 드리프트한다 모든 호출을 무상태로. 기억은 게임 DB에 구조체로, 요약은 규칙으로. 드리프트가 원천 발생하지 않는다
외부 API 지연이 p99에서 수십 초까지 튄다 LLM을 게임 크리티컬 패스에서 완전히 뺀다. 틱 루프 안에 LLM 호출이 존재하지 않는다
LLM이 죽거나 매번 다른 답을 준다 플랜을 생성 시점에 저장. 캐시 → 인접 재사용 → 폴백 3단 방어. 리플레이는 LLM 없이 재현

02핵심 아이디어 — LLM을 실행기가 아니라 컴파일러로

흔한 접근은 "NPC가 행동할 때마다 LLM에게 물어본다"이다. 그러면 NPC 1마리당 1초에 한 번씩 LLM을 불러야 하고, 5,000마리면 초당 5,000 요청이다. 비용도 지연도 성립하지 않는다.

이 프로젝트는 반대로 간다. LLM은 "대장장이가 비 오는 저녁, 전시 상황에 하는 일과"라는 플랜을 한 번 만들어 둔다. 그 플랜은 JSON이고, 런타임은 그 JSON을 배열 첨자로 꺼내 0.4밀리초 만에 실행한다. 같은 상황의 대장장이 200마리가 같은 플랜을 공유한다.

생성 (느려도 된다)

초 단위 지연, 돈이 든다, 결과가 매번 다르다. → 미리, 배치로, 검증해서 저장.

실행 (빨라야 한다)

10Hz 틱, 예산 20ms, 힙 할당 0, 리플레이 100% 일치. → LLM이 끼어들 자리가 없다.

이 판단의 결과가 실측으로 나왔다. NPC 5,000마리에서 틱 p99가 0.37ms(예산 20ms의 1.9%)이고, 틱 루프의 힙 할당은 0 바이트다. 그리고 LLM을 3단계로 전부 차단해도 5,000마리가 게임 13일을 완주한다.

3.3 NPC 한 마리가 한 걸음 내딛는 과정

글로 먼저 읽고, 4장에서 같은 것을 움직여 본다.

  1. 틱이 온다 — 100ms마다. GameClock이 Tick(long)을 하나 올린다. 벽시계는 보지 않는다.
  2. 인지 스캔 — 전수 5,000마리를 보지 않는다. LOD 밴드별로 시야내 매 틱 · 동일존 10틱 · 원거리 100틱 · 비활성 이벤트 시에만. 틱당 스캔 상한 150마리.
  3. 인터럽트 판정 — "피습", "화재" 같은 즉시 반응은 규칙이 판정한다. LLM에게 묻지 않는다. 반응 속도가 필요한 것은 전부 규칙이다.
  4. 플랜 조회 — PlanStore.Resolve(버킷키). 배열 첨자 하나. 미스면 인접 버킷 → 아키타입 폴백 순으로 내려간다.
  5. 스텝 실행 — 현재 스텝의 전제조건(월드 플래그 비트마스크)을 확인하고, 만족하면 명령을 만든다.
  6. 명령 송출 — Enqueue로 배치에 쌓고 틱 끝에 FlushAsync 한 번. 모든 명령에 CorrelationId가 붙는다.
  7. 이벤트 수신 — 게임서버(또는 Npc.Sim)가 ActionCompleted / ActionFailed를 Sequence와 함께 돌려준다. 갭이 생기면 경보.
  8. 응답이 안 오면 — 모든 스텝에 timeout_s가 있다. 지나면 로컬에서 ActionFailed(Timeout)을 합성해 진행을 재개한다. 명령은 유실된다고 가정한다.
  9. 재계획 필요 판정 — 전제가 이탈했거나 지역 상태가 바뀌었으면 재계획 큐에 점수와 함께 넣는다. 실제 LLM 호출은 틱 밖에서 일어나고, 결과는 Volatile.Write로 전달된다.
  10. 플랜 교체 — 스텝 경계에서만 원자적으로 스왑한다. 스텝 중간에 바꾸면 CorrelationId가 꼬인다. (인터럽트만 예외 — 즉시 스왑하되 진행 중 명령은 상관 ID로 무시)

Npc.Runtime은 Npc.Llm을 참조하지 않는다. 참조가 생기는 순간 틱 루프에 LLM이 들어올 길이 열리기 때문이다. 이 규칙은 ArchitectureTests가 리플렉션으로 강제한다 — 어기면 빌드가 아니라 테스트가 깨진다.

같은 이유로 Npc.Runtime·Npc.Core·Npc.Planning은 Npc.Gateway를 참조조차 하지 않는다. 그래서 링크 구현체를 Loopback → Null → Recording으로 갈아 끼워도 NPC 서버 코드가 한 줄도 안 바뀐다.

3.8 플랜은 어떻게 생겼나

LLM이 만드는 것도, 사람이 고치는 것도 이 JSON이다. masterdata/fallback_plans.json의 대장장이 폴백 플랜을 그대로 옮긴 것이다. 

{
  "id": "fb_blacksmith",
  "archetype": "blacksmith",
  "goal": "earn_and_rest",
  "steps": [
    { "action": "MoveTo", "args": { "poi": "$workplace" },            "timeout_s": 300  },
    { "action": "Work",   "args": { "recipe": "iron_sword", "count": 1 }, "timeout_s": 900  },
    { "action": "Trade",  "args": { "item": "iron_sword", "amount": 1 }, "timeout_s": 600  },
    { "action": "MoveTo", "args": { "poi": "$tavern" },               "timeout_s": 300  },
    { "action": "Drink",  "args": {},                                "timeout_s": 120  },
    { "action": "MoveTo", "args": { "poi": "$home" },                 "timeout_s": 300  },
    { "action": "Sleep",  "args": { "until_time": "Morning" },          "timeout_s": 7200 }
  ],
  "on_step_fail": "skip",
  "loop": true
}
  • $workplace·$home 같은 심볼은 NPC마다 실제 POI로 바인딩된다. 그래서 같은 플랜을 200마리가 공유해도 각자 자기 대장간으로 간다.
  • timeout_s가 없는 스텝은 존재할 수 없다 — 명령 유실 시 복구할 방법이 사라진다.
  • 플랜 JSON은 사람이 열어서 고치고 planstore/pinned/에 pin할 수 있다. pin된 플랜은 재생성해도 덮이지 않는다.

5.5 Npc.Runtime — 심장부

전체 14파일 2,707줄. 이 저장소에서 가장 규칙이 빡빡한 곳이고, 대신 가장 짧다. 틱 루프 본체는 220줄이고 그중 실제 한 틱은 아래 열다섯 줄이다.

/// 틱 한 번을 손으로 돌린다. 테스트와 드라이런이 쓴다.
public void RunTick(Tick tick, int drained = 0)
{
    Observer?.OnTickBegin(tick);

    _bands.Rebalance();
    _cognition.Scan(tick, _replanQueue);
    _executor.Step(tick, _link);

    // 시간대 전환 예약은 스왑 적용 전에 걸어야 이번 틱의 스텝 경계에서 갈아탄다.
    Transition?.Tick(_clock, _swapper);

    _swapper.ApplyPendingSwaps(_executor);

    TicksProcessed++;
    Observer?.OnTickEnd(tick, _cognition.LastScanned, drained);
}
이 메서드에 async가 붙어 있지 않다는 것이 핵심이다. await를 쓸 수 없으니 LLM도, 파일 IO도, 네트워크도 들어올 수 없다. Observer가 별도 인터페이스인 이유도 같다 — 시간 측정은 벽시계를 봐야 하는데 게임 로직이 벽시계를 보면 리플레이가 깨지므로, 계측은 Npc.Runtime 밖(호스트)에서 한다.

23바이트 × 5,000 = 약 115KB. 요즘 CPU의 L2 캐시에 통째로 들어간다. class Npc를 5,000개 만들었다면 참조 추적 5,000번 + 흩어진 캐시 라인이 됐을 것이다. 인벤토리도 int[][]가 아니라 평탄한 1차원 배열 + 스트라이드다 — Inventory[npc * InventoryStride + itemCode]. 배열 5,000개는 그 자체가 비용이다.

5.6 Npc.Planning — 캐시와 큐

PlanStore는 표를 둘 들고 있다. 버킷으로도 찾고 PlanId로도 찾는다 — 런타임이 NPC마다 들고 있는 것은 버킷이 아니라 NpcStore.PlanId[i]이기 때문이다.

src/Npc.Planning/PlanStore.cs — Resolve 핵심부
public CompiledPlan Resolve(BucketKey key, out PlanOrigin origin)
{
    int index = key.ToIndex();
    int planId = Switches.IsDisabled(KillSwitchTarget.PlanStore)
        ? IdlePlanId
        : Volatile.Read(ref _byBucket[index]);

    if (planId != IdlePlanId)
    {
        Interlocked.Increment(ref _hits[index]);
        origin = (PlanOrigin)Volatile.Read(ref _origin[index]);
        return this[planId];
    }

    Interlocked.Increment(ref _misses[index]);
    origin = PlanOrigin.Fallback;

    // 미스여도 항상 유효한 플랜을 반환한다.
    int fallback = (uint)key.A.Value < (uint)_byArchetype.Length
        ? Volatile.Read(ref _byArchetype[key.A.Value])
        : IdlePlanId;

    return this[fallback];
}
lock이 한 줄도 없다. 읽기는 Volatile.Read, 쓰기는 원자 참조 교체다. 읽는 쪽이 한 틱 낡은 플랜을 봐도 다음 틱에 새것을 본다. List<T>를 안 쓰는 이유도 같다 — 내부 배열 교체와 Count 갱신 사이에 읽는 쪽이 범위 밖을 볼 창이 열린다. 그래서 고정 크기 청크 배열이다.

ReplanQueue는 지금 FIFO + 중복 제거만 한다(P4에서 우선순위 힙으로 교체 예정). TryEnqueue(npc, score)가 이미 점수를 받는 이유가 그것이다 — 인터페이스를 바꾸지 않고 내부만 갈아 끼울 수 있게 미리 열어 뒀다. 같은 NPC를 두 번 넣지 않는 것이 핵심인데, 중복을 허용하면 큐가 즉시 포화된다.

public PlanTier SelectTier(in PlanRequest request)
{
    // 재사용 횟수에 비례해 품질에 투자한다.
    // 아키타입 플랜은 수천 NPC 가 공유하므로 T2, 개체 1회용은 T1.
    PlanTier wanted = request.Quality == PlanQuality.Archetype
        ? PlanTier.T2
        : PlanTier.T1;

    return Downgrade(wanted);
}

/// 쓸 수 없으면 한 단계 내린다. T2 → T1 → None.
private PlanTier Downgrade(PlanTier tier)
{
    if (tier == PlanTier.T2 && Available(PlanTier.T2)) return PlanTier.T2;
    return Available(PlanTier.T1) ? PlanTier.T1 : PlanTier.None;
}

6.3 추적 시나리오 — 콜 체인을 따라가기

코드를 "읽는" 대신 하나의 사건을 끝까지 따라가는 방법. 다섯 개면 충분하다.

Npc.Runtime이 Npc.Llm을 참조하지 않는다 Architecture/ArchitectureTests.cs 허용 참조 집합을 Dictionary로 박아 두고 .csproj의 ProjectReference를 XML로 읽어 대조
패킷에 string·DateTime·참조 필드가 없다 (N2·N3·N4) Contracts/ContractRuleTests.cs Npc.Contracts 어셈블리의 모든 public struct를 리플렉션으로 훑는다
이벤트 처리가 멱등이다 (N7) Runtime/EventApplierTests.cs 같은 이벤트를 2회 주입하고 NpcStore.StateHash()가 같은지
리플레이가 100% 일치한다 Determinism/ReplayTests.cs Recording으로 남긴 jsonl을 Replay로 재생해 명령 열이 바이트 동일한지
게임 로직이 DateTime·Stopwatch를 안 쓴다 Determinism/ClockAuditTests.cs 소스 감사. 화이트리스트는 어셈블리 단위로 Npc.Host 하나뿐이다
무시드 Random을 안 쓴다 Determinism/RandomAuditTests.cs 같은 방식의 소스 감사
틱 루프의 힙 할당이 0이다 Runtime/TickAllocationTests.cs GC.GetAllocatedBytesForCurrentThread() 델타. 다른 테스트와 병렬로 못 돈다 — 옆 스레드 할당이 델타를 오염시킨다
인지 스캔이 틱당 150을 넘지 않는다 Runtime/CognitionSchedulerTests.cs 군중 상황을 만들고 LastScanned를 본다
응답이 안 와도 진행이 재개된다 Runtime/TimeoutSynthesisTests.cs 이벤트를 안 주고 틱만 돌려 ActionFailed(Timeout)이 합성되는지
프롬프트 서픽스가 300토큰을 안 넘는다 Llm/SuffixBudgetTests.cs 상한이 상수 Budget = 300으로 박혀 있다
링크를 갈아 끼워도 NPC 서버 코드가 안 바뀐다 Gates/LinkSwapTests.cs 4종을 각각 기동하고 같은 시나리오에서 판단이 같은지까지 본다
LLM을 전부 끊어도 NPC가 돈다 (시나리오 C) Scenarios/BlackoutTests.cs KillSwitch로 실제로 끊고 완주하는지

6.6 파일을 열기 전에 알아 둘 것

주석 규약이 있다

거의 모든 public 타입의 <summary> 첫 줄에 docs/11 §4처럼 사양 문서의 절 번호가 적혀 있다. "왜 이렇게 짰나"가 궁금하면 그 절을 읽으면 된다.

주석이 금지 사항을 설명하는 경우가 많다 — "왜 List<T>를 쓰지 않는가", "왜 여기서 끊는가". 그런 주석은 대개 실제로 한 번 데인 자리다.

큰 파일부터 열지 않는다

MasterDataSet.cs(1,055) · MasterDataValidator.cs(755) · ActionCatalog.cs(739) · Program.cs(753)는 대부분 로딩·파싱·검증 코드다. 구조를 이해하는 데 기여하지 않는다.

구조는 작은 파일들에 있다 — IGameServerLink.cs(59) · BucketKey.cs(97) · CognitionScheduler.cs(124) · PlanSwapper.cs(129).

이름 규칙

  • 코드 주석 · 커밋 메시지 · 문서는 한국어
  • 식별자 · 타입명 · 로그 메시지는 영어
  • N1~N8 = 게임서버 계약 규칙 (docs/02)
  • V1~V13 = 마스터데이터 검증 (docs/01)
  • V1.*~V4.* = 플랜 검증 실패 코드 (docs/03)
  • T{n}-{nn} = 태스크 번호. 주석에 자주 나온다

"아직 없는 것"이 주석에 적혀 있다

P4(스케줄러·티어링)가 미착수라 ReplanQueue·TieredPlanCompiler 등에는 "정식은 T4-01이 넣는다" 같은 주석이 붙어 있다.

이 주석들을 신뢰해도 된다. 없는 기능을 있는 척하지 않는 것이 이 저장소의 방침이고, Gate 카테고리 테스트가 산출물이 없으면 실패하도록 되어 있는 것도 같은 이유다.

07용어 사전

문서와 코드 전체가 이 단어들을 쓴다. 여기만 읽어도 대화가 통한다.

아키타입 archetype
NPC의 직업 원형. 대장장이·농부·경비병 등 40종. 어떤 액션이 허용되는지, 인구의 몇 %인지, 폴백 플랜이 무엇인지를 정한다.
버킷 BucketKey
플랜 캐시의 키. (아키타입 40 × 시간대 6 × 지역상태 4 × 기후 3) = 2,880. 시간대는 Dawn·Morning·Noon·Afternoon·Evening·Night, 지역상태는 Peace·Alert·War·Disaster, 기후는 Fair·Cold·Storm. 0~2879로 전단사 매핑되므로 조회는 배열 첨자 한 번이다.
플랜 Plan / 스텝 Step
NPC 하루 일과의 액션 시퀀스와 그 한 칸. 각 스텝에는 액션·인자·timeout_s가 있다.
폴백 플랜 fallback_plan
아키타입마다 하나씩 사람이 손으로 쓴 플랜. LLM이 전부 죽어도 이것으로 돈다. 이 40개가 "LLM 없이 만들었다면 나왔을 결과물"의 실제 크기이기도 하다.
핀 pin
사람이 검수·수정한 플랜을 planstore/pinned/에 고정하는 것. 로드할 때 생성분(plans/)을 덮어쓴다. 재생성해도 살아남는다.
인지 LOD Level of Detail
NPC를 플레이어와의 거리에 따라 4밴드로 나눠 스캔 주기를 다르게 한다 — 시야내 매 틱 · 동일존 10틱 · 원거리 100틱 · 비활성 이벤트 시에만. 밴드 이동은 PlayerProximity 이벤트로만 일어나고, 틱당 최대 64건으로 제한한다.
SoA struct of arrays
NPC 5,000마리를 객체 5,000개가 아니라 "필드별 배열"로 갖는 방식. 캐시 지역성을 위해서다.
3티어 T0 / T1 / T2
T0 = 캐시(플랜 스토어), T1 = 로컬 LLM, T2 = 외부 API. 재사용 횟수가 많으면 T2로 고품질을, 1회용이면 T1을 쓴다. 예산을 넘으면 T2 → T1 → 거절 순으로 강등한다.
프리픽스 / 서픽스
프롬프트의 고정부와 가변부. 프리픽스는 기동 시 1회 조립하고 이후 절대 변하지 않는다(현재 11,967 토큰) — 그래야 제공사의 프롬프트 캐시가 적중한다. 서픽스는 300 토큰 이하로 테스트가 강제한다. 재시도 피드백도 서픽스에만 넣는다.
프리베이크 prebake
2,880개 버킷의 플랜을 서비스 시작 전에 배치로 미리 생성하는 것. tools/Npc.Prebake가 한다.
인터럽트 interrupt
진행 중인 플랜을 즉시 갈아 끼우는 사건(피습·화재 등). 규칙이 판정한다. 반응 속도가 필요한 판정은 LLM에게 맡기지 않는다.
Npc.Sim (게임서버 대역)
진짜 게임서버 없이 검증하기 위한 우리 쪽 가짜 월드. 이동·상호작용·필요(배고픔 등)·플레이어 봇·시나리오 주입·장애 주입을 한다. --fail-rate(액션 실패)와 --drop-rate(명령 유실)로 상시 괴롭힐 수 있다.
링크 IGameServerLink
NPC 서버가 게임서버로 나가는 유일한 출구. 구현이 4종 있다 — Loopback(Sim 직결) · Null(아무데도 안 보냄) · Recording(jsonl 기록) · Replay(기록 재생).

08어디에 쓰는가

① 결정론적 NPC 행동 런타임 — 지금 바로 쓸 수 있는 부분

LLM 판정과 무관하게 이미 완성돼 있다. 마스터데이터와 폴백 플랜만으로 5,000마리를 틱 p99 0.37ms에 돌리고, 같은 입력이면 명령 시퀀스가 바이트 단위로 같다.

쓰는 법: --no-llm으로 기동하면 LLM이 개입할 여지가 아예 없다.

② 행동 플랜 오써링 자동화

사람이 40개(아키타입당 1개)를 쓰는 대신, 같은 비용으로 2,880개(아키타입 × 72상황)를 만든다. 커버리지 72배. 기계 시간 0.32h · $5.12.

쓰는 법: Npc.Prebake로 생성 → 4단 검증 통과분만 저장 → 사람이 열어서 고치고 pin.

③ 게임서버 붙이기 전의 통합 테스트 하네스

Npc.Sim + 링크 4종 + 시나리오 주입 + 장애 주입이 갖춰져 있다. 실제 게임서버가 없어도 "5,000마리가 공성 중에 어떻게 움직이는가"를 재현 가능하게 돌릴 수 있다.

쓰는 법: --link record로 남기고 --link replay로 재생한다.

④ "LLM을 게임에 넣어도 되는가"에 대한 실측 데이터

지연·비용·통과율·캐시 적중률·다양성이 전부 docs/measurements/에 원자료로 있다. 추정이 실제와 얼마나 어긋났는지도 같이 기록돼 있다(비용 5배, 지연 2~3배).

읽을 것: 실측 데이터 → 무엇이 빗나갔고 무엇이 맞았나.

실제 게임서버에 붙이려면

NPC 서버 코드는 건드리지 않는다. IGameServerLink 구현을 하나 더 만들고 호스트에서 갈아 끼우면 끝이다. Npc.Gateway/TcpGameServerLink.cs에 골격이 있다.

남은 작업내용
프레이밍길이 프리픽스 등
직렬화MemoryPack 또는 소스 생성. 패킷이 전부 readonly record struct라 유리하다
재접속 · 시퀀스 재동기화Sequence 갭에서 어디부터 다시 받을지
Nagle 비활성 + 배치 코얼레싱틱당 flush 1회 구조를 그대로 살린다
흐름 제어백프레셔

이 5가지 중 NPC 서버 쪽 코드를 고쳐야 하는 것은 없다. 런타임 3개 프로젝트가 Npc.Gateway를 참조조차 하지 않는다는 사실을 테스트가 고정하고 있다.

14.6 결론 한 문장

런타임 LLM은 아직 근거가 없고, 오써링 자동화는 근거가 생겼다. 그리고 이 프로젝트가 실제로 만들어 낸 것은 LLM 없이도 도는 결정론적 NPC 서버다.

블라인드 A/B의 예비 실시(LLM 심사원 6명 × 40건 = 240 판정)에서 Q1 정답률이 50.8%[44.5, 57.1] · p=0.85로 나왔다 — 사람이 만든 것과 구분하지 못한다는 뜻이다. 다만 심사원이 LLM이므로 정식 측정이 아니고, 이 값의 값어치는 "정식 평가를 돌릴 만하다"는 판단 하나다. 정식 평가에는 사람 12명 × 40~60분이 필요하다.

고치기 전에 확인할 것

  1. 건드리는 타입이 연동 계약·마스터데이터 레퍼런스에 정의되어 있는가 — 있으면 그 이름·시그니처를 그대로 쓴다

  3. 수용 기준에 해당 항목이 있는가 — 있으면 테스트를 같이 쓴다
  4. dotnet build && dotnet test 전체 통과
  5. 문서와 어긋나는 변경이면 같은 커밋에서 해당 레퍼런스도 수정한다

17자주 막히는 곳

Q. warn: 미생성 버킷 2880건이 뜬다. 고장인가?

아니다. 프리베이크를 안 돌린 상태라는 뜻이고, 이 경우 아키타입 폴백 40개로 정상 동작한다. LLM 없이 검증만 할 거라면 이 상태가 정상이다.

Q. NPC들이 아무것도 안 하고 가만히 있다.

--player-bots 0으로 돌렸을 가능성이 높다. 가상 플레이어가 없으면 모든 NPC가 비활성 LOD 밴드에 머물러 이벤트가 있을 때만 깨어난다. 기본값 20으로 두면 된다.

Q. ./masterdata나 ./scenarios/siege.jsonl 같은 상대경로가 안 잡힌다.

dotnet run --project src/Npc.Host는 작업 폴더를 프로젝트 폴더로 잡는다. 그래서 호스트는 --masterdata·--planstore·--scenario·--trace를 전부 기동 직후 한 번에 풀고, 못 찾으면 저장소 루트를 위로 찾아 올라간다. --trace로 새로 만드는 파일도 저장소 루트 기준이다 — 같은 명령이 실행 방식에 따라 다른 곳에 쓰면 안 되기 때문이다.

그래도 못 찾으면 한 줄짜리 에러와 종료 코드 2로 끝난다(스택트레이스가 아니다). 경로를 확인하거나 절대경로를 주면 된다.

Q. 빌드가 경고 하나 때문에 실패한다.

TreatWarningsAsErrors=true다. 의도된 동작이다. #pragma warning disable로 억제하지 말고 원인을 고친다.

Q. 테스트가 Gate 카테고리에서 실패한다.

Gate는 실측 산출물이 있어야 판정되는 항목이다. planstore/manifest.json이나 검수 기록이 없으면 실패하는 것이 맞다 — 없는 것을 통과로 세면 게이트가 거짓이 된다. 평소에는 --filter "Category!=Golden&Category!=Gate"로 돌린다.

Q. LLM 호출이 계속 실패하거나 429가 뜬다.

세 가지를 순서대로 본다. ① 환경변수에 API 키가 있는가 (POE_API_KEY · OPENROUTER_API_KEY · GEMINI_API_KEY) ② 무료 등급은 모델당 하루 500건 제한이 있다 ③ --concurrency를 낮춘다 — AIMD가 429를 보면 자동으로 감속하지만 초기값이 높으면 초반에 몰린다.

Q. 두 번 돌렸는데 기록 파일이 다르다.

--seed·--npcs·--days·--scenario가 전부 같은지 먼저 확인한다. 같은데도 다르면 결정론 규칙 위반이 새로 들어온 것이므로 dotnet test --filter Category=Determinism을 돌린다.

Q. 프리베이크 도중 예산이 끊겼다.

정상 동작이다. manifest가 partial: true로 기록되고, --resume으로 미생성 버킷만 이어서 만들 수 있다.

Q. 플랜을 고쳤는데 다시 생성하니 사라졌다.

planstore/plans/는 생성물이라 덮인다. 사람이 고친 것은 tools/pin_plan.ps1로 planstore/pinned/에 고정해야 살아남는다.
