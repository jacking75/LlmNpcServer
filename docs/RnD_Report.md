## 1. 요약 — 판정과 권고

### 한 문장

> **런타임 LLM 은 아직 근거가 없고, 오써링 자동화는 근거가 생겼다.
> 그리고 이 프로젝트가 실제로 만들어 낸 것은 LLM 없이도 도는 결정론적 NPC 서버다.**

### 판정

| 축 | 판정 | 근거 |
|---|---|---|
| **결정론 런타임** | **성립한다** | 5,000 NPC 틱 p99 **0.37ms** (예산 20ms) · Gen0 GC 0 · 기록 2회 바이트 동일 · 재생 명령 열 동일 |
| **가용성 (LLM 없이)** | **성립한다** | T2 → T1 → PlanStore 3단 차단에서 5,000 NPC 가 게임 13일 완주. 크래시 0 · 오버런 0 |
| **플랜 품질** | **조건부** | 골든 단언 합격률 **93.6 %** (게이트 90 %). 단 4단 검증 통과율은 **78 %** 라 22 %가 폴백으로 떨어진다 |
| **오써링 자동화** | **정황 근거 있음** | 커버리지 **72배** (40 → 2,880), 기계 시간 0.32h · $5.12. 다만 사람 비교값이 미측정이다 |
| **런타임 LLM** | **근거 없음** | 이 빌드의 런타임은 LLM 을 한 번도 부르지 않는다 (P4 미착수). 비용·지연 실측이 없다 |
| **블라인드 A/B** | **결론 보류** | 참가자 0명. 자료 40건과 분석기는 준비됐다 |

### 권고

1. **결정론 NPC 런타임을 먼저 자산으로 확정한다.** LLM 판정과 무관하게 이미 완성돼 있고,
   P1 게이트 8/8 · P5 결정론 100 % 일치로 검증됐다. 이것만으로도 쓸 수 있다.
2. **오써링 자동화는 "도달 집합"으로 좁혀서 간다.** 2,880개 중 실제로 도달하는 것은
   **264개(9.2 %)** 다 (§6). 전량을 만들 이유가 없고, 좁히면 비용이 1/11 이 된다.
3. **런타임 LLM 은 판단을 미룬다.** P4(스케줄러·티어링)가 없어 요청 수·지연·비용의
   실측이 하나도 없다. 지금 결정하면 계획서의 추정을 근거로 결정하는 것인데,
   그 추정은 **비용에서 5배, 지연에서 2~3배 빗나갔다** (§3.1·§3.3).
4. **블라인드 평가를 실제로 돌린다.** 이것 없이는 "사람 수준인가" 에 답할 수 없고,
   그것이 이 프로젝트의 원래 질문이다. 자료·양식·분석기는 다 있고 사람만 필요하다.

## 3. 기술 검증 결과

### 3.1 처리량 · 지연 — 실측 vs 계획 추정

| 항목 | 계획 추정 | 실측 | 판정 |
|---|---|---|---|
| 틱 p99 (NPC 5,000) | ≤ 20ms | **0.37 ms** | 통과 (54배 여유) |
| 인지 스캔 | ≤ 150/틱 | 150 (상한에 붙음) | 통과 |
| 틱 루프 할당 | Gen0 = 0 | **0 B/틱** | 통과 |
| 로컬 LLM 지연 (8B) | 1.75 s | **5.1 s** | **미달 (2.9배)** |
| 로컬 LLM 지연 (4B) | 1.75 s | **3.7 s** | **미달 (2.1배)** |

**틱 루프는 예산을 크게 남긴다.** 병목은 전부 LLM 쪽이다.
로컬 지연이 2~3배 빗나간 큰 원인은 **VRAM 8GB 제약**이다 —
8B Q4_K_M 가중치만 4,789 MiB 라 KV 캐시를 눌러야 겨우 올라간다(`W1_env.md`).

### 3.2 캐시 아키텍처 효과

| 항목 | 값 | 출처 |
|---|---|---|
| 프리픽스 캐시 prefill 절감 | **85~88 %** (1,531→237ms · 2,608→316ms) | W1 |
| 프롬프트 캐시 적중률 | **30.7 ~ 42.6 %** | W8·W11·W12 |
| 캐시로 줄인 비용 | **33.4 %** ($0.3294 → $0.2193) | `cost_actual.md §3` |
| 플랜 캐시(버킷) 히트율 | **미측정** — 프리베이크 전량 회차가 없다 | - |

**설계 판단은 옳았고 목표치는 틀렸다.** 프리픽스 캐시는 prefill 을 실제로 85~88 % 줄였다.
하지만 게이트가 요구한 적중률 95 % 는 **명시적 캐싱** 전제이고, 실제로 쓴 Gemini 계열은
암시적 캐싱이라 요청 단위로 전부 적중하거나 전부 미적중한다 — 어느 쪽일지 비결정적이다
(`W8_prebake.md §2`). 이 엔진 계열에서 95 % 는 도달 불가다.

### 3.3 비용 실측

| 시나리오 | 계획 추정 | 실측(환산) | 오차 |
|---|---|---|---|
| 프리베이크 2,880건 | $0.94 | **$5.12** | **+445 %** |
| 월 운영 (20,000 재계획/일) | $195 | **$609** | +212 % |
| 요청당 입력 토큰 | 1,750 | **13,948** | **8.0배** |

**오차의 대부분이 한 원인이다 — 프리픽스 크기를 축소판으로 추정했다.**
계획의 1,500 토큰은 액션 12·플래그 16 짜리 축소 카탈로그 값이었고, 정식 카탈로그는
11,967 토큰이다. **비용 모델 자체(토큰 × 단가, 캐시 1/10 할인)는 실측과 일치한다.**

절대 금액은 여전히 작다 — 5배 틀려도 월 $609 는 단일 월드 운영비로 큰 값이 아니다.
자세한 내역: [`measurements/cost_actual.md`](measurements/cost_actual.md).

### 3.4 가용성 — 시나리오 C

| 단계 | 남은 것 | 결과 |
|---|---|---|
| T2 차단 | 캐시 + T1 | 라우터가 T1 으로 강등 (단위 테스트) |
| T1 차단 | 캐시만 | 재계획 거절, 기존 플랜으로 계속 |
| PlanStore 차단 | 폴백 40개 | **5,000 NPC 게임 13일 완주** · p99 0.367ms · 갭 0 |

**"LLM 이 전부 죽어도 NPC 는 멈추지 않는다"가 실측으로 확인됐다.**
`PlanStore.Resolve` 가 절대 null 을 반환하지 않는 설계(CLAUDE.md §2.6)가 여기서 값을 한다.

추가 장애 5종도 통과했다 — 링크 단절 시 명령 축적·복구, 시퀀스 갭 경보,
드롭율 5 % 에서 타임아웃 합성, 429 폭주 AIMD 감속, 타임아웃 30초 서킷 개방 (T5-10).

## 4. 품질 검증 결과

### 4.1 검증 통과율과 실패 원인

| 지표 | 목표 | 실측 | 판정 |
|---|---|---|---|
| 4단 검증 통과율 | ≥ 90 % | **78.3 %** (고른 표본 60) / 67.7 % (연속 288) | **미달** |
| 폴백까지 떨어진 비율 | ≤ 5 % | **15.6 %** | **미달** |
| 골든 단언 합격률 | ≥ 90 % | **93.6 %** (206/220) | **통과** |

**두 수치가 어긋나 보이는데, 재는 것이 다르다.**
통과율은 "플랜이 4단을 다 통과했는가"이고, 골든은 "플랜이 상황에 맞는가"를 9종 단언으로
나눠 본다. 골든에서도 `validates` 단언만 보면 **82 %** 로 통과율과 같은 수준이다.

실패 원인 분포(골든 50건 × 3회, 합격 못 한 단언 14개):

| 원인 | 단언 수 |
|---|---|
| `V3.PRECONDITION_UNMET` (전제 플래그 미충족) | 4 |
| 컴파일 실패 — 없는 `npc_ref` 심볼을 지어냄 (`nearest:horse`) | 3 (픽스처 1건이 3단언을 끌고 감) |
| `V2.ACTION_NOT_ALLOWED` (아키타입에 없는 액션) | 2 |
| `V4.DEADLOCK` / `V4.INFINITE_LOOP` | 2 |
| 속성 단언 실패 (기대한 액션 누락 · 산출물 없음) | 3 |

**가장 흔한 실패는 "장소로 이동하지 않고 그 장소의 액션을 한다" 하나다.**
프롬프트에 액션별 플래그 표를 실어(T2-03) 크게 줄였지만 남아 있다.

### 4.2 블라인드 A/B 결과

**결론 보류 — 참가자 0명.**

준비된 것: 자료 40건(A군 20 + B군 20, 짝 매칭) · 응답 양식 · 정답 키(시드 고정) ·
통계 처리기(이항검정 · 짝지은 t검정 + Cohen's d · 부호검정 · 95 % 신뢰구간).

짝 매칭은 정의상 완벽하다 — 두 실행은 `--planstore` 만 다르고 **같은 NPC 가 같은 세계·
같은 시각**을 두 번 살았다. 아키타입·시간대·지역상태를 따로 맞출 필요가 없다.

필요한 것은 사람 12명 × 40~60분이다. [`measurements/blind_eval_result.md`](measurements/blind_eval_result.md).

### 4.3 플랜 다양성

| 지표 | 목표 | 실측 |
|---|---|---|
| 유니크 액션 시퀀스 / 생성 성공 | 60 % | **37.1 %** |
| 아키타입 안 유니크 비율 | 60 % | 51.6 % |

## 6. 발견과 예상 밖의 것

### 6.1 버킷의 91 %는 애초에 쓰이지 않는다 — 가장 값어치 있는 발견

| 시나리오 | 도달 버킷 | 비율 | 비용 |
|---|---|---|---|
| A — 평시 하루 | **264** | **9.2 %** | $0.47 |
| B — 공성 | 978 | 34.0 % | $1.74 |
| 전량 | 2,880 | 100 % | $5.12 |

**지역상태 4종 중 2종(War·Disaster)과 기후 3종 중 1종(Storm)이 어느 존의 기본값도 아니다.**
게다가 아키타입과 존이 묶여 있어(광부는 광산 언덕에만 산다) 한 아키타입이 겪는
(지역상태, 기후) 조합은 보통 하나다 — 둘 이상 겪는 것은 4종뿐이다.

**이건 버킷 차원을 잘못 설계했다는 뜻이 아니다.** 미도달 버킷은 폴백이 이미 덮고 있고
(시나리오 C 가 확인), War·Disaster 버킷은 "공성이 터진 뒤에 만들면 늦으니 미리 만들어 두는 값"이다.
**다음 버전은 도달 집합만 만들어 1/11 비용으로 갈 수 있다.**
자세한 내역: [`measurements/bucket_usage.md`](measurements/bucket_usage.md).

### 6.2 강제 디코딩이 프롬프트 지시보다 나빴다 — 통념의 반례

| 모드 | 유효 JSON | 어휘 검증 통과 |
|---|---|---|
| `forced` (json_schema strict) | **99/100** | **0/100** |
| `prompt` (지시만) | 93/100 | 93/100 |

**스키마를 만족시키면서 인자를 지어낸다.** 실패는 전부 `V2.UNKNOWN_ARG` 였다 —
문법은 완벽한데 존재하지 않는 아이템·POI 를 쓴다. "strict 모드면 안전하다"는
통념이 여기서 깨졌고, 이 프로젝트는 강제 디코딩을 **기본에서 뺐다**.

> `docs/10 §5` 의 위험 신호("유효율 90 % 미만")로는 이 실패가 잡히지 않는다.
> 유효율은 99 % 였다. **측정 지표를 잘못 고르면 100 % 실패를 통과로 읽는다.**

### 6.3 로컬 지연이 계획 가정의 2~3배다 — 그리고 원인은 모델이 아니라 VRAM

| 모델 | 계획 가정 | 실측 |
|---|---|---|
| 4B | 1.75 s | 3.7 s |
| 8B | 1.75 s | 5.1 s |

동시성을 올리면 4B 는 2.46 → 12.07 req/s 로 오르는데 **8B 는 동시 8에서 0.36 req/s 로 붕괴한다.**
배칭이 없어서가 아니라 **VRAM 8GB 에서 KV 캐시가 넘쳐 PCIe 페이징이 걸리기 때문**이다.
같은 코드가 24GB 급에서는 다른 곡선을 그린다 — 이 수치를 그대로 상용에 옮기면 안 된다.

### 6.4 프리픽스 캐시가 prefill 을 85~88 % 줄였다 — 설계 판단은 옳았다

| 엔진 | 캐시 없음 | 캐시 있음 | 절감 |
|---|---|---|---|
| 4B | 1,531 ms | 237 ms | 85 % |
| 8B | 2,608 ms | 316 ms | 88 % |

dotLLM 의 prefill 이 llama.cpp 의 2~5배라는 것이 프리픽스 고정 설계의 이유였고,
그 판단은 실측으로 옳았다.

### 6.5 예상 밖 — 이번 Phase 에서 나온 버그 셋

세 개 다 "테스트를 쓰다가" 발견됐고, 전부 **아무도 보지 않던 경로**에 있었다.

1. **기록이 실행마다 달랐다.** 같은 시나리오 2회에서 이벤트 30,416 vs 30,649.
   원인 셋 — 이벤트 배수가 틱 경계를 넘었고, flush 가 틱마다가 아니었고,
   게임서버 대역이 명령 flush 전에 다음 틱을 밀었다. 고치니 바이트 동일이 됐고
   **전체 테스트가 1분 39초 → 42초로 오히려 빨라졌다.**
2. **Null 링크가 이벤트 시퀀스로 명령 카운터를 썼다.** 1,440틱에 갭 445건.
   "성능 기준선" 이라 아무도 이벤트를 안 봤고, 링크 4종을 나란히 놓기 전에는 안 드러났다.
3. **티어 라우터가 외부 타임아웃을 그대로 흘려보냈다.** `HttpClient` 타임아웃도
   `TaskCanceledException` 이라 "호출자 취소" 필터에 걸려 나갔다. 서킷이 영영 안 열린다.

## 7. 상용 전환 시 남는 과제

### 7.1 실제 네트워크 구현 (`docs/02 §7`)

`TcpGameServerLink` 는 골격만 있다(컴파일되고 전송에서 던진다). 필요한 것 5가지 —
프레이밍 · 직렬화(MemoryPack 또는 소스 생성) · 재접속과 시퀀스 재동기화 ·
Nagle 비활성 + 배치 코얼레싱 · 흐름 제어.

**이 5가지 중 NPC 서버 코드를 건드려야 하는 것은 없다.** T5-11 이 그것을 기계로 고정했다 —
`Npc.Runtime`·`Npc.Core`·`Npc.Planning` 은 `Npc.Gateway` 를 **참조조차 하지 않는다.**

### 7.2 GPLv3 (dotLLM)

dotLLM 은 GPLv3 다. 인프로세스 임베딩이 금지이고 별도 프로세스 + HTTP 경계를 유지해야 한다
(CLAUDE.md §2.7). 현재 설계가 그 경계를 지키고 있으나 **법무 확인이 남았다.**
`IChatClient` 추상화 덕에 엔진 교체 자체는 설정 한 줄이다.

### 7.3 다중 월드 스케일 비용

여기 수치는 **단일 월드 5,000 NPC** 다. 월드가 N개면 프리베이크는 공유되지만
(마스터데이터가 같다면) 런타임 재계획은 N배가 된다. 월 $609 × N 이 되는 구조이고,
§6.1 의 도달 집합 축소가 여기서 다시 값을 한다.

### 7.4 continuous batching 부재 → llama.cpp / vLLM 전환 검토

dotLLM 은 continuous batching 이 없다. 동시 2에서 처리량이 오르고 4에서 평평해지는 것이
그 결과다. T1 을 진지하게 쓸 거라면 vLLM 이나 llama.cpp 서버로 갈아타는 것을
먼저 재야 한다 — `IChatClient` 뒤라 코드 변경은 없다.
