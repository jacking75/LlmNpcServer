# 1장 — 옵션 하나씩 바꿔 보기

`variants.ps1` 이 뽑은 표다. 전부 `--max-speed`(10Hz 페이싱 없음)라 한 회차가 몇 초면 끝난다.

```powershell
./samples/ch01_first_run/variants.ps1 -NoBuild -Csv ./lab/ch01_variants.csv
```

## 읽는 법 — 이 표에서 볼 것 다섯

**1. LLM 열이 전부 0이다.** 옵션을 어떻게 바꾸든 `--no-llm` 인 한 LLM 은 한 번도 안 불린다.
명령은 최대 279만 건이 나갔다. 플랜은 이미 만들어져 있었고 런타임은 실행만 했다.

**2. `bytes/tick` 이 전부 0이다.** NPC 를 100배로 늘려도 틱 루프는 힙에 한 바이트도 안 쓴다.
NPC 상태가 SoA(struct of arrays) 배열이고, 틱 루프에 `new`·LINQ·문자열 보간이 없기 때문이다.
이 열이 0이 아니게 되는 순간이 회귀다 — 19장에서 일부러 깨뜨려 본다.

**3. NPC 100배에 p99 는 23배다** (0.105 → 2.368 ms). 선형보다 낫다. 그리고 여전히 예산 20ms 의 12% 다.

**4. `--npcs 5000` 의 스캔/틱이 정확히 150이다.** 우연이 아니라 상한값이다
(`CognitionScheduler.MaxScansPerTick`). 5,000마리를 매 틱 전수 조사하지 않고 150마리만 본다 —
이 상한이 "NPC 를 늘려도 인지 비용이 O(1)" 을 만든다. 6장의 주제다.

**5. `--drop-rate 0.2` 에서 명령은 줄고 타임아웃은 늘었다** (26,746 → 20,509 / 3,980 → 5,802).
명령 5건 중 1건을 버렸는데 **NPC 는 멈추지 않았다.** 응답 이벤트가 안 오면 NPC 서버가
로컬에서 `ActionFailed(Timeout)` 을 합성해 진행을 재개하기 때문이다.
"명령은 유실된다고 가정한다"는 설계가 여기서 눈에 보인다. 11장에서 더 세게 흔든다.

## 덤으로 보이는 것 둘

**`--player-bots 0` 의 명령·스텝·타임아웃이 기준선과 한 건도 안 틀리다.**
플레이어가 하나도 없으면 인지 스캔이 0이 되지만(스캔/틱 0), **행동은 똑같다.**
인지 스캔은 *누구를 재계획 대상으로 고를까* 를 정할 뿐이고, `--tier none` 에서는
재계획 자체가 없으므로 결과가 바뀌지 않는다. 티어를 켜면 달라진다 — 16장에서 다시 본다.

**배속이 높을수록 타임아웃 비율이 커진다.** 배속 600에서 1틱 = 게임 60초이므로
`timeout_s: 300` 인 스텝은 5틱이면 만료된다. 배속 60(1틱 = 게임 6초)에서는 50틱을 기다린다.
같은 게임 1일인데 배속 600은 스텝의 16%가 타임아웃이고, 배속 60은 6%다.
**배속은 "빨리 보기" 옵션이지 "같은 것을 빨리 보기" 옵션이 아니다.**
NPC 의 하루를 제대로 관찰하려면 배속을 60 쯤으로 낮춘다 — 2장이 그렇게 한다.
